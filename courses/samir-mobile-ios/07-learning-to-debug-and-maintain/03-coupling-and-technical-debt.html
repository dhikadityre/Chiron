Belajar Debugging & Maintenance — 03. Coupling and Technical Debt

📚 Modul: 03-coupling-and-technical-debt 🎯 Scope: SAMIR Mobile (iOS Native UIKit & FChannel) ⏱️ Estimasi: 20 Menit 🏷️ Git Branch: learn/iOS-Arch

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumen ini menyajikan audit menyeluruh terhadap arsitektur, derajat keterikatan (coupling), dan utang teknis (technical debt) di dalam codebase iOS SAMIR. Sebagai senior engineer yang baru bergabung, pemahaman terhadap area-area rentan ini krusial agar Anda dapat memperkirakan risiko sebelum melakukan perubahan fitur atau estimasi beban kerja teknis.

🎯 A. Learning Objective

Setelah mempelajari dokumen ini, Anda diharapkan mampu:

  1. Mengidentifikasi titik-titik utang teknis kritis berisiko tinggi (high-risk debt), menengah (medium-risk), dan rendah (low-risk).
  2. Memahami konsekuensi dari ~1.488 force unwraps (!) dan hardcoded credentials terhadap stabilitas dan keamanan aplikasi.
  3. Memetakan God Objects dan Massive ViewControllers yang melebihi 1.000 hingga 2.200 baris kode.
  4. Menganalisis isolasi paradigma reaktif (RxSwift "Island") pada modul pinjaman dibanding keseluruhan arsitektur aplikasi.
  5. Mengetahui bug tersembunyi pada module loader (module priority no-op bug) dan salah ketik API protokol (reapyService).
  6. Memahami batasan penting: tidak ada refactoring yang diizinkan dalam fase dokumentasi ini, namun semua temuan dicatat dengan bukti kode yang valid.

📋 B. Prerequisites

Sebelum membaca dokumen ini, Anda disarankan telah membaca:

  • 03-understanding-architecture/01-architecture-overview.md — Struktur modular monolith SAMIR.
  • 03-understanding-architecture/04-shared-components-and-services.md — Service registry IDServiceManager.
  • 07-learning-to-debug-and-maintain/02-testing-and-debugging.md — Ketiadaan target pengujian otomatis.

💡 C. Simple Explanation: "Peta Ranjau di Dalam Kode"

Bayangkan Anda pindah ke rumah tua yang baru direnovasi sebagian. Ruang tamu tampak modern, tetapi di balik dinding terdapat sambungan kabel tanpa isolator (force unwraps), kunci pintu utama tersimpan di bawah keset (hardcoded secret), dan pipa air dari dapur tersambung langsung ke pipa pembuangan tanpa katup pengaman (tight coupling).

Di SAMIR:

  • Aplikasi berfungsi dengan baik di tangan ratusan ribu pengguna karena alur pengujian manual (QA) yang ketat.
  • Namun dari kacamata arsitektur, terdapat beberapa "ranjau teknis" yang dapat meledak menjadi crash runtime jika seorang developer baru mengubah tipe data respons API atau melakukan force-unwrapping pada nilai opsional yang bernilai nil.

1. Kategori Risiko Tinggi (High Risk) [Verified]

A. 1.488 Force Unwraps & Force Casts (! / as!)

Pemeriksaan kode dengan ripgrep menemukan sekitar 1.488 baris yang menggunakan tanda seru paksa tanpa guard let atau if let defensif.

  • Bukti Sampel:
    • IDNetworkRequest.swift:L480: Akses paksa dictionary response.
    • IDMainTabBarController.swift:L65: rootVC.view.addSubview(self.button!).
    • Presenter Auth & KTP: Akses paksa image picker result dan parsing tanggal lahir.
  • Dampak: Backend yang mengirimkan field null tak terduga akan langsung menyebabkan crash fatal SIGABRT di runtime pengguna.
B. Kredensial & Kunci Rahasia Hardcoded

Kunci rahasia third-party dan enkripsi disimpan langsung sebagai string literal di dalam kode sumber:

  • AppsFlyer Dev Key:
    • File: ios/IDSamirLoan/Application/SamirPointsModule/Classes/IDAppsFlyerManager.swift:L24
    • Bukti: AppsFlyerLib.shared().appsFlyerDevKey = "KMuxXxjrdNtBQE4M83xR8h"
  • Static AES-GCM Key:
    • File: ios/IDSamirLoan/Application/SamirLoginModule/Classes/IDModel/IDLoginCodeModel.swift:L33
    • Bukti: static let staticKey = SymmetricKey(data: "samir-ios-secure-key-2024".data(using: .utf8)!)
  • Dampak: Siapa pun yang melakukan dekompilasi IPA dapat mengekstraksi kunci analitik dan kunci enkripsi file sesi pengguna lokal.
C. Penonaktifan ATS Global (NSAllowsArbitraryLoads = true)
  • File: ios/IDSamirLoan/Application/IDSamirLoan-Info.plist:L93-97 
<key>NSAppTransportSecurity</key>
<dict>
    <key>NSAllowsArbitraryLoads</key>
    <true/>
</dict>
  • Dampak: Membuka kerentanan Man-in-the-Middle (MitM) jika WebView atau API client memanggil endpoint http:// non-terenkripsi. Berpotensi ditolak saat audit berkala App Store jika tidak disertai justifikasi eksplisit.
D. Ketiadaan Pengujian Otomatis (Zero Tests)
  • Bukti: Tidak ada file *Tests.swift, tidak ada dependensi Quick/Nimble, dan tidak ada target test di project.pbxproj.
  • Dampak: Tim tidak memiliki safety net otomatis saat melakukan refactoring atau pembaruan dependensi.

2. Kategori Risiko Menengah (Medium Risk) [Verified]

A. Massive ViewControllers & God Objects

Terdapat file-file raksasa yang menggabungkan presentation logic, view layouting, validasi input, dan network orchestration:

File SumberBaris KodePeran & Masalah Arsitektur
LoanConfirmViewController_Rx.swift2.250 barisForm konfirmasi pinjaman raksasa: kalkulasi bunga, agreement checkbox, OTP trigger, dan dynamic fee breakdown.
LoanConfirmService.swift1.541 barisService pinjaman mengelola puluhan state request dan model mapping.
LoanConfirmAmountView.swift1.465 barisView pemilihan nominal dan tenor pinjaman dengan animasi slider dan label formatting.
IDNetworkRequest.swift1.428 barisGod-class networking: signature generation, parameter injection, header assembly, error parsing, dan DebugUI bridge.
LoanConfirmViewModel.swift1.396 barisState store pinjaman dengan puluhan BehaviorRelay dan PublishSubject.
IDNewAuthPresenter.swift1.251 barisPresenter e-KYC 6 langkah dengan logika parsing respon OCR, Liveness, dan Advance AI.
IDHomeViewController.swift1.212 barisDashboard tab pertama: polling status aplikasi, dynamic banner, dialog popups, dan rating prompt.
B. Isolasi Reaktif RxSwift ("The Reactive Island")

Modul SamirLoanConfirmModule ditulis menggunakan arsitektur MVVM berbasis RxSwift & RxCocoa (BehaviorRelay, DisposeBag, Observable.combineLatest), sementara seluruh modul lainnya (SamirAuthModule, SamirMainModule, SamirLoginModule) menggunakan pola imperatif MVP + Delegates/Closures.

  • Dampak: Developer harus menguasai dua paradigma mental yang saling bertolak belakang dalam satu aplikasi. Terjadi fragmentasi standar penulisan kode.
C. Assertion Failure pada Duplikasi Host Router
  • File: CZSwiftRouterLib/Classes/CZRouterCenter.swift:L48 
if self.routerMap.keys.contains(host) {
    assertionFailure("Host already exists: \(host)")
}
  • Dampak: Jika ada developer baru yang mendaftarkan router handler dengan host yang sama (misalnya samir://order), aplikasi akan langsung crash pada mode Debug/Test. Pada mode Release/Production, assertionFailure diabaikan oleh compiler sehingga handler lama ditimpa tanpa peringatan.
D. Module Priority No-Op Bug
  • File: CZSwiftModuleLib/Classes/CZModuleManager.swift:L87-92 
var moduleContext = CZModuleContext()
// moduleContext.modulePriority tidak pernah diisi dari moduleObject.loadPriority!
self.moduleList.sort { $0.modulePriority > $1.modulePriority }
  • Dampak: Properti loadPriority di IDModuleList.plist sama sekali tidak berfungsi. Urutan inisialisasi modul murni mengikuti urutan iterasi dictionary di dalam file plist.
E. Salah Ketik pada API Protokol Publik: reapyService()
  • File: ios/IDSamirLoan/Application/SamirServiceModule/Classes/IDServiceManager.swift:L25 
public static func reapyService() -> IDReapyServiceProtocol?
  • Dampak: Typo huruf 'p' dan 'a' tertukar (reapy alih-alih repay). Karena sudah tersebar di puluhan call site, perbaikan typo ini memerlukan refactoring massal lintas modul.

3. Kategori Risiko Rendah & Kode Mati (Low Risk / Dead Code) [Verified]

  1. File main.m (Objective-C):
    • File ios/IDSamirLoan/Application/Launcher/main.m masih tersimpan di repository namun target entry point aktif menggunakan main.swift.
  2. Stub Kosong IDSamirRepayRouterHandler.swift:
    • Method handler untuk rute samir://repay/historyOrder dan samir://repay/order dibiarkan kosong ({ }) karena fungsionalitas riwayat pembayaran telah dipindahkan ke tab Flutter dan authenticated H5.
  3. Kategori Extension UIImage yang Duplikatif:
    • Terdapat fungsi kompresi gambar yang terduplikasi antara CZSwiftUIKit dan SamirAuthModule.

🪜 E. Step-by-Step Walkthrough: Analisis Bahaya Modifikasi pada IDHomeViewController

Jika Anda diminta untuk menambahkan banner promosi baru di tab Home:

  1. Buka file: ios/IDSamirLoan/Application/SamirLoanModule/Classes/IDController/IDHomeViewController.swift.
  2. Periksa ukuran file: 1.212 baris kode dengan puluhan property tersimpan (var orderModel, var bannerList, var dialogManager).
  3. Telusuri Lifecycle: viewDidLoad memanggil lebih dari 8 method konfigurasi terpisah.
  4. Analisis Risiko Titik Runtuh (Coupling Points):
    • Method pullToRefresh memicu loadAppIndexData().
    • Di dalam closure respon API, terdapat navigasi implisit ke halaman KYC jika auditStatus == 2 atau ke halaman pinjaman jika kuota tersedia.
    • Menambahkan subview baru tanpa memperhatikan auto-layout SnapKit berisiko merusak scroll view container di layar iPhone berukuran kecil (iPhone SE / 8).
  5. Kesimpulan Senior: Selalu pecah view baru menjadi komponen UIView terisolasi (CustomPromoBannerView) daripada menulis 200 baris kode tambahan langsung di dalam IDHomeViewController.swift.

⚖️ F. Why It Matters: Rencana Strategis Penanganan Teknis

Meskipun tidak boleh melakukan refactoring pada fase dokumentasi ini, pemetaan utang teknis ini menjadi modal berharga bagi tim engineering untuk menyusun Technical Debt Roadmap:

  1. Fase 1 (Safety First): Mengganti force unwraps (!) pada layer networking dan model parsing dengan guard let dan default fallback values.
  2. Fase 2 (Security Hardening): Memindahkan API keys ke xcconfig/environment injection dan meninjau ulang domain whitelist untuk ATS.
  3. Fase 3 (Modular Decomposition): Memecah LoanConfirmViewController_Rx dan IDHomeViewController menjadi modul-modul sub-komponen presenter/interactor yang lebih kecil.
  4. Fase 4 (Test Foundation): Membuat target IDSamirLoanTests pertama untuk menguji parsing model KakaJSON dan validasi signature LibNetSignGenerator.

🔬 G. Practical Example: Mengapa Force Unwrap Berbahaya di Kasus KYC

Perhatikan pola rentan berikut di controller upload KTP:

// Pola Rentan yang Ditemukan di Codebase:
let image = info[.originalImage] as! UIImage // Crash jika user memilih format gambar HEIC/WebP yang tidak kompatibel!
let compressedData = image.jpegData(compressionQuality: 0.5)! // Crash jika gambar corrupt!

// Pola Aman yang Direkomendasikan untuk Masa Depan:
guard let image = info[.originalImage] as? UIImage,
      let compressedData = image.jpegData(compressionQuality: 0.5) else {
    IDToast.show(text: "Format foto tidak didukung, silakan ambil ulang.")
    return
}

⚠️ H. Common Mistakes and Debugging

1. Menghapus Protocol Method yang Mengandung Typo Tanpa Cek Dependensi

  • Kesalahan: Mencoba memperbaiki reapyService() menjadi repayService() di IDServiceManager.swift.
  • Akibat: Proyek langsung gagal compile (build error) di puluhan modul karena protocol conformance di SamirRepayModule dan pemanggilan di IDMainTabBarController masih mengacu ke nama lama.

2. Mendaftarkan Route dengan Host yang Sama

  • Kesalahan: Membuat rute samir://auth/biometric padahal host auth sudah didaftarkan oleh IDSamirAuthRouterHandler.
  • Akibat: Crash fatal assertionFailure("Host already exists") saat aplikasi baru pertama kali dibuka di lingkungan Debug.

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Keterikatan Kuat Antar Sub-Modul & Kurangnya Inversi Dependensi

Implementasi komponen sering mengasumsikan keberadaan lingkungan runtime tertentu tanpa kontrak antarmuka yang didefinisikan secara tegas.

⚠️ Smells 2: Risiko Regresi & Minimnya Kontrak Pengujian Terisolasi

Perubahan pada satu service atau helper berpotensi merusak fungsionalitas di modul lain karena tingginya kohesi tersembunyi antar file.

🚀 Blueprint Refactoring Standar Industri: Pola Service Locator & Interface Segregation (SOLID)

Menerapkan prinsip Interface Segregation (ISP) dan Dependency Injection agar setiap service hanya mengekspos metode yang relevan bagi kliennya.

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol SessionProvider: AnyObject {
    var currentToken: String? { get }
    var isAuthenticated: Bool { get }
}

public final class AppSessionManager: SessionProvider {
    public static let shared = AppSessionManager()
    public var currentToken: String?
    public var isAuthenticated: Bool { currentToken != nil }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
