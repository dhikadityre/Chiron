Belajar Debugging & Maintenance — 04. Change Impact Analysis

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumen ini adalah panduan penilaian risiko (blast radius analysis) sebelum Anda memodifikasi kode di codebase iOS SAMIR. Sebagai senior mobile developer, dokumen ini membekali Anda dengan peta dampak perubahan, area-area paling berbahaya (danger zones), dan pre-PR verification checklist untuk mencegah regresi sistemik.

🎯 A. Learning Objective

Setelah mempelajari dokumen ini, Anda diharapkan mampu:

  1. Memetakan blast radius (radius ledakan dampak) dari setiap perubahan pada komponen fondasi, networking, routing, dan integrasi hybrid.
  2. Memahami konsekuensi fatal dari modifikasi parameter umum API terhadap generator signature (LibNetSignGenerator).
  3. Mencegah regresi pada sistem deep link dan JavaScript Bridge (H5-to-Native) saat mengubah format routing.
  4. Menjaga kontrak komunikasi MethodChannel antara Swift native dan Flutter engine tetap sinkron.
  5. Menjalankan Pre-PR Verification Checklist komprehensif sebelum mengajukan code review.

📋 B. Prerequisites

Sebelum membaca dokumen ini, Anda disarankan telah membaca:

  • 04-understanding-navigation/02-navigation-fundamentals.md — Mekanisme registrasi router SAMIR.
  • 06-understanding-data-and-dependencies/02-networking-and-api-flow.md — 18 parameter umum dan signature hashing.

💡 C. Simple Explanation: "Mengetahui Kabel Mana yang Menyetrum Sebelum Memotong"

Bayangkan Anda sedang merenovasi sirkuit kelistrikan di gedung bertingkat. Jika Anda memotong kabel lampu di koridor lantai 3, hanya lampu koridor yang padam. Namun, jika Anda mencabut sekring utama di ruang genset bawah tanah, seluruh gedung akan gelap gulita dan lift akan berhenti mendadak.

Di SAMIR:

  • Ada perubahan lokal berisiko rendah, misalnya mengubah warna teks di halaman syarat & ketentuan pinjaman.
  • Namun ada komponen fondasi (seperti ApiParamsHelper, CZRouterCenter, atau IDLoginCodeModel) yang bila diubah satu baris saja, dampaknya dapat melumpuhkan seluruh transaksi pinjaman, merusak token sesi semua pengguna, atau membuat aplikasi crash saat pertama kali dibuka.

1. Zona Berbahaya 1: Networking, Headers, & Signature [Verified]

  • File Kunci:
  • ios/IDSamirLoan/Application/SamirNetworkModule/Classes/Common/ApiParamsHelper.swift
  • ios/IDSamirLoan/Application/SamirNetworkModule/Classes/Common/IDNetworkRequest.swift
  • Tingkat Bahaya: EXTREME (100% dari seluruh fungsionalitas aplikasi)
  • Mekanisme Dampak:
  • ApiParamsHelper menyuplai 18 parameter umum (seperti mid, userNo, sysVersion, appVersion, channelCode, token).
  • Parameter ini diurutkan dan dikirim ke framework biner tertutup LibNetSignGenerator.framework untuk membuat header sign.
  • Skenario Bencana: Jika Anda mengubah penamaan parameter (misalnya mengubah sysVersion menjadi systemVersion) atau mengubah urutan enkapsulasi parameter, generator signature akan menghasilkan hash yang tidak cocok dengan formula backend.
  • Akibat: Seluruh panggilan API di aplikasi (Login, Home, KYC, Konfirmasi Pinjaman, Repayment) akan serentak ditolak oleh server gateway dengan respons error code: 10004 (Signature verification failed).

2. Zona Berbahaya 2: Router Tables & URL Schemes [Verified]

  • File Kunci:
  • CZSwiftRouterLib/Classes/CZRouterCenter.swift
  • ios/IDSamirLoan/Application/SamirMainModule/Classes/IDRouter/IDRouterManager.swift
  • IDSamir*RouterHandler.swift
  • Tingkat Bahaya: HIGH (Navigasi global, Deep Link, dan H5 Bridge)
  • Mekanisme Dampak:
  • Router bekerja berdasarkan pola skema URL samir://<host>/<path>.
  • Terdapat tiga konsumen eksternal yang mengandalkan kestabilan URL scheme ini:
  1. APNs Push Notification Payload: Notifikasi promosi dari server membawa string deep link mentah.
  2. H5 Marketing / Event Banners: Halaman webview memanggil fungsi JavaScript callApp({url: "samir://..."}).
  3. Backend App Configuration: Respons API getAppIndexNew mengembalikan route target ke tahapan KYC pengguna.
  • Skenario Bencana:
  • Jika Anda mengubah format path (misalnya samir://auth/baseInfo diubah menjadi samir://auth/step1), maka notifikasi yang dikirim server atau halaman webview yang belum diperbarui akan gagal membuka layar target (silent failure / drop).
  • Jika Anda mendaftarkan handler baru dengan nama host yang sudah ada, aplikasi akan crash saat diluncurkan: assertionFailure("Host already exists").

3. Zona Berbahaya 3: Saluran Hybrid Flutter (samir_native_channel) [Verified]

  • File Kunci:
  • ios/IDSamirLoan/Application/SamirMainModule/Classes/Flutter/FlutterEngineManager.swift
  • ios/IDSamirLoan/Application/SamirMainModule/Classes/IDController/IDMainTabBarController.swift
  • Tingkat Bahaya: HIGH (Tab Repay, Tab Mine, dan Konsistensi Token Sesi)
  • Mekanisme Dampak:
  • Flutter engine tunggal (singleEngine) beroperasi di background dan menerima event melalui FlutterMethodChannel(name: "samir_native_channel").
  • Method penting:
  • getRootPageData: Mengirim token, mid, status login, dan environment URL ke Dart runtime.
  • pushNativePage: Menerima instruksi dari Flutter untuk membuka halaman native (KYC atau Pengaturan).
  • nativeLogout: Menginstruksikan pembersihan sesi native saat user logout dari tab Flutter.
  • Skenario Bencana: Mengubah tipe payload dictionary atau nama method channel di sisi Swift tanpa memperbarui kode Dart di repository flutter/ akan mengakibatkan halaman Repay dan Mine menampilkan layar putih (blank screen) atau sesi token tidak sinkron.

4. Zona Berbahaya 4: Penyimpanan Sesi Pengguna Lokal (IDLoginCodeModel) [Verified]

  • File Kunci:
  • ios/IDSamirLoan/Application/SamirLoginModule/Classes/IDModel/IDLoginCodeModel.swift
  • Tingkat Bahaya: CRITICAL (Kehilangan Sesi Seluruh Pengguna / Mass Forced Logout)
  • Mekanisme Dampak:
  • File sesi disimpan terenkripsi di Library/Application Support/idn_userFile.plist menggunakan kunci simetris AES-GCM (staticKey).
  • Skenario Bencana: Jika Anda memodifikasi string kunci staticKey atau mengubah struktur decoding NSCoding / NSSecureCoding tanpa mekanisme migrasi data, aplikasi tidak akan dapat mendekripsi file sesi yang ada saat update versi.
  • Akibat: Seluruh pengguna yang melakukan update aplikasi dari App Store akan otomatis ter-logout (mass forced logout) dan harus memasukkan nomor HP serta OTP ulang.

📌 E. Pre-PR Verification Checklist: Standar Wajib Sebelum Merge Kode

Gunakan checklist ini setiap kali Anda atau anggota tim hendak mengajukan Pull Request (PR):

1. Build & Configuration Verification

  • [ ] Proyek berhasil dicompile di bawah keempat build scheme:
  • [ ] TEST (memastikan DebugUI dan pre-build test macros berfungsi).
  • [ ] PROD-TEST (memastikan environment pre-production stabil).
  • [ ] PROD (memastikan build release bersih dari debug symbols dan logging).
  • [ ] IDSamirEnvironment (memastikan parser environment switch bekerja).
  • [ ] Tidak ada penambahan file di luar folder yang diizinkan (jangan commit file cache .DS_Store atau Pods artifacts).
  • [ ] File konfigurasi build (IDSamirLoan.xcodeproj/project.pbxproj) tidak mengalami modifikasi bundle identifier, provisioning profile, atau deployment target tanpa persetujuan tim lead.

2. Networking & Routing Verification

  • [ ] Tidak ada perubahan nama key pada ApiParamsHelper.swift.
  • [ ] Seluruh endpoint baru yang ditambahkan mengembalikan format envelope { "code": Int, "msg": String, "result": Any }.
  • [ ] Uji coba request di build TEST dan pastikan respon code bernilai 200 (bukan 10004 Sign Verification Failed).
  • [ ] Tidak ada host duplikat yang didaftarkan di IDRouterManager.swift.
  • [ ] Format skema URL baru telah didokumentasikan di katalog rute dan divalidasi terhadap event H5 JSBridge.

3. Memory & Safety Verification

  • [ ] Tidak ada penambahan force unwrap (!) atau force cast (as!) baru pada model decoding dan parsing respons API. Gunakan guard let defensif.
  • [ ] Periksa closure / asynchronous callbacks apakah telah menyertakan [weak self] untuk mencegah retain cycle dan kebocoran memori (memory leak).
  • [ ] Lakukan uji coba navigasi keluar-masuk layar (push lalu pop berulang kali) untuk memastikan deallokasi berjalan normal.

4. Hybrid Sync Verification

  • [ ] Jalankan perpindahan tab: Tab 0 (Home Native) -> Tab 1 (Repay Flutter) -> Tab 2 (Mine Flutter) -> Tab 0.
  • [ ] Pastikan tidak ada stuttering atau penurunan frame rate (FPS drop) saat transisi tab.
  • [ ] Uji alur logout dari halaman Mine (Flutter) dan pastikan Tab 0 (Native) langsung memperbarui tampilan ke status belum login.

⚖️ F. Why It Matters: Stabilitas Finansial & Kepercayaan Pengguna

Sebagai aplikasi pinjaman online berlisensi OJK, kestabilan aplikasi memiliki korelasi langsung dengan reputasi dan finansial perusahaan:

  • Kegagalan Signature (10004): Menghentikan 100% penyaluran pinjaman (disbursement) dan pelunasan angsuran. Kerugian finansial terjadi setiap menit sistem offline.
  • Crash pada Halaman Konfirmasi Pinjaman: Pengguna yang sedang menunggu pencairan dana dapat mengalami ketidakpastian status apakah pinjaman telah disetujui atau gagal, memicu lonjakan tiket komplain di Customer Support.
  • Mass Logout: Mengakibatkan lonjakan biaya SMS OTP (setiap SMS OTP berbayar per pengiriman) dan meningkatkan rasio drop-off pengguna yang malas login ulang.

🔬 G. Practical Example: Mengubah Penamaan Field API Tanpa Menghancurkan App

Misalkan backend meminta penambahan parameter baru deviceModel ke dalam setiap request:

// CARA SALAH (Mengubah properti yang sudah ada):
// Mengubah key 'sysVersion' -> Menghancurkan hash LibNetSignGenerator!

// CARA BENAR:
// 1. Tambahkan parameter baru di akhir dictionary pada ApiParamsHelper:
params["deviceModel"] = UIDevice.current.model

// 2. Lakukan pengujian di skema TEST:
// Buka DebugUI -> tab request -> pastikan backend menerima parameter dan mengembalikan HTTP 200.
// 3. Pastikan backend di staging telah dideploy dengan parser signature yang mengenali field baru tersebut sebelum rilis ke PROD.

⚠️ H. Common Mistakes and Debugging

1. Menguji Perubahan Hanya di Skema TEST

  • Kesalahan: Lupa menguji di skema PROD.
  • Dampak: Kode yang bergantung pada macro #if TEST atau CZPreBuildMacro.cz_buildTest() mungkin berjalan mulus di staging, namun ketika dicompile untuk App Store Release (PROD), blok kode tersebut diabaikan compiler sehingga memicu nil pointer atau alur yang terputus.
  • Solusi: Selalu jalankan uji verifikasi minimal satu kali pada skema PROD-TEST atau PROD sebelum merge PR.

2. Mengubah Sifat Singleton Menjadi Local Instance

  • Kesalahan: Menginstansiasi FlutterEngineManager() baru di dalam sebuah ViewController alih-alih menggunakan FlutterEngineManager.shared.
  • Dampak: Membengkakkan konsumsi RAM hingga 80-120 MB ekstra per engine dan merusak sinkronisasi event channel Flutter.

  3. Sebutkan 3 dampak berbahaya jika kunci enkripsi sesi staticKey di IDLoginCodeModel.swift diubah!
  4. Sebutkan 4 build scheme yang wajib diverifikasi sebelum mengajukan Pull Request!

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Keterikatan Kuat Antar Sub-Modul & Kurangnya Inversi Dependensi

Implementasi komponen sering mengasumsikan keberadaan lingkungan runtime tertentu tanpa kontrak antarmuka yang didefinisikan secara tegas.

⚠️ Smells 2: Risiko Regresi & Minimnya Kontrak Pengujian Terisolasi

Perubahan pada satu service atau helper berpotensi merusak fungsionalitas di modul lain karena tingginya kohesi tersembunyi antar file.

🚀 Blueprint Refactoring Standar Industri: Pola Service Locator & Interface Segregation (SOLID)

Menerapkan prinsip Interface Segregation (ISP) dan Dependency Injection agar setiap service hanya mengekspos metode yang relevan bagi kliennya.

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol SessionProvider: AnyObject {
    var currentToken: String? { get }
    var isAuthenticated: Bool { get }
}

public final class AppSessionManager: SessionProvider {
    public static let shared = AppSessionManager()
    public var currentToken: String?
    public var isAuthenticated: Bool { currentToken != nil }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
