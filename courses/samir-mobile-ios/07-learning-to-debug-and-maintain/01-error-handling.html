01 — Error Handling

Hierarki & Pola Penanganan Kesalahan

📚 Modul: 01-error-handling 🎯 Scope: SAMIR Mobile (iOS Native UIKit & FChannel) ⏱️ Estimasi: 20 Menit 🏷️ Git Branch: learn/iOS-Arch

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumen ini menjelaskan strategi penanganan kesalahan (error handling) bertingkat di SAMIR iOS: mulai dari error transport jaringan, status HTTP, kode error bisnis backend (200, 10006, dll.), toleransi parsing model, hingga penyajian umpan balik visual (error state presentation) kepada pengguna dalam Bahasa Indonesia.

Status Verifikasi: [Verified] (diverifikasi langsung dari IDNetworkRequest.swift, NSError+CZExtension.swift, dan IDBaseViewController.swift).

🎯 A. Learning Objective

Setelah mempelajari dokumen ini, pembaca akan mampu:

  1. Membedakan 5 tingkatan hierarki error di SAMIR iOS.
  2. Memahami bagaimana NSError.cz_isConnectionError() mendeteksi kendala konektivitas fisik dan memetakan pesan ramah pengguna.
  3. Menjelaskan penanganan kesalahan pada level bisnis (Business Error vs Transport Error).
  4. Mengetahui kapan harus menggunakan Toast, Dialog Modal, atau Empty State View saat terjadi error.

📋 B. Prerequisites

  • Sudah membaca 02-networking-and-api-flow.md.
  • Mengetahui konsep error domain dan status code pada NSError iOS.

💡 C. Simple Explanation (Analogi Petugas Loket dan Kendala Paspor)

Bayangkan Anda mengajukan visa di kantor kedutaan:

  1. Mati Lampu / Telepon Putus (Layer 1: Transport Error): Anda tidak bisa berbicara dengan petugas karena sambungan putus. Solusinya: Tunggu listrik menyala (Periksa Koneksi Internet).
  2. Loket Tutup (Layer 2: HTTP 500 / 404): Server sedang dalam perbaikan (Maintenance).
  3. Paspor Kadaluwarsa (Layer 3: Business Code 10006): Petugas menolak berkas karena masa berlaku identitas habis. Anda disuruh memperpanjang paspor terlebih dahulu (Re-Login).
  4. Foto Paspor Miring (Layer 3: Business Code Khusus): Petugas memberitahu spesifik apa yang salah: "Foto KTP buram, silakan ambil ulang."
  5. Papan Peringatan (Layer 5: UI Presentation):
    • Kesalahan kecil disampaikan lisan (Toast pop-up).
    • Kesalahan fatal menghentikan antrean (Dialog Modal Peringatan).
    • Seluruh sistem offline menampilkan papan tanda tutup (Empty View).

1. Layer 1: Error Transportasi Jaringan

Path: 🦊 ios/IDSamirLoan/Application/CZSwiftUtils/Classes/CZExtension/NSError+CZExtension.swift learn/iOS-Arch ↗

Aplikasi memeriksa kode domain NSURLErrorDomain:

extension NSError {
    public func cz_isConnectionError() -> Bool {
        switch self.code {
        case NSURLErrorNotConnectedToInternet,
             NSURLErrorNetworkConnectionLost,
             NSURLErrorTimedOut,
             NSURLErrorCannotConnectToHost:
            return true
        default:
            return false
        }
    }
    
    public var cz_errorMessage: String {
        if self.cz_isConnectionError() {
            return "Tampaknya ada masalah dengan jaringan, periksa pengaturan koneksi Anda."
        }
        if let customMsg = self.userInfo[NSLocalizedDescriptionKey] as? String, !customMsg.isEmpty {
            return customMsg
        }
        return "Terjadi kendala pada sistem, silakan coba lagi."
    }
}

2. Layer 2: Status HTTP Transport

Alamofire mengevaluasi kode HTTP server:

  • Jika server mengembalikan 502 Bad Gateway atau 500 Internal Server Error, request gagal di level Alamofire dan langsung dilempar ke closure failure(req) tanpa mencoba mem-parse JSON.

3. Layer 3: Envelope Status Kode Bisnis

Path: 🦊 ios/IDSamirLoan/Application/SamirNetworkModule/Classes/Common/IDNetworkRequest.swift learn/iOS-Arch ↗

Response JSON dipetakan:

private func p_handleSuccessRequest() {
    guard let responseDict = self.responseObject as? [String: Any],
          let code = responseDict["code"] as? String else {
        self.p_handleFailure(NSError.cz_errorWithDescription("Format respon tidak valid"))
        return
    }
    
    if code == IDNetworkStatusCode.success { // "200"
        self.responseObject = responseDict["result"]
        self.successCompletionBlock?(self)
    } else if code == IDNetworkStatusCode.reLogin { // "10006"
        self.p_handleReLoginError()
    } else {
        let msg = responseDict["msg"] as? String ?? "Operasi gagal"
        let error = NSError(domain: "IDBusinessError", code: Int(code) ?? -1, userInfo: [NSLocalizedDescriptionKey: msg])
        self.p_handleFailure(error)
    }
}

4. Layer 4: Toleransi Parsing Model (KakaJSON)

Jika field tertentu hilang dari JSON server (misal: backend lupa mengirim field termDays), KakaJSON tidak memicu exception fatal. Model tetap diinisialisasi dengan nilai default (misal: termDays = 0), sehingga aplikasi tetap dapat berjalan secara graceful.

5. Layer 5: Strategi Penyajian Error di UI (Error Presentation)

Presenter dan ViewController memilih cara penyajian berdasarkan keparahan error:

  1. Umpan Balik Cepat (Toast):
    • Digunakan untuk validasi form atau kegagalan minor (misal: "Nomor ponsel tidak boleh kurang dari 10 digit").
    • Pemanggilan: self.view.showToast(withMessage: errorMsg).
  2. State Layar Kosong (Empty View):
    • Digunakan ketika request daftar (seperti riwayat pinjaman atau daftar kupon) gagal akibat koneksi internet mati.
    • Menggunakan IDEmptyView dengan callback tombol coba lagi: 
     id_clickEmptyBlock = { [weak self] in
         self?.presenter.fetchData()
     }
  1. Peringatan Pemblokiran (Modal Alert / Pop-up):
    • Digunakan untuk penolakan pengajuan kredit, limit pinjaman kadaluwarsa, atau pembaruan aplikasi wajib.
    • Menggunakan IDNPopupController yang mewajibkan pengguna menekan tombol aksi untuk menutupnya.

🪜 E. Step-by-Step Walkthrough: Alur Penanganan Error Koneksi Mati

  1. User menekan tombol "Refresh Tagihan".
  2. iPhone sedang dalam mode pesawat (Airplane Mode).
  3. Alamofire mengembalikan error NSURLErrorNotConnectedToInternet (-1009).
  4. IDNetworkRequest membungkus error tersebut ke dalam req.error.
  5. Service memanggil blok failure(req).
  6. Presenter mengekstrak pesan: req.error.cz_errorMessage.
  7. Karena fungsi cz_isConnectionError() mengembalikan true, pesan otomatis disesuaikan menjadi:

"Tampaknya ada masalah dengan jaringan, periksa pengaturan koneksi Anda."

  1. Presenter memerintahkan ViewController: view.showNetworkEmptyView().
  2. Layar menampilkan ilustrasi kabel terputus dengan tombol "Coba Lagi".

⚖️ F. Why It Matters: Standarisasi Pesan Error Pengguna

Senior engineer harus memastikan bahwa detail teknis internal tidak pernah bocor ke pengguna akhir:

  • Jangan pernah menampilkan teks mentah seperti: "JSONSerializationException: Unexpected token at row 4" atau "Alamofire.AFError 4".
  • Seluruh pesan error wajib dipetakan ke bahasa yang dapat dipahami nasabah awam, memberikan instruksi jelas tentang apa yang harus dilakukan (contoh: "Periksa sinyal ponsel Anda" atau "Pastikan ruangan cukup terang saat mengambil foto").

🔬 G. Practical Example: Guard Nil pada Callback Presenter

// Pola penanganan error standar di Presenter
service.fetchLoanDetail(bizId: bizId) { [weak self] model in
    guard let self = self else { return }
    self.view?.hideLoading()
    guard let model = model else {
        self.view?.showEmptyState(message: "Data pinjaman tidak ditemukan")
        return
    }
    self.view?.renderLoanDetail(model)
} failure: { [weak self] errorMsg in
    guard let self = self else { return }
    self.view?.hideLoading()
    self.view?.showToast(withMessage: errorMsg)
}

⚠️ H. Common Mistakes & Debugging

  • Crash Karena Force-Unwrap pada req.error!:
    • Di blok failure, jangan berasumsi req.error pasti memiliki nilai; selalu gunakan optional binding req.error?.cz_errorMessage ?? "Kendala sistem".
  • Menelan Error Tanpa Memberi Tahu UI:
    • Menulis blok failure: { req in } kosong (silent failure) membuat loading indicator terus berputar selamanya di layar (infinite spinner). Selalu sembunyikan loading HUD di blok failure!

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Keterikatan Kuat Antar Sub-Modul & Kurangnya Inversi Dependensi

Implementasi komponen sering mengasumsikan keberadaan lingkungan runtime tertentu tanpa kontrak antarmuka yang didefinisikan secara tegas.

⚠️ Smells 2: Risiko Regresi & Minimnya Kontrak Pengujian Terisolasi

Perubahan pada satu service atau helper berpotensi merusak fungsionalitas di modul lain karena tingginya kohesi tersembunyi antar file.

🚀 Blueprint Refactoring Standar Industri: Pola Service Locator & Interface Segregation (SOLID)

Menerapkan prinsip Interface Segregation (ISP) dan Dependency Injection agar setiap service hanya mengekspos metode yang relevan bagi kliennya.

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol SessionProvider: AnyObject {
    var currentToken: String? { get }
    var isAuthenticated: Bool { get }
}

public final class AppSessionManager: SessionProvider {
    public static let shared = AppSessionManager()
    public var currentToken: String?
    public var isAuthenticated: Bool { currentToken != nil }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
