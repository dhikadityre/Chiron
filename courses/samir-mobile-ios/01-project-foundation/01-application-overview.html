Core Knowledge

Dokumentasi ini memberikan gambaran komprehensif mengenai profil aplikasi finansial SAMIR iOS (IDSamirLoan), model bisnis pinjaman Peer-to-Peer (P2P) Lending yang dijalankan, target pengguna di Indonesia, serta batasan-batasan teknis platform.

Status Verifikasi: [Verified] (diverifikasi langsung dari konfigurasi IDSamirLoan-Info.plist, entitlements, dan source code aktif).

🎯 A. Learning Objective

Setelah menyelesaikan dokumen ini, pembaca akan mampu:

  1. Menjelaskan domain bisnis SAMIR sebagai platform Pinjaman Daring / Fintech P2P Lending berizin di Indonesia.
  2. Menyebutkan identitas teknis aplikasi (Bundle ID, App Store ID, skema URL, target OS minimal).
  3. Memahami persona pengguna, izin perangkat (device permissions) yang diminta, serta kepatuhan regulasi finansial.

📋 B. Prerequisites

Tidak ada prasyarat khusus untuk dokumen ini. Ini adalah pintu gerbang pengenalan sebelum mendalami arsitektur dan kode.

💡 C. Simple Explanation (Analogi & Konsep Sederhana)

Bayangkan aplikasi perbankan mikro di mana nasabah dapat meminjam dana darurat tanpa harus datang ke kantor cabang fisik:

  1. Nasabah mengunduh aplikasi SAMIR dari App Store.
  2. Nasabah mendaftarkan nomor ponsel dan memverifikasi identitas menggunakan e-KTP dan foto wajah (Liveness Detection).
  3. Sistem secara otomatis menganalisis skor kredit dan memberikan limit pinjaman (Plafon Kredit).
  4. Nasabah memilih nominal dan tenor, lalu dana dicairkan ke rekening bank nasabah.
  5. Pada tanggal jatuh tempo, nasabah membayar kembali melalui Virtual Account atau gerai retail.

Karena ini adalah aplikasi finansial, aspek keamanan, integritas data perangkat, anti-fraud, dan tanda tangan digital menjadi pilar paling vital di seluruh arsitektur sistem.

🪜 E. Step-by-Step Walkthrough (Alur Pemahaman Aplikasi)

  1. Unduh & Pasang: Aplikasi diinstal di iPhone (minimal iOS 14.0).
  2. Boot Awal: Aplikasi memeriksa ketersediaan konfigurasi environment (AppEnv.swift).
  3. Pengenalan UI:
  • Jika pengguna baru, splash countdown ditampilkan selama 3 detik (IDLaunchViewController).
  • Aplikasi kemudian memuat kontainer utama berupa 3 Tab:
  • Tab 0 (Beranda / Home): Menampilkan limit kuota, kalkulator pinjaman, banner promo, dan tombol ajukan. (Native Swift IDHomeViewController).
  • Tab 1 (Tagihan / Repay): Menampilkan status pinjaman aktif, jadwal angsuran, dan kode pembayaran. (Hybrid Flutter repay_home_page.dart yang di-host oleh IDRepayViewController).
  • Tab 2 (Saya / Mine): Profil nasabah, riwayat pesanan, pengaturan privasi, kontak CS, dan pusat bantuan. (Hybrid Flutter mine_home_page.dart yang di-host oleh IDMineViewController).

⚖️ F. Why It Matters (Trade-Offs & Implikasi Teknis)

  • Mengapa Portrait & Light Mode Only?

Aplikasi finansial dan verifikasi KTP/wajah sangat sensitif terhadap rotasi kamera dan konsistensi kontras warna saat proses OCR. Membatasi orientasi ke portrait dan light-mode mengeliminasi ratusan edge-case bug pada layout kamera dan form tabel.

  • Mengapa Minimal iOS 14.0?

Mulai iOS 14.0, Apple mewajibkan framework AppTrackingTransparency (ATTrackingManager). Selain itu, Flutter Engine terbaru dan pustaka kriptografi modern (CryptoKit) bekerja optimal di iOS 14+.

🔬 G. Practical Example (Skenario Penggunaan Nyata)

Ketika seorang user membuka aplikasi di simulator atau perangkat fisik, kode pertama yang memeriksa identitas aplikasi adalah CZEnvironmentManager. Nilai appleId (6475002606) dan apiBaseUrl (https://domain-loansapp-test.samir.co.id/ di mode TEST) langsung diinjeksikan ke dalam singleton jaringan IDNetworkManager.

⚠️ H. Common Mistakes & Debugging

  • Kesalahan Umum: Mencoba menjalankan aplikasi dengan simulator ber-iOS 13.
  • Efek: Xcode akan menampilkan error build / deploy The run destination is not valid for running the scheme.
  • Solusi: Pastikan simulator atau iPhone fisik menggunakan iOS 14.0 atau lebih baru.
  • Kesalahan Dark Mode: Berasumsi aplikasi mendukung Dark Mode otomatis.
  • Efek: Mengubah warna label menjadi dinamis dapat merusak keterbacaan karena aset background di-hardcode ke palet terang.

🏛️ Bagian 2: Architecture Lab, SOLID Audit & Retention Quizzes

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Keterikatan Kuat Antar Sub-Modul & Kurangnya Inversi Dependensi

Implementasi komponen sering mengasumsikan keberadaan lingkungan runtime tertentu tanpa kontrak antarmuka yang didefinisikan secara tegas.

⚠️ Smells 2: Risiko Regresi & Minimnya Kontrak Pengujian Terisolasi

Perubahan pada satu service atau helper berpotensi merusak fungsionalitas di modul lain karena tingginya kohesi tersembunyi antar file.

🚀 Blueprint Refactoring Standar Industri: Pola Service Locator & Interface Segregation (SOLID)

Menerapkan prinsip Interface Segregation (ISP) dan Dependency Injection agar setiap service hanya mengekspos metode yang relevan bagi kliennya.

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol SessionProvider: AnyObject {
    var currentToken: String? { get }
    var isAuthenticated: Bool { get }
}

public final class AppSessionManager: SessionProvider {
    public static let shared = AppSessionManager()
    public var currentToken: String?
    public var isAuthenticated: Bool { currentToken != nil }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
