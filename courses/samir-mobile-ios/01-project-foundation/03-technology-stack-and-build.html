Core Knowledge

Dokumen ini mendokumentasikan seluruh tumpukan teknologi (technology stack), manajemen dependensi pihak ketiga, skema build Xcode, skrip pra-kompilasi, dan arsitektur pipeline build SAMIR iOS.

🎯 A. Learning Objective

Setelah mempelajari dokumen ini, pembaca akan mampu:

  1. Mengidentifikasi seluruh pustaka open-source, vendor framework closed-source, dan SDK analitik yang digunakan dalam aplikasi.
  2. Memahami 4 Xcode Shared Schemes (TEST, PROD-TEST, PROD, IDSamirEnvironment) dan perbedaan perilakunya saat kompilasi.
  3. Memahami 4 fase build script otomatis di Xcode: generasi environment_preprocess.h, kompilasi Flutter, generasi aset R.swift, dan arsitektur thinning LibNetSignGenerator.framework.

📋 B. Prerequisites

  • Sudah membaca 01-application-overview.md dan 02-repository-structure.md.
  • Mengetahui cara kerja CocoaPods (pod install) dan pengaturan Target di Xcode.

💡 C. Simple Explanation (Analogi Pabrik Perakitan)

Bayangkan aplikasi SAMIR seperti mobil yang dirakit di pabrik:

  • Komponen Standar: Baut, mur, dan ban diambil dari pasar umum (pustaka open-source seperti SnapKit, Alamofire, Kingfisher).
  • Komponen Khusus / Berlisensi: Mesin keamanan anti-maling dan modul sensor wajah dipasok oleh vendor khusus dengan teknologi tertutup (TrustDecision, Advance AI, LibNetSignGenerator).
  • Lini Perakitan (Xcode Scheme):
  • Lini Uji Coba (TEST): Mobil dipasangi alat diagnosis tambahan (tombol DebugUI), mesin tidak dibatasi, dan speedometer menampilkan angka debug.
  • Lini Produksi (PROD): Alat diagnosis dicopot, nama pabrik dirapikan, performa dioptimalkan secara maksimal, dan siap dijual ke publik (App Store).

3. Build Phases & Custom Shell Scripts

Proyek Xcode IDSamirLoan mengeksekusi 4 skrip otomatis saat proses kompilasi berlangsung:

Fase 1: Pra-proses Environment (app_environment.sh)
  • Lokasi file: 🦊 ios/IDSamirLoan/Application/Configuration/Environment/app_environment.sh learn/iOS-Arch ↗
  • Fungsi: Menghitung jumlah commit git (git rev-list HEAD | wc -l), mengambil tanggal saat ini, dan menghasilkan file header 🦊 ios/IDSamirLoan/Application/environment_preprocess.h learn/iOS-Arch ↗.
  • Hasil: Jika mode TEST, nama aplikasi diubah dinamis menjadi Samir <tanggal_hari_ini> sehingga tester dapat membedakan build hari ini dengan build kemarin.
Fase 2: Flutter Tools Build (xcode_backend.sh)
  • Definisi di PBX: project.pbxproj:L1104
  • Fungsi: Mengekspor environment Flutter dari ../flutter/.ios/Flutter/flutter_export_environment.sh dan mengompilasi kode Dart ke dalam biner framework native iOS.
Fase 3: R.swift Generation
  • Definisi di PBX: project.pbxproj:L1141
  • Perintah: "$PODS_ROOT/R.swift/rswift" generate "$SRCROOT/IDSamirLoan/R.generated.swift"
  • Fungsi: Membaca folder Assets.xcassets dan memperbarui file R.generated.swift agar semua gambar dapat diakses secara type-safe (R.image.icon_name()).
Fase 4: Arsitektur Thinning LibNetSignGenerator (lipo -extract)
  • Definisi di PBX: project.pbxproj:L1153
  • Fungsi: Memeriksa framework vendor LibNetSignGenerator.framework di dalam build directory (TARGET_BUILD_DIR), mengekstrak hanya arsitektur yang cocok dengan target kompilasi ($ARCHS), dan menggabungkan kembali (lipo) agar ukuran biner tetap ramping dan tidak ditolak oleh App Store Connect karena arsitektur yang tidak digunakan.
  • Kode Skrip PBX Aktual:
  APP_PATH="${TARGET_BUILD_DIR}/${WRAPPER_NAME}"

  # Cari LibNetSignGenerator.framework di dalam bundle aplikasi
  find "$APP_PATH" -name 'LibNetSignGenerator.framework' -type d | while read -r FRAMEWORK
  do
      FRAMEWORK_EXECUTABLE_NAME=$(defaults read "$FRAMEWORK/Info.plist" CFBundleExecutable)
      FRAMEWORK_EXECUTABLE_PATH="$FRAMEWORK/$FRAMEWORK_EXECUTABLE_NAME"
      echo "Executable is $FRAMEWORK_EXECUTABLE_PATH"
      
      EXTRACTED_ARCHS=()
      for ARCH in $ARCHS
      do
          echo "Extracting $ARCH from $FRAMEWORK_EXECUTABLE_NAME"
          lipo -extract "$ARCH" "$FRAMEWORK_EXECUTABLE_PATH" -o "$FRAMEWORK_EXECUTABLE_PATH-$ARCH"
          EXTRACTED_ARCHS+=("$FRAMEWORK_EXECUTABLE_PATH-$ARCH")
      done
      
      echo "Merging extracted architectures: ${ARCHS}"
      lipo -o "$FRAMEWORK_EXECUTABLE_PATH-merged" -create "${EXTRACTED_ARCHS[@]}"
      rm "${EXTRACTED_ARCHS[@]}"
      
      echo "Replacing original executable with thinned version"
      rm "$FRAMEWORK_EXECUTABLE_PATH"
      mv "$FRAMEWORK_EXECUTABLE_PATH-merged" "$FRAMEWORK_EXECUTABLE_PATH"
  done
  • Alur Eksekusi lipo -extract Langkah-demi-Langkah:
  1. Identifikasi Binary: Membaca nama biner framework dari Info.plist menggunakan defaults read ... CFBundleExecutable.
  2. Isolasi Arsitektur Target (lipo -extract): Variabel $ARCHS dari Xcode (misal: arm64) diiterasi. Perintah lipo -extract "$ARCH" ... mengambil hanya slice arsitektur tersebut ke file sementara.
  3. Penyatuan Kembali (lipo -create): Menggabungkan kembali irisan yang dibutuhkan (-create) menjadi satu binary biner bersih (-merged).
  4. *Pembersihan (Thinning Replacement)*: Menghapus binary fat asli yang berukuran besar dan menggantinya dengan binary hasil thinning. Hal ini mencegah App Store menolak build karena arsitektur simulator (x86_64) yang tertinggal di dalam binary dinamis.

4. Vendor Framework Khusus: LibNetSignGenerator.framework

  • Fungsi: Pustaka biner dinamis closed-source (C++/ObjC) yang bertugas menghitung tanda tangan enkripsi (sign) pada setiap request jaringan HTTP (normal request, upload gambar, hingga config request). Tanda tangan ini menggunakan formula hashing yang dikombinasikan dengan staticKey sesi user untuk melindungi API dari request tampering, replay attacks, dan sniffing.
  • Header Publik:
  • NetworkRequestSignWrapper.h: Menyediakan ns_initialize(appName:), ns_encryptForNormal(requestJsonString:staticKey:), ns_encryptWithImage(...), dan ns_checkSign(...).
  • NetworkRequestEventSignWrapper.h: Menyediakan nsEvent_encrypt(...) untuk payload telemetri.
  • Cara Setup & Import di Proyek:
  1. Penyimpanan Berkas: File LibNetSignGenerator.framework diletakkan di Application/SamirNetworkModule/Frameworks/.
  2. Xcode Build Settings:
  • FRAMEWORK_SEARCH_PATHS diarahkan ke "$(PROJECT_DIR)/Application/SamirNetworkModule/Frameworks".
  • Ditambahkan ke fase "Link Binary With Libraries" dan "Embed Frameworks" (dengan opsi CodeSignOnCopy).
  1. Import di Swift / ObjC:
  • Karena framework memiliki Modules/module.modulemap, kode Swift cukup menuliskan import LibNetSignGenerator.
  • Untuk modul ObjC / Bridging Header, disertakan baris #import <LibNetSignGenerator/LibNetSignGenerator.h>.

5. Konfigurasi Khusus Podfile (BUILD_LIBRARY_FOR_DISTRIBUTION & Xcode 16 Synchronized Groups)

A. Mengapa Kingfisher Disetel BUILD_LIBRARY_FOR_DISTRIBUTION = 'NO'?

Di baris 91-95 🦊 ios/Podfile learn/iOS-Arch ↗:

if target.name == 'Kingfisher'
  target.build_configurations.each do |config|
    config.build_settings['BUILD_LIBRARY_FOR_DISTRIBUTION'] = 'NO'
  end
end

Tujuan dan Alasan:

  1. BUILD_LIBRARY_FOR_DISTRIBUTION = YES menginstruksikan compiler Swift untuk menghasilkan file interface publik .swiftinterface demi mendukung Swift Module Stability (biner yang dapat digunakan lintas versi compiler Swift).
  2. Namun, saat compiler mencoba menghasilkan .swiftinterface untuk Kingfisher versi 7/8, Swift compiler mengalami kegagalan kompilasi karena inferensi tipe generik pada pipeline pemrosesan gambar Kingfisher serta adanya atribut @_implementationOnly atau default arguments yang melanggar aturan stabilitas modul Swift.
  3. Karena Kingfisher dikompilasi langsung dari kode sumber di dalam workspace aplikasi kita (bukan didistribusikan sebagai biner tertutup untuk developer pihak ketiga), stabilitas modul tidak diperlukan.
  4. Menyetelnya ke 'NO' mematikan pembuatan .swiftinterface, menyelesaikan error kompilasi Swift compiler secara tuntas, dan mempercepat proses build secara signifikan.
B. Pengaturan Xcode 16 Synchronized Groups: Manual vs Otomatis

Di Xcode 16, Apple memperkenalkan format baru Synchronized Groups (PBXFileSystemSynchronizedRootGroup dengan objectVersion 73 di project.pbxproj):

  • Perbedaan Konsep:
  • Legacy Groups (PBXGroup): Virtual folder di Xcode. Menambah/menghapus file di disk macOS tidak otomatis mengubah struktur project di Xcode tanpa diedit di file .pbxproj.
  • Synchronized Groups: Terikat 1:1 langsung ke direktori filesystem. Setiap file yang dibuat di folder Finder langsung otomatis menjadi anggota target kompilasi Xcode.
  • Manual atau Otomatis?:
  • Untuk proyek lama yang di-upgrade, Xcode TIDAK mengubahnya secara otomatis menjadi Synchronized Groups. Struktur grup dipertahankan manual sebagai PBXGroup kecuali jika developer sengaja memilih Right Click -> "Convert to Synchronized Group...".
  • Namun, saat project dibuka di Xcode 16, Xcode secara otomatis menaikkan format objectVersion project menjadi 73 (Xcode 16.0 compatibility).
  • Dampak pada CocoaPods & Monkey Patch di Podfile:
  • Library xcodeproj ruby bawaan CocoaPods versi lama akan crash dengan error: [Xcodeproj] Unknown object version '73' saat menjalankan pod install.
  • Oleh karena itu, di baris 2-6 Podfile SAMIR disematkan patch manual:
    require 'xcodeproj'
    compatibility_versions = Xcodeproj::Constants::COMPATIBILITY_VERSION_BY_OBJECT_VERSION.dup
    compatibility_versions[73] ||= 'Xcode 16.0'
    Xcodeproj::Constants.send(:remove_const, :COMPATIBILITY_VERSION_BY_OBJECT_VERSION)
    Xcodeproj::Constants.const_set(:COMPATIBILITY_VERSION_BY_OBJECT_VERSION, compatibility_versions.freeze)
  • Rekomendasi: Pertahankan pengaturan grup sebagai Manual (Virtual Group) untuk saat ini guna mencegah konflik mapping build phase file CocoaPods.

⚖️ F. Why It Matters (Trade-Offs & Catatan Arsitektur)

  • Mengapa Podfile.lock di-ignore di Git?

Di file .gitignore, Podfile.lock tidak di-commit.

Trade-off: Ini dapat menimbulkan variasi versi minor antarmesin developer jika tidak berhati-hati saat menjalankan pod update. Pastikan hanya menjalankan pod install dan versi dependensi penting telah di-pin secara eksplisit (seperti SnapKit 5.6.0, Kingfisher 8.6.2).

  • Keberadaan RxSwift yang Terisolasi:

RxSwift (6.9.0) hanya digunakan pada modul konfirmasi pinjaman (LoanConfirmModule). Modul lain menggunakan callback Presenter biasa. Ini menimbulkan overhead biner, namun memigrasikannya membutuhkan refactoring yang sangat hati-hati karena alur konfirmasi pinjaman adalah alur konversi bisnis utama.

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Keterikatan Kuat Antar Sub-Modul & Kurangnya Inversi Dependensi

Implementasi komponen sering mengasumsikan keberadaan lingkungan runtime tertentu tanpa kontrak antarmuka yang didefinisikan secara tegas.

⚠️ Smells 2: Risiko Regresi & Minimnya Kontrak Pengujian Terisolasi

Perubahan pada satu service atau helper berpotensi merusak fungsionalitas di modul lain karena tingginya kohesi tersembunyi antar file.

🚀 Blueprint Refactoring Standar Industri: Pola Service Locator & Interface Segregation (SOLID)

Menerapkan prinsip Interface Segregation (ISP) dan Dependency Injection agar setiap service hanya mengekspos metode yang relevan bagi kliennya.

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol SessionProvider: AnyObject {
    var currentToken: String? { get }
    var isAuthenticated: Bool { get }
}

public final class AppSessionManager: SessionProvider {
    public static let shared = AppSessionManager()
    public var currentToken: String?
    public var isAuthenticated: Bool { currentToken != nil }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
