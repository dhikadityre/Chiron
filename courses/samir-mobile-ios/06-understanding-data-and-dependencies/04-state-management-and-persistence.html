04 — State Management & Persistence

Pengelolaan State & Penyimpanan Data

📚 Modul: 04-state-management-and-persistence 🎯 Scope: SAMIR Mobile (iOS Native UIKit & FChannel) ⏱️ Estimasi: 20 Menit 🏷️ Git Branch: learn/iOS-Arch

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumen ini menjelaskan hierarki pengelolaan state dan persistensi data di SAMIR iOS: pembagian antara penyimpanan terenkripsi AES-GCM di Application Support, penyimpanan kredensial perangkat di iOS Keychain, penyimpanan bendera non-sensitif di UserDefaults, cache memori (in-memory state), hingga sinkronisasi data sesi ke runtime Flutter.

Status Verifikasi: [Verified] (diverifikasi langsung dari IDLoginManager.swift, CZEnvironmentManager.swift, dan FlutterNativeChannel+method.swift).

🎯 A. Learning Objective

Setelah mempelajari dokumen ini, pembaca akan mampu:

  1. Memetakan 4 lapisan persistensi data di SAMIR iOS berdasarkan tingkat keamanan dan kebutuhan akses.
  2. Memahami alur kerja enkripsi dan dekripsi model sesi menggunakan CryptoKit.AES.GCM.
  3. Mengidentifikasi kunci apa saja yang aman disimpan di UserDefaults dan data apa saja yang dilarang keras disimpan di sana.
  4. Menjelaskan bagaimana method channel getRootPageData membagikan state sesi native ke widget Flutter.

📋 B. Prerequisites

  • Sudah membaca 02-authentication-and-session-flow.md.
  • Mengetahui konsep iOS Keychain Services, Sandbox Application Directory, dan thread safety pada caching.

💡 C. Simple Explanation (Analogi Tingkat Keamanan Brankas Bank)

Sebuah kantor perbankan menyimpan dokumen dengan 4 tingkat brankas:

  1. Papan Pengumuman Lobi (UserDefaults): Siapa saja boleh melihat (papan pengumuman apakah ada iklan hari ini, catatan nomor loket antrean yang tertunda).
  2. Lemari Arsip Kerja Harian (In-Memory Cache RAM): Dokumen kerja yang sedang dipegang staf saat melayani nasabah. Cepat diakses, tetapi hilang saat kantor tutup (aplikasi di-kill).
  3. Brankas Rahasia Berlian (Application Support + Enkripsi AES-GCM): Tempat menyimpan identitas lengkap nasabah dan kunci transaksi (staticKey). Dikunci rapat dengan algoritma enkripsi modern.
  4. Bunker Bawah Tanah Tahan Gempa (iOS Keychain): Tempat menyimpan nomor registrasi brankas perangkat (UUID, ID Instalasi). Data di bunker ini tetap utuh meskipun aplikasi dihapus dan diinstal ulang!

1. Lapisan 1: Penyimpanan Terenkripsi (Application Support Directory)

Path: 🦊 ios/IDSamirLoan/Application/SamirLoginModule/Classes/IDPresenter/IDLoginManager.swift learn/iOS-Arch ↗

  • File: idn_userFile.plist di dalam FileManager.default.urls(for: .applicationSupportDirectory, in: .userDomainMask).
  • Data yang Disimpan: Objek IDLoginCodeModel (berisi mid, userNo, staticKey, nomor HP).
  • Mekanisme Enkripsi:
  1. Data di-archive via NSKeyedArchiver.
  2. Kunci enkripsi diturunkan via SHA-256 dari bundle id:

"IDSamirLoan.LoginUser.AES256.v1.\(Bundle.cz.appBundleIdentifier)".

  1. Dienkripsi menggunakan CryptoKit.AES.GCM.seal.
  2. Header string ID_LOGIN_USER_AES256_V1\n disematkan di awal data binary.
  • Tingkat Keamanan: Sangat Tinggi. Jika file diekstrak dari perangkat yang di-jailbreak, penyerang hanya melihat byte teracak (ciphertext) tanpa bisa membaca nomor HP atau staticKey.

2. Lapisan 2: iOS Keychain Services (CZKeychainManager)

Path: 🦊 ios/IDSamirLoan/Application/CZSwiftAntiFraudLib/Classes/CZCommon/CZKeychainManager.swift learn/iOS-Arch ↗

  • Peran: Menyimpan pengenal unik perangkat yang tidak boleh berubah meskipun aplikasi dihapus dan dipasang kembali oleh pengguna (device fingerprinting persistence).
  • Service Name: Bundle Identifier aplikasi (com.samir.loan).
  • Data yang Disimpan:
  • uuid: Pengenal hardware unik untuk mitigasi penipuan akun ganda (multi-accounting fraud).
  • secure.installation_id: ID unik instalasi Firebase.
  • secure.liveness_token: Kredensial lisensi SDK deteksi wajah.

3. Lapisan 3: Pengaturan Non-Sensitif (UserDefaults)

Digunakan hanya untuk penanda status UI dan transisi navigasi:

Kunci UserDefaultsTipe DataTujuan Teknis
APP_Start_HideString ("1" / "0")Menentukan apakah splash screen countdown dilewati saat boot berikutnya.
Samir_DeepLink_StrStringMenyimpan URL deep link yang tiba saat cold start sebelum UI siap.
Samir_DeepLink_TypeString ("1" / "2")Tipe deep link yang sedang menunggu eksekusi.

[!CAUTION] Audit Keamanan Penting: Pada versi-versi awal aplikasi, idn_mid dan idn_mobile disimpan dalam bentuk plaintext di UserDefaults. Pada implementasi modern saat ini, kedua kunci tersebut secara eksplisit dihapus (UserDefaults.cz.remove(IDStorageKey.idn_mid)) dan dipindahkan ke brankas terenkripsi saveUserModel. Jangan pernah menyimpan data PII (Personally Identifiable Information) di UserDefaults!

4. Lapisan 4: Pengelolaan State di Memori (In-Memory RAM)

  • IDLoginManager.shared.userModel: Singleton instance yang di-cache di memori agar presenter tidak perlu melakukan operasi I/O dekripsi file disk pada setiap frame tampilan.
  • CZModuleManager.cachedServiceDict: Singleton cache untuk handler protokol layanan, dilindungi oleh antrean serial serviceCacheQueue untuk mencegah race condition multithreading.
  • CZMultiCache: Pustaka caching dua tingkat (Memory Cache berbasis NSCache dengan LRU eviction + Disk Cache terenkripsi).

// FlutterNativeChannel+method.swift:L34-41
func getRootPageData(result: @escaping FlutterResult) {
    let isLogin = IDServiceManager.loginService()?.isLogin() ?? false
    result([
        "isLogin": isLogin,
        "mobile": IDServiceManager.loginService()?.loginInfo()?.mobile ?? "",
        "showSocialMedia": IDServiceManager.mainService()?.getAppConfig()?.appSocialMedia == "1"
    ])
}

Metode ini memastikan Flutter tidak perlu mengimplementasikan sistem login atau penyimpanan kredensialnya sendiri; Native iOS tetap menjadi Single Source of Truth (SSOT) untuk seluruh state autentikasi pengguna!

⚖️ F. Why It Matters: Thread-Safety pada Caching Modul

Perhatikan baris 40–50 di 🦊 CZModuleManager.swift learn/iOS-Arch ↗:

private let serviceCacheQueue = DispatchQueue(label: "com.samir.CZModuleManager.serviceCache")

public func serviceForProtocol(_ serviceProtocolName: String) -> CZBaseServiceProtocol? {
    // Akses thread-safe menggunakan serial queue sync
    return serviceCacheQueue.sync {
        let service = cachedServiceDict[serviceProtocolName]
        if service == nil {
            let s = (object as! NSObject.Type).init() as? CZBaseServiceProtocol
            cachedServiceDict[serviceProtocolName] = s
            return s
        }
        return service
    }
}

Karena pemanggilan service seperti IDServiceManager.loginService() dapat terjadi bersamaan dari background network thread dan main UI thread, penggunaan serviceCacheQueue.sync mencegah terjadinya crash fatal akibat dictionary concurrent read-write mutation.

📌 G. Bedah Pustaka CZSwiftStorageLib: Penggunaan & Panduan Pembuatan di Proyek Baru

Path: 🦊 ios/IDSamirLoan/Application/CZSwiftStorageLib/ learn/iOS-Arch ↗

1. Struktur Internal & Digunakan di Mana Saja?

CZSwiftStorageLib adalah pustaka manajemen cache in-house yang mengimplementasikan arsitektur two-tier caching (Memory + Disk):

  • CZMemoryStorage<Value: Codable>: Cache RAM berbasis algoritma LRU (Least Recently Used) menggunakan struktur data doubly-linked list (CZLinkedNode) dan dictionary lookup O(1). Memiliki batas biaya (totalCostLimit) dan batas kuantitas (totalCountLimit).
  • CZDiskStorage<Value: Codable>: Penyimpanan disk berbasis file yang meng-encode model Codable ke dalam file terpisah dengan nama file berbasis hash SHA-256 dari key di folder Caches.
  • CZMultiCache<Value: Codable>: Lapisan fasad gabungan (CZCacheProtocol). Saat membaca data (object(forKey:)), ia mencari di memori (L1). Jika cache miss, ia membaca dari disk (L2) dan langsung mempromosikan nilainya kembali ke L1 cache memori.

Di Mana Saja Digunakan di SAMIR?

Pustaka ini dirancang sebagai pustaka cache umum (CZCache). Namun di lapisan bisnis SAMIR, persistensi model pengguna utama (IDLoginCodeModel) didelegasikan langsung ke enkripsi CryptoKit.AES.GCM di IDLoginManager, sedangkan flag preferensi disimpan via UserDefaults, dan kredensial hardware disimpan via CZKeychainManager.

2. Cara Membuat Pustaka Storage Serupa di Proyek Baru:

Jika Anda ingin membangun modul storage performa tinggi dari nol di proyek baru:

  1. Definisikan Kontrak Abstraksi (CacheProtocol):
   public protocol CacheProtocol {
       associatedtype Value: Codable
       func set(_ value: Value, forKey key: String)
       func get(forKey key: String) -> Value?
       func remove(forKey key: String)
       func removeAll()
   }
  1. Implementasikan Memory Cache (L1):

Gunakan NSCache<NSString, AnyObject> bawaan Apple (sudah thread-safe dan otomatis mengosongkan RAM saat memory warning), atau bangun custom Doubly-Linked List + Hash Map jika membutuhkan kontrol LRU yang ketat.

  1. Implementasikan Disk Cache (L2):

Gunakan FileManager untuk menulis data ke direktori Application Support atau Caches:

   let fileURL = cacheDirectory.appendingPathComponent(key.sha256())
   let data = try JSONEncoder().encode(value)
   try data.write(to: fileURL)
  1. Gabungkan Menjadi MultiTierCache:
   public class TwoLevelCache<T: Codable>: CacheProtocol {
       private let memoryCache: MemoryCache<T>
       private let diskCache: DiskCache<T>
       
       public func get(forKey key: String) -> T? {
           if let memValue = memoryCache.get(forKey: key) { return memValue }
           if let diskValue = diskCache.get(forKey: key) {
               memoryCache.set(diskValue, forKey: key) // Promosi ke RAM
               return diskValue
           }
           return nil
       }
   }

🔬 H. Practical Example: Mengambil Data Sesi yang Aman

Untuk membaca nomor HP pengguna yang sedang login di mana pun dalam kode native:

if let user = IDLoginManager.shared.getUserModel() {
    print("User Mobile: \(user.mobile ?? "")")
}

Method getUserModel() pertama-tama memeriksa cache RAM self.userModel. Jika nil (misal: baru boot), ia otomatis memanggil __decodeUserModel() untuk mendekripsi file disk idn_userFile.plist.

⚠️ I. Common Mistakes & Debugging

  • Menyimpan Kredensial Baru di UserDefaults:
  • Kesalahan: Menambahkan UserDefaults.standard.set(token, forKey: "user_auth_token").
  • Bahaya: Pelanggaran kepatuhan audit keamanan fintech. Semua token autentikasi wajib melalui saveUserModel.
  • Crash AES.GCM.open Karena Bundle ID Berubah:
  • Jika Anda mengubah PRODUCT_BUNDLE_IDENTIFIER di Xcode, kunci turunan SHA-256 akan berubah, sehingga data sesi lama tidak dapat didekripsi. Fungsi decryptUserModelDataIfNeeded menangani ini dengan memicu re-login alih-alih melempar unhandled crash.

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Keterikatan Kuat Antar Sub-Modul & Kurangnya Inversi Dependensi

Implementasi komponen sering mengasumsikan keberadaan lingkungan runtime tertentu tanpa kontrak antarmuka yang didefinisikan secara tegas.

⚠️ Smells 2: Risiko Regresi & Minimnya Kontrak Pengujian Terisolasi

Perubahan pada satu service atau helper berpotensi merusak fungsionalitas di modul lain karena tingginya kohesi tersembunyi antar file.

🚀 Blueprint Refactoring Standar Industri: Pola Service Locator & Interface Segregation (SOLID)

Menerapkan prinsip Interface Segregation (ISP) dan Dependency Injection agar setiap service hanya mengekspos metode yang relevan bagi kliennya.

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol SessionProvider: AnyObject {
    var currentToken: String? { get }
    var isAuthenticated: Bool { get }
}

public final class AppSessionManager: SessionProvider {
    public static let shared = AppSessionManager()
    public var currentToken: String?
    public var isAuthenticated: Bool { currentToken != nil }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
