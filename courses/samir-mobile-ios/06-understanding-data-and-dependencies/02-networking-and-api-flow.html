02 — Networking & API Flow

Pipeline Jaringan & Penandatanganan Request

📚 Modul: 02-networking-and-api-flow 🎯 Scope: SAMIR Mobile (iOS Native UIKit & FChannel) ⏱️ Estimasi: 20 Menit 🏷️ Git Branch: learn/iOS-Arch

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumen ini menjelaskan arsitektur jaringan (networking layer) di SAMIR iOS: bagaimana request HTTP dibangun melalui IDNetworkRequest, penyuntikan parameter umum otomatis via ApiParamsHelper, mekanisme penandatanganan kriptografis menggunakan LibNetSignGenerator, pembongkaran envelope respon {code, msg, result}, hingga evaluasi keamanan TLS.

Status Verifikasi: [Verified] (diverifikasi langsung dari IDNetworkRequest.swift, ApiParamsHelper.swift, dan IDNetworkSignatureHandler.swift).

🎯 A. Learning Objective

Setelah mempelajari dokumen ini, pembaca akan mampu:

  1. Menelusuri siklus hidup request HTTP dari pemanggilan di Service hingga pengiriman data oleh Alamofire.
  2. Memahami daftar 18 parameter umum (common parameters) yang wajib disuntikkan ke setiap request in-house.
  3. Menjelaskan 3 varian penandatanganan request: Normal, Image Upload, dan App Config.
  4. Memahami struktur envelope response backend dan penanganan otomatis error code 200 vs 10006.
  5. Mengetahui konfigurasi evaluasi TLS (validatesDomainName) dan risiko NSAllowsArbitraryLoads = true.

📋 B. Prerequisites

  • Sudah membaca 01-dependency-catalog.md.
  • Mengetahui protokol HTTP (Headers, Body, Method POST/GET, Status Codes).

💡 C. Simple Explanation (Analogi Surat Resmi Bersegel Lilin)

Di zaman kerajaan, seorang utusan yang membawa surat ke istana pusat:

  1. Surat Perintah: Surat berisi instruksi spesifik (misal: "Kirim data KTP nasabah").
  2. Kop Surat Standar (ApiParamsHelper): Di bagian atas surat wajib dicap identitas pengirim (nomor HP, tipe perangkat iPhone, versi aplikasi, ID instalasi, jam pengiriman).
  3. Segel Lilin Khusus Raja (sign via LibNetSignGenerator): Sebelum surat dikirim, stempel rahasia dicapkan ke atas lilin panas menggunakan cincin stempel raja (staticKey).
  4. Pemeriksaan di Pintu Gerbang (Backend): Penjaga gerbang memeriksa segel lilin:
  • Jika segel rusak atau huruf di surat diubah satu saja -> Surat Ditolak / Dihancurkan.
  • Jika cap stempel sah -> Surat Diterima.
  1. Amplop Balasan (Envelope {code, msg, result}): Istana membalas dengan amplop standar yang berisi status (200 = Berhasil) dan peti harta (result).

2. Mekanisme Penandatanganan Kriptografis (IDNetworkSignatureHandler)

Path: 🦊 ios/IDSamirLoan/Application/SamirNetworkModule/Classes/Signature/IDNetworkSignatureHandler.swift learn/iOS-Arch ↗

Tersedia 3 varian tanda tangan:

  1. Normal Request Sign (normalRequestSign):
  • Digunakan oleh 95% request API.
  • Mengambil seluruh parameter (umum + payload fitur) -> dikonversi ke JSON string berurutan.
  • Memanggil NetworkRequestSignWrapper.ns_encrypt(forNormal: jsonStr, staticKey: IDNetworkManager.shared.static_key ?? "").
  • Menghasilkan nilai string yang dimasukkan ke field sign.
  1. Image Upload Sign (imageRequestSign):
  • Khusus untuk unggah foto KTP atau selfie wajah.
  • Memanggil NetworkRequestSignWrapper.ns_encrypt(withImage: jsonStr, staticKey: ...).
  1. App Config Sign (appConfigRequestSign):
  • Khusus untuk request pra-login (seperti app-configuration).
  • Tidak membawa parameter pengguna dan menggunakan staticKey = "" (string kosong).

[!CRITICAL] Larangan Keras Developer: Menambah, mengubah nama, atau menghapus salah satu field di ApiParamsHelper AKAN MERUSAK PERHITUNGAN sign! Backend akan langsung menolak request dengan error tanda tangan tidak valid. Setiap perubahan parameter wajib disinkronkan dengan tim backend.

3. Envelope Respon Backend & Status Code

Seluruh API in-house mengembalikan format envelope standar:

{
    "code": "200",
    "msg": "Operasi Berhasil",
    "result": {
        "quotaAmount": 5000000,
        "status": "APPROVED"
    }
}
  • code == "200": Sukses bisnis. IDNetworkRequest langsung mengekstrak objek result dan mengopernya ke block success(req).
  • code == "10006": Sesi kedaluwarsa. IDNetworkRequest otomatis memicu reloginWhenRequestError().
  • Kode Error Lain: Dianggap kegagalan bisnis. Error dilempar ke block failure(req) dengan error domain NSError.cz_stringErrorCode dan pesan cz_errorMessage.

4. Permintaan Pihak Ketiga / Eksternal

Jika aplikasi perlu memanggil API pihak ketiga di luar server SAMIR (contoh: API Advance AI atau server pelacakan risiko):

  • Gunakan helper:
  IDNetworkRequest.id_startPOSTExternalRequest(url, params: [...])
  • Helper ini sengaja melewati penandatanganan sign, tidak menyuntikkan parameter umum SAMIR, dan tidak memeriksa envelope {code, msg, result}.

5. Evaluasi Keamanan TLS & Reachability

  • Dynamic Server Trust (CZDynamicServerTrustManager):

Aplikasi memvalidasi nama domain sertifikat SSL hanya pada build PROD (validatesDomainName = cz_buildProd()). Pada build TEST, validasi nama domain dilonggarkan untuk mempermudah pengujian dengan sertifikat staging atau self-signed.

  • ATS Bypass (NSAllowsArbitraryLoads = true):

Di file IDSamirLoan-Info.plist, pengaturan ini aktif. Ini memungkinkan aplikasi memuat konten HTTP biasa pada webview H5 atau komunikasi mitra perbankan tertentu.

Catatan Audit: Ini adalah celah keamanan yang harus terus dipantau agar server produksi selalu dipaksa HTTPS.

  • Reachability (CZNetworkReachabilityBridge):

Memantau koneksi internet secara realtime. Properti IDNetworkManager.shared.networkEnable dapat diperiksa kapan saja sebelum melakukan request.

6. Audit Arsitektur: Apakah CZNetworkLib Masih Digunakan?

Di dalam direktori proyek masih ditemukan folder 🦊 ios/IDSamirLoan/Application/CZNetworkLib/ learn/iOS-Arch ↗. Apakah library ini masih aktif?

A. Bukti Penelusuran (Code Truth):
  1. Import Dikomentari di Seluruh Bridging Header:
  • Di IDSamirLoan-Bridging-Header.h:L15:
     //#import <CZNetworkLib/CZNetworkLib.h>
  • Di SamirNetworkModule-Bridging-Header.h:L6:
     //#import <CZNetworkLib/CZNetworkLib.h>
  • Di IDNetworkManager.swift:L10:
     //import CZNetworkLib
  1. Dependensi AFNetworking Sudah Dicopot:
  • Di Podfile:L24-25:
     pod 'Alamofire'
     # pod 'AFNetworking'
  1. Pipeline Eksekusi Aktif:
  • Seluruh request jaringan HTTP diinisiasi melalui SamirNetworkModule (IDNetworkRequest.swift dan IDNetworkManager.swift), lalu diteruskan ke Alamofire melalui adapter CZAlamofireBridge.swift.
B. Kesimpulan:

CZNetworkLib SUDAH TIDAK DIGUNAKAN (DEPRECATED / DEAD CODE). Library ini merupakan peninggalan masa lalu saat aplikasi masih berbasis Objective-C dan AFNetworking. Folder yang tertinggal hanya berisi file pembantu kategori yang tidak lagi terpanggil dalam rantai request aktif.

🪜 E. Step-by-Step Walkthrough: Cara Memanggil Endpoint Baru di Service

// Contoh penulisan di IDLoanService.swift
public func requestProductDetail(productId: String, success: @escaping (IDProductDetailModel?) -> Void, failure: @escaping (String) -> Void) {
    let path = "product/V4/detail"
    let params: [String: Any] = ["productId": productId]
    
    IDNetworkRequest.id_startPOSTRequest(path, params: params) { req in
        // 1. Blok Sukses: Data sudah dipastikan code == 200 dan dibungkus di responseObject
        if let resultDict = req.responseObject as? [String: Any] {
            let model = resultDict.kj.model(IDProductDetailModel.self)
            success(model)
        } else {
            success(nil)
        }
    } failure: { req in
        // 2. Blok Gagal: Ambil pesan error dari server
        let errorMsg = req.error?.cz_errorMessage ?? "Terjadi kendala jaringan"
        failure(errorMsg)
    }
}

⚖️ F. Why It Matters: Mengapa Timeout Disetel 90 Detik?

Parameter apiRequestTimeout diatur ke nilai yang cukup longgar, yaitu 90 detik:

// IDNetworkMacro.swift
DefaultTimeout = 90

Hal ini dikarenakan nasabah fintech sering kali berada di daerah dengan koneksi sinyal 3G/4G yang tidak stabil di Indonesia, serta proses scoring risiko di backend terkadang memerlukan waktu komputasi beberapa detik sebelum respon dapat dikembalikan.

🔬 G. Practical Example: Format Pesan Error Fallback Bahasa Indonesia

Jika koneksi internet pengguna terputus saat request sedang berjalan, ekstensi NSError+CZExtension.swift secara otomatis memetakan NSURLErrorNotConnectedToInternet menjadi pesan ramah dalam Bahasa Indonesia:

"Tampaknya ada masalah dengan jaringan, periksa pengaturan koneksi Anda."

sehingga pengguna tidak melihat pesan teknis bahasa Inggris yang membingungkan.

⚠️ H. Common Mistakes & Debugging

  • Mengirim Nilai nil di Dictionary Parameter:
  • Menyertakan nilai nil di dalam dictionary Swift dapat memicu crash atau menghilangkan kunci saat dikonversi ke JSON, yang mengakibatkan perbedaan tanda tangan antara klien dan server.
  • Lupa Base URL Pada External Request:
  • Saat menggunakan id_startPOSTExternalRequest, Anda wajib menyetel req.cz_baseUrl secara eksplisit karena ia tidak menggunakan apiBaseUrl default.

  3. Mengapa penambahan field baru di parameter request harus dikoordinasikan dengan backend?

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Keterikatan Kuat Antar Sub-Modul & Kurangnya Inversi Dependensi

Implementasi komponen sering mengasumsikan keberadaan lingkungan runtime tertentu tanpa kontrak antarmuka yang didefinisikan secara tegas.

⚠️ Smells 2: Risiko Regresi & Minimnya Kontrak Pengujian Terisolasi

Perubahan pada satu service atau helper berpotensi merusak fungsionalitas di modul lain karena tingginya kohesi tersembunyi antar file.

🚀 Blueprint Refactoring Standar Industri: Pola Service Locator & Interface Segregation (SOLID)

Menerapkan prinsip Interface Segregation (ISP) dan Dependency Injection agar setiap service hanya mengekspos metode yang relevan bagi kliennya.

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol SessionProvider: AnyObject {
    var currentToken: String? { get }
    var isAuthenticated: Bool { get }
}

public final class AppSessionManager: SessionProvider {
    public static let shared = AppSessionManager()
    public var currentToken: String?
    public var isAuthenticated: Bool { currentToken != nil }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
