📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumen ini membandingkan dokumentasi lama yang tersimpan di Documentation/docs-samir/docs/id/iOS/ dengan implementasi aktual yang ditemukan pada kode sumber cabang aktif (feature/on-demand-testing-by-DA). Sebagai senior mobile engineer, audit ini membantu Anda membedakan mana informasi warisan (historical documentation) yang masih berlaku dan mana yang sudah usang (deprecated / invalid).

🎯 A. Learning Objective

Setelah mempelajari dokumen ini, Anda diharapkan mampu:

  1. Mengetahui perbedaan nyata (delta discrepancies) antara dokumentasi lama dan kode aktif.
  2. Memahami evolusi sistem konfigurasi environment dari dekripsi gambar JPG ke AppEnv.swift.
  3. Menyadari kehadiran integrasi Flutter hybrid yang sama sekali tidak tercatat di dokumentasi lama.
  4. Menghindari jebakan asumsi teknis saat membaca dokumen-dokumen warisan tim terdahulu.

📌 C. Analisis Mendalam Perbedaan Utama

1. Evolusi Sistem Environment: Kematian Dekripsi JPG [Verified]

Dokumentasi lama mencurahkan bab khusus mengenai "Keamanan Konfigurasi Lingkungan":

"File konfigurasi tidak disimpan dalam bentuk plist terbuka, melainkan disamarkan sebagai berkas gambar JPEG (environment_TEST.jpg) dan didekripsi di runtime menggunakan library C..."

Realitas Kode Sumber Terkini:

Saat memeriksa ios/IDSamirLoan/Application/CZSwiftEnviromentLib/Classes/Base/AppEnv.swift:L25-50:

// Implementasi Aktif:
public class AppEnv {
    public static let `default` = AppEnv()
    public var config: [String: Any] {
        #if TEST
        return [
            "base_url": "https://api-dev.samir.co.id",
            "h5_url": "https://h5-dev.samir.co.id",
            "app_key": "samir_dev_key"
        ]
        #elseif PROD_TEST
        return [ ... ]
        #else
        return [ ... ]
        #endif
    }
}

CZEnvironmentManager.initWithSecret(secret: "...") tetap menerima parameter string rahasia untuk menjaga kompatibilitas API, namun isinya langsung menimpa cachedConfigData = AppEnv.default.config.

  • Pelajaran untuk Engineer Baru: Jangan membuang waktu mencari script enkripsi gambar atau mencari tahu mengapa file .jpg tidak ditemukan di bundle aplikasi. Konfigurasi kini murni ditentukan oleh compiler macro Swift.

2. Tab Repay & Mine Dialihkan ke Flutter [Verified]

Dokumentasi lama mendeskripsikan IDRepayViewController.swift sebagai controller UITableView native yang kompleks dengan custom cell jadwal angsuran.

Realitas Kode Sumber Terkini:

  • Di cabang aktif, saat pengguna mengetuk Tab 1 atau Tab 2, IDMainTabBarController tidak lagi membuka controller native tersebut.
  • Sebaliknya, IDMainTabBarController.installPersistentFlutterHost() menaruh satu view controller FlutterViewController yang terus hidup di background.
  • Ketika Tab 1 diketuk, native memanggil flutterEngineManager.switchTab(to: 0) untuk memerintahkan Flutter IndexedStack menampilkan halaman /repay.
  • Pelajaran untuk Engineer Baru: Jika Anda diminta memperbaiki bug tampilan pada halaman Pembayaran atau Akun Saya, bug tersebut tidak berada di folder ios/IDSamirLoan/Application/, melainkan di folder flutter/lib/pages/.

📌 D. Rekomendasi Penanganan Dokumentasi Lama

  1. Jangan Menghapus Dokumentasi Lama: Folder Documentation/docs-samir/ tetap dipertahankan sebagai artefak historis perjalanan arsitektur SAMIR.
  2. Gunakan iOS-SAMIR-LearningCurve/ Sebagai Single Source of Truth: Seluruh developer baru yang bergabung harus diarahkan ke folder dokumentasi baru ini karena seluruh analisanya telah divalidasi langsung terhadap source code aktif.
  3. Pemberian Catatan Deprecasi: Di masa mendatang, buat file DEPRECATED.md di folder lama yang mengarahkan pembaca ke learning guide ini.

🧠 E. Knowledge Check

  1. Mengapa alur dekripsi file konfigurasi environment_*.jpg tidak lagi berjalan di codebase SAMIR aktif?
  2. Apa perubahan arsitektural terbesar pada Tab 1 (Repay) dan Tab 2 (Mine) yang tidak tercatat di dokumentasi lama?
  3. Berapa deployment target minimum iOS yang sesungguhnya digunakan oleh proyek saat ini?

  • Anda tidak mengasumsikan keberadaan fitur lama yang sudah mati saat melakukan debugging.

🏛️ Bagian 2: Architecture Lab, SOLID Audit & Retention Quizzes

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Keterikatan Kuat Antar Sub-Modul & Kurangnya Inversi Dependensi

Implementasi komponen sering mengasumsikan keberadaan lingkungan runtime tertentu tanpa kontrak antarmuka yang didefinisikan secara tegas.

⚠️ Smells 2: Risiko Regresi & Minimnya Kontrak Pengujian Terisolasi

Perubahan pada satu service atau helper berpotensi merusak fungsionalitas di modul lain karena tingginya kohesi tersembunyi antar file.

🚀 Blueprint Refactoring Standar Industri: Pola Service Locator & Interface Segregation (SOLID)

Menerapkan prinsip Interface Segregation (ISP) dan Dependency Injection agar setiap service hanya mengekspos metode yang relevan bagi kliennya.

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol SessionProvider: AnyObject {
    var currentToken: String? { get }
    var isAuthenticated: Bool { get }
}

public final class AppSessionManager: SessionProvider {
    public static let shared = AppSessionManager()
    public var currentToken: String?
    public var isAuthenticated: Bool { currentToken != nil }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.

🧠 Interactive Retention & Architectural Quiz

Uji pemahaman alur kode nyata dan keputusan arsitektur Anda:

Kuis 1 (Memory Recall): Berdasarkan standar Clean Architecture, apa peran utama dari domain layer pada modul IOS?

Kuis 2 (Architectural Decision): Mengapa penerapan Dependency Inversion Principle (DIP) sangat krusial dalam pembuatan unit test?

Kuis 3 (Debugging & Maintenance): Apa keuntungan utama membatasi dependensi antar modul ke arah satu arah (Unidirectional Dependency)?
