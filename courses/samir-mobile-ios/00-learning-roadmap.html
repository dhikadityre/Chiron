📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumen ini adalah silabus dan peta jalan resmi untuk menguasai codebase SAMIR iOS (IDSamirLoan). Roadmap ini dirancang secara berjenjang (progressive curriculum) dari Level 1 hingga Level 8.

📌 🧭 Filosofi & Struktur Tingkatan (Levels)

Mempelajari codebase monolit modular berskala besar dengan integrasi hybrid Native-Flutter bisa sangat membingungkan jika dilakukan secara acak. Oleh karena itu, kurikulum ini dirancang berurutan:

📊 Diagram Alur #1
graph TD L1[Level 1: Pondasi Proyek & Tooling] --> L2[Level 2: Bootstrapping & Lifecycle] L2 --> L3[Level 3: Arsitektur Monolit Modular] L3 --> L4[Level 4: Fitur & URL Router] L4 --> L5[Level 5: Alur Bisnis End-to-End] L5 --> L6[Level 6: Jaringan, Data, & Flutter Engine] L6 --> L7[Level 7: Debugging, Debt, & Analisis Dampak] L7 --> L8[Level 8: Referensi & Pengayaan]

Mengapa Urutan Ini Efektif?

  • Anda tidak dapat memahami Arsitektur (Level 3) sebelum mengetahui cara aplikasi di-boot dan modul di-load (Level 2).
  • Anda tidak dapat menelusuri Alur Bisnis (Level 5) sebelum memahami URL Router dan peta fitur (Level 4).
  • Anda tidak dapat melakukan Debugging dan Refactoring (Level 7) dengan aman sebelum memahami pipeline data, penandatanganan request, dan integrasi Flutter (Level 6).

📌 Level 1 — Kenali Aplikasi, Struktur Folder, & Build Tooling

A. Tujuan Belajar

Memahami profil aplikasi finansial SAMIR, target pengguna, ekosistem P2P Lending, struktur fisik folder repositori, serta konfigurasi build Xcode (Scheme, Deployment Target, CocoaPods).

B. Pengetahuan yang Diperoleh

  • Mengetahui identitas aplikasi: Bundle ID com.samir.loan, target minimal iOS 14.0, Swift 5.0.
  • Mengetahui letak file source code native (IDSamirLoan/Application), modul Flutter hybrid (flutter/), dan pustaka internal CZ*.
  • Memahami 4 Xcode Schemes (TEST, PROD-TEST, PROD, IDSamirEnvironment).
  • Mengetahui dependensi eksternal utama melalui Podfile.

C. Dokumen yang Harus Dibaca

  1. 01-application-overview.md
  2. 02-repository-structure.md
  3. 03-technology-stack-and-build.md

D. Konsep Kunci Sebelum Melanjutkan

  • Workspace CocoaPods (IDSamirLoan.xcworkspace) vs Xcode Project file (IDSamirLoan.xcodeproj).
  • Mekanisme Build Configuration di Xcode (Preprocessor Macros #if TEST).

E. Pertanyaan yang Harus Bisa Dijawab Setelah Selesai

  1. Mengapa developer harus selalu membuka IDSamirLoan.xcworkspace dan bukan IDSamirLoan.xcodeproj?
  2. Apa perbedaan konfigurasi antara Scheme TEST dan PROD?
  3. Di mana letak source code modul Flutter dan bagaimana CocoaPods menghubungkannya ke proyek iOS?

F. Latihan Eksplorasi Source Code (Observasional)

  • Buka terminal di root repo, amati isi ios/Podfile pada baris 14–20 untuk melihat integrasi podhelper.rb Flutter.
  • Buka ios/IDSamirLoan.xcodeproj/project.pbxproj, cari baris IPHONEOS_DEPLOYMENT_TARGET dan pastikan nilainya adalah 14.0.

G. Kriteria Kelulusan Level 1

Anda dapat menunjukkan lokasi setiap direktori utama di workspace tanpa tersesat dan dapat menjelaskan konfigurasi target build SAMIR kepada rekan setim.

📌 Level 2 — Pahami Bagaimana Aplikasi Berjalan (Bootstrapping & Lifecycle)

A. Tujuan Belajar

Menelusuri urutan eksekusi sejak user menyentuh ikon aplikasi di springboard hingga layar UI pertama tampil di layar kaca perangkat.

B. Pengetahuan yang Diperoleh

  • Peran main.swift sebagai satu-satunya entry point aplikasi (serta inisialisasi Tingyun APM).
  • Bagaimana CZModuleHandler.ModuleManagerApplicationMain memuat daftar modul dari IDModuleList.plist dan IDServiceList.plist.
  • Bagaimana CZAppDelegate mendistribusikan event lifecycle UIApplication ke seluruh modul terdaftar via CZModuleManager.
  • Tahapan inisialisasi di IDSamirMainModule: migrasi data, network setup, prewarming FlutterEngine, dan inisialisasi window.
  • Logika penentuan tampilan awal: IDLaunchViewController (splash countdown 3 detik) vs IDMainTabBarController.

C. Dokumen yang Harus Dibaca

  1. 01-ios-entry-point.md
  2. 02-application-lifecycle.md
  3. 03-startup-sequence-and-initial-routing.md
  4. 04-czmodulemanager-deep-dive.md
  5. Diagram: application-startup.md

D. Konsep Kunci Sebelum Melanjutkan

  • Pola Delegate pada iOS (UIApplicationDelegate).
  • Dynamic class instantiation via NSClassFromString di Swift/Objective-C runtime.

E. Pertanyaan yang Harus Bisa Dijawab Setelah Selesai

  1. File mana yang dieksekusi pertama kali oleh iOS runtime: main.swift atau IDSamirMainModule.swift?
  2. Bagaimana cara modul fitur seperti SamirLoanModule menerima event applicationDidBecomeActive tanpa menyentuh CZAppDelegate?
  3. Kondisi apa yang menyebabkan layar splash dilewati (skip) dan langsung membuka tab bar?

F. Latihan Eksplorasi Source Code

  • Buka ios/IDSamirLoan/main.swift, amati pemanggilan ApplicationLauncher.performLaunchSetup() dan CZModuleHandler.ModuleManagerApplicationMain.
  • Buka ios/IDSamirLoan/Application/SamirMainModule/Classes/IDModule/IDSamirMainModule.swift, periksa method application(_:didFinishLaunchingWithOptions:) pada baris 54–75.

G. Kriteria Kelulusan Level 2

Anda dapat menggambar atau menjelaskan urutan eksekusi startup dari main.swift -> CZModuleManager -> IDSamirMainModule -> IDMainTabBarController secara presisi.

📌 Level 3 — Pahami Arsitektur (Modular Monolith & Decoupled Services)

A. Tujuan Belajar

Menganalisis prinsip arsitektur modular yang membagi aplikasi menjadi pustaka fondasi (CZ*), modul bisnis (Samir*Module), dan mekanisme komunikasi tanpa tight-coupling.

B. Pengetahuan yang Diperoleh

  • Memahami arsitektur Modular Monolith: pemisahan kode secara logis ke dalam folder independen tanpa saling import langsung.
  • Pola Presenter buatan sendiri (ViewController + Presenter + Service + Model).
  • Protokol Layanan Lintas Modul (SamirServiceModule): memanggil fungsi bisnis modul lain melalui IDServiceManager (contoh: memeriksa status login dari modul pinjaman).
  • Peran CZSwiftUIKit dan utility bersama.

C. Dokumen yang Harus Dibaca

  1. 01-architecture-overview.md
  2. 02-layers-and-responsibilities.md
  3. 03-dependency-direction.md
  4. 04-shared-components-and-services.md
  5. Diagram: architecture-overview.md

D. Konsep Kunci Sebelum Melanjutkan

  • Inversion of Control (IoC) & Service Locator Pattern.
  • Clean separation between presentation layer and business/network logic.

E. Pertanyaan yang Harus Bisa Dijawab Setelah Selesai

  1. Jika SamirLoanModule ingin mengetahui apakah pengguna sudah login, bagaimana kodenya memanggil modul login tanpa melakukan import SamirLoginModule?
  2. Apa tanggung jawab sebuah Presenter di codebase ini dan di mana network service dipanggil?
  3. Apa kelebihan dan kelemahan penggunaan NSClassFromString pada registry modul?

F. Latihan Eksplorasi Source Code

  • Buka ios/IDSamirLoan/Application/SamirServiceModule/Classes/IDServiceManager.swift, telusuri method loginService() dan lihat bagaimana protokol IDLoginModuleServiceProtocol di-resolve secara dinamis.
  • Buka ios/IDSamirLoan/Application/SamirLoanModule/Classes/IDPresenter/IDAssessPresenter.swift dan identifikasi interaksinya dengan IDAssessService.

G. Kriteria Kelulusan Level 3

Anda dapat menambahkan interface service baru di SamirServiceModule dan mengimplementasikannya di modul terkait tanpa menimbulkan circular dependency.

📌 Level 4 — Pahami Seluruh Fitur & URL Router (Navigation System)

A. Tujuan Belajar

Menguasai sistem navigasi decoupled berbasis URL (CZSwiftRouterLib + SamirRouterModule), menginventarisasi seluruh fitur yang ada di aplikasi, dan memetakan alur navigasinya.

B. Pengetahuan yang Diperoleh

  • Bagaimana URL Scheme samir:// di-parse dan di-routing oleh CZRouterCenter.
  • Mengetahui seluruh endpoint route yang terdaftar di IDRouterSchemeConstants (Auth, Loan, Main, Web, Repay, Mine).
  • Peta navigasi dari Home ke KYC, Credit Assessment, Loan Confirmation, Voucher, dan WebView.
  • Penanganan deep links (AppsFlyer, Push Notification) dan route filtering.

C. Dokumen yang Harus Dibaca

  • Regex matching pada router table.

E. Pertanyaan yang Harus Bisa Dijawab Setelah Selesai

  2. Bagaimana sebuah halaman Web H5 memerintahkan aplikasi native untuk membuka halaman formulir identitas KTP?

G. Kriteria Kelulusan Level 4

Anda dapat menelusuri rute navigasi dari tombol apa pun di UI ke ViewController tujuan dan memahami parameter data yang dibawanya.

📌 Level 5 — Pahami Business Flow End-to-End

A. Tujuan Belajar

Menganalisis alur bisnis inti dari perspektif pengguna dan bisnis pinjaman: mulai dari onboarding, autentikasi OTP, pengisian KYC, penilaian kredit, konfirmasi pencairan pinjaman, hingga pembayaran tagihan.

B. Pengetahuan yang Diperoleh

  • Alur Otentikasi & Sesi: Request OTP, verifikasi SMS/WA, penanganan 2FA, enkripsi user info, dan token fcm.
  • Alur KYC (Verifikasi Identitas): OCR KTP (IDNewOCRViewController), data pribadi, info pekerjaan, kontak darurat, rekening bank, dan liveness detection (Advance AI / TrustDecision).
  • Alur Penilaian Kuota (Credit Assessment) & Polling: Polling interval status analisa risiko.
  • Alur Konfirmasi Pinjaman (LoanConfirmModule): Penggunaan RxSwift, pemilihan voucher diskon, dan persetujuan kontrak digital.
  • Alur Pembayaran Tagihan: Menampilkan daftar tagihan, kode bayar (VA/minimarket), dan detail pelunasan.

📌 Level 6 — Pahami Data, Pipeline Jaringan, & Integrasi Flutter Hybrid

A. Tujuan Belajar

Memahami bagaimana data ditransformasi, diamankan, dan dikirimkan melalui jaringan terenkripsi bertanda tangan, serta bagaimana runtime Native iOS berbagi state dengan Flutter Engine.

B. Pengetahuan yang Diperoleh

  • Arsitektur Jaringan: IDNetworkRequest (subclass CZBaseRequest), CZAlamofireBridge, dan parameter global default (ApiParamsHelper).
  • Penandatanganan Request: Penggunaan vendor library closed-source LibNetSignGenerator.framework menggunakan staticKey login.
  • Transformasi Data: Serialisasi JSON ke model menggunakan KakaJSON (kj.model).
  • Keamanan & Persistensi: Enkripsi file sesi pengguna idn_userFile.plist menggunakan CryptoKit.AES.GCM dan penyimpanan token di Keychain.
  • Integrasi Hybrid Flutter: FlutterEngineManager (single engine prewarming), routing /mine dan /repay, serta komunikasi via FlutterNativeChannel (samir_native_channel & samir_tracking_channel).

C. Dokumen yang Harus Dibaca

📌 Level 7 — Belajar Debugging, Deteksi Debt, & Maintenance

A. Tujuan Belajar

Mengembangkan kemampuan mendiagnosis masalah di lingkungan lokal, memahami pola error handling, mengidentifikasi technical debt berisiko tinggi, dan melakukan mitigasi risiko saat merilis fitur baru.

B. Pengetahuan yang Diperoleh

  • Memanfaatkan in-app DebugUI pada Scheme TEST untuk membaca request, response payload, dan event analitik secara realtime.
  • Penanganan error: Membedakan error konektivitas HTTP vs kode error bisnis backend (200, 10006, dll).
  • Audit Technical Debt: Risiko ~1.700 force-unwrap (!), isolasi RxSwift hanya di satu modul, hardcoded credentials/secrets, dan duplikasi kode.
  • Analisis Dampak Perubahan (Change Impact Analysis): Checklist sebelum melakukan refactoring atau modifikasi modul fondasi.

C. Dokumen yang Harus Dibaca

  4. 04-change-impact-analysis.md

D. Konsep Kunci Sebelum Melanjutkan

  • Defensive programming vs fail-fast force-unwrapping.
  • Blast radius analysis pada arsitektur modular.

E. Pertanyaan yang Harus Bisa Dijawab Setelah Selesai

  2. Mengapa build PROD menonaktifkan fitur DebugUI secara total?
  3. Langkah apa saja yang wajib dilakukan sebelum mengubah kode di CZNetworkCenter atau SamirServiceModule?

G. Kriteria Kelulusan Level 7

Anda dapat mereproduksi bug API menggunakan DebugUI, mengidentifikasi akar masalah di kode, dan menilai tingkat risiko perubahan sebelum membuat pull request.

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Keterikatan Kuat Antar Sub-Modul & Kurangnya Inversi Dependensi

Implementasi komponen sering mengasumsikan keberadaan lingkungan runtime tertentu tanpa kontrak antarmuka yang didefinisikan secara tegas.

⚠️ Smells 2: Risiko Regresi & Minimnya Kontrak Pengujian Terisolasi

Perubahan pada satu service atau helper berpotensi merusak fungsionalitas di modul lain karena tingginya kohesi tersembunyi antar file.

🚀 Blueprint Refactoring Standar Industri: Pola Service Locator & Interface Segregation (SOLID)

Menerapkan prinsip Interface Segregation (ISP) dan Dependency Injection agar setiap service hanya mengekspos metode yang relevan bagi kliennya.

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol SessionProvider: AnyObject {
    var currentToken: String? { get }
    var isAuthenticated: Bool { get }
}

public final class AppSessionManager: SessionProvider {
    public static let shared = AppSessionManager()
    public var currentToken: String?
    public var isAuthenticated: Bool { currentToken != nil }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
