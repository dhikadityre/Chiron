03 — Dependency Direction

Arah Ketergantungan & Isolasi Modul

📚 Modul: 03-dependency-direction 🎯 Scope: SAMIR Mobile (iOS Native UIKit & FChannel) ⏱️ Estimasi: 20 Menit 🏷️ Git Branch: learn/iOS-Arch

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumen ini menjelaskan aturan arah ketergantungan (dependency direction), hierarki dependensi antar-layer, dan bagaimana protokol antarmuka di SamirServiceModule mencegah timbulnya ketergantungan sirkular (circular dependencies) di SAMIR iOS.

Status Verifikasi: [Verified] (diverifikasi langsung dari import statement di source code aktif).

🎯 A. Learning Objective

Setelah mempelajari dokumen ini, pembaca akan mampu:

  1. Memetakan hierarki ketergantungan piramida dari Foundation (CZ*), Shared Service (SamirServiceModule), hingga Modul Bisnis (Samir*Module).
  2. Menjelaskan prinsip Inversion of Control (IoC) yang diterapkan untuk mencegah modul bisnis saling import secara langsung.
  3. Mengidentifikasi dan mencegah potensi ketergantungan sirkular antara modul Auth, Loan, dan Login.

📋 B. Prerequisites

  • Sudah membaca 01-architecture-overview.md dan 02-layers-and-responsibilities.md.
  • Mengetahui konsep acyclic dependencies principle (ADP) dalam arsitektur perangkat lunak.

💡 C. Simple Explanation (Analogi Rantai Komando Militer)

Dalam struktur militer yang disiplin:

  • Jenderal (Modul Bisnis) dapat memberi instruksi ke Staf Logistik (Pustaka Fondasi & Jaringan).
  • Staf Logistik dilarang memberi perintah atau bergantung pada keputusan Jenderal (pustaka CZ* tidak boleh tahu apa pun tentang bisnis pinjaman).
  • Dua Jenderal dari divisi berbeda (Jenderal Pinjaman dan Jenderal Penagihan) tidak boleh saling memerintah secara langsung. Jika mereka butuh koordinasi, mereka harus mengirimkan memo melalui Biro Penghubung Resmi (SamirServiceModule & SamirRouterModule).

Dengan aturan ini, jika satu divisi bubar atau dirombak total, divisi lain tetap dapat beroperasi tanpa terganggu.

1. Tiga Aturan Mutlak Ketergantungan (Dependency Rules)

  1. Aturan 1 (Downward Dependency Only):

Modul pada layer yang lebih tinggi boleh bergantung pada layer di bawahnya, tetapi layer bawah HARAM bergantung pada layer di atasnya.

Contoh: SamirLoanModule boleh meng-import CZSwiftUIKit, tetapi CZSwiftUIKit dilarang keras meng-import SamirLoanModule.

  1. Aturan 2 (No Sibling Imports):

Modul fitur pada Layer 4 DILARANG KERAS saling meng-import satu sama lain:

  • SamirLoanModule ❌ TIDAK BOLEH meng-import SamirLoginModule.
  • SamirAuthModule ❌ TIDAK BOLEH meng-import SamirLoanModule.
  • SamirRepayModule ❌ TIDAK BOLEH meng-import SamirAuthModule.
  1. Aturan 3 (Protocol Decoupling via Layer 3):

Semua interaksi antarmodul wajib melalui SamirServiceModule (untuk pertukaran data/aksi) atau SamirRouterModule (untuk perpindahan layar).

🪜 E. Step-by-Step Walkthrough: Mencegah Ketergantungan Sirkular

Mari kita telaah skenario klasik yang rawan circular dependency:

  • Modul Pinjaman (Loan) butuh memeriksa apakah user sudah login di Modul Login.
  • Modul Login setelah berhasil login butuh membuka kembali Modul Pinjaman atau me-refresh kuota pinjaman.

Jika kedua modul saling import secara langsung di proyek:

SamirLoanModule -> SamirLoginModule -> SamirLoanModule

Hal ini akan memicu error kompilasi fatal: Circular dependency detected.

📊 Diagram Alur #2
sequenceDiagram participant Loan as SamirLoanModule participant Service as SamirServiceModule (Protocol) participant Handler as SamirLoginModule (Handler) participant Center as NotificationCenter Note over Loan,Handler: Alur Terbebas dari Circular Dependency Loan->>Service: IDServiceManager.loginService()?.isLogin() Service->>Handler: Dipanggil via protokol IDLoginModuleServiceProtocol Handler-->>Loan: Return true/false Note over Handler: User melakukan login di LoginModule Handler->>Center: post(IDN_SamirLoginModule_LoginSuccess_Notification) Center-->>Loan: LoanModule merespon notifikasi dan me-refresh data

Solusi di SAMIR iOS:

  1. SamirServiceModule mendefinisikan interface murni:
   // SamirServiceModule/Classes/LoginModuleService/IDLoginModuleServiceProtocol.swift
   public protocol IDLoginModuleServiceProtocol: CZBaseServiceProtocol {
       func isLogin() -> Bool
       func loginInfo() -> IDLoginCodeModel?
       func loginAction()
   }
  1. SamirLoginModule mengimplementasikan protokol tersebut di IDLoginModuleServiceHandler.
  2. SamirLoanModule hanya meng-import SamirServiceModule dan membaca protokol.
  3. Ketika login selesai, SamirLoginModule tidak memanggil LoanModule secara langsung, melainkan menyiarkan broadcast event via NotificationCenter.
  4. Hasil: Rantai sirkular berhasil diputus secara elegan (Dependency Inversion Principle).

⚖️ F. Why It Matters (Trade-Offs & Analisis Dampak)

  • Keuntungan:
  • Modul Login dapat ditulis ulang atau diganti antarmukanya tanpa mengubah kode internal Modul Pinjaman.
  • Setiap modul fitur dapat di-test secara terisolasi dengan membuat mock handler untuk protokol SamirServiceModule.
  • Kelemahan & Trade-Off:
  • Compiler Swift tidak dapat memeriksa keberadaan handler pada waktu kompilasi (compile-time safety). Jika seseorang menghapus entri di IDServiceList.plist, pemanggilan IDServiceManager.loginService() akan mengembalikan nil secara diam-diam saat runtime.

🔬 G. Practical Example (Contoh Pemanggilan Layanan Nyata)

Di file 🦊 ios/IDSamirLoan/Application/SamirLoanModule/Classes/IDPresenter/IDLoanPresenter.swift learn/iOS-Arch ↗:

// Memeriksa status login sebelum mengambil data produk pinjaman
if let isLogin = IDServiceManager.loginService()?.isLogin(), isLogin == true {
    // Pengguna sudah login, ambil produk yang dipersonalisasi
    self.requstQueryProduct()
} else {
    // Pengguna tamu, tampilkan halaman produk default
    self.handleGuestProductDisplay()
}

Kode ini sangat bersih karena tidak peduli bagaimana SamirLoginModule menyimpan sesi login (apakah di Keychain, UserDefaults, atau file terenkripsi).

⚠️ H. Common Mistakes & Debugging

  • Crash Karena Handler Bernilai nil:
  • Gejala: IDServiceManager.loginService() mengembalikan nil sehingga logika sesi gagal.
  • Penyebab: Typo pada kunci IDLoginModuleServiceProtocol di file IDServiceList.plist atau class IDLoginModuleServiceHandler gagal diinisialisasi.
  • Membuat Protokol Layanan di Folder Modul Fitur:
  • Kesalahan: Mendeklarasikan protokol baru di dalam folder SamirLoanModule/Classes/.
  • Solusi: Protokol yang ditujukan untuk konsumsi lintas modul wajib diletakkan di dalam folder SamirServiceModule/Classes/.

🧠 I. Knowledge Check

  1. Mengapa pustaka fondasi CZ* dilarang meng-import modul bisnis Samir*Module?
  2. Bagaimana cara modul fitur A berkomunikasi dengan modul fitur B tanpa menimbulkan circular dependency?
  3. Di mana file plist yang memetakan nama protokol layanan ke class handler konkretnya?

Latihan Observasi:

Buka file ios/IDSamirLoan/Application/Configuration/Module/IDServiceList.plist. Cocokkan 4 nama protokol yang ada di dalamnya dengan file deklarasinya di folder SamirServiceModule/Classes/.

🏛️ Bagian 2: Architecture Lab, SOLID Audit & Retention Quizzes

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Keterikatan Kuat Antar Sub-Modul & Kurangnya Inversi Dependensi

Implementasi komponen sering mengasumsikan keberadaan lingkungan runtime tertentu tanpa kontrak antarmuka yang didefinisikan secara tegas.

⚠️ Smells 2: Risiko Regresi & Minimnya Kontrak Pengujian Terisolasi

Perubahan pada satu service atau helper berpotensi merusak fungsionalitas di modul lain karena tingginya kohesi tersembunyi antar file.

🚀 Blueprint Refactoring Standar Industri: Pola Service Locator & Interface Segregation (SOLID)

Menerapkan prinsip Interface Segregation (ISP) dan Dependency Injection agar setiap service hanya mengekspos metode yang relevan bagi kliennya.

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol SessionProvider: AnyObject {
    var currentToken: String? { get }
    var isAuthenticated: Bool { get }
}

public final class AppSessionManager: SessionProvider {
    public static let shared = AppSessionManager()
    public var currentToken: String?
    public var isAuthenticated: Bool { currentToken != nil }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
