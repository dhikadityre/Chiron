📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumen ini membedah lapisan internal (internal layers) yang membentuk setiap modul di SAMIR iOS: peran ViewController, Presenter, Service, Model, dan View, serta kasus khusus arsitektur reaktif di LoanConfirmModule.

Status Verifikasi: [Verified] (diverifikasi langsung dari implementasi class di SamirLoanModule, SamirAuthModule, dan SamirCommonModule).

🎯 A. Learning Objective

Setelah mempelajari dokumen ini, pembaca akan mampu:

  1. Memahami pembagian layer: Presentation (ViewController & View), Business/Presentation Logic (Presenter), Data/Network (Service), dan State/Schema (Model).
  2. Mengetahui fitur bawaan dari IDBaseViewController (nav bar style, pop gesture toggle, tracking view duration).
  3. Memahami perbedaan antara pola Presenter standar vs pola MVVM-Rx di LoanConfirmModule.

📋 B. Prerequisites

  • Sudah membaca 01-architecture-overview.md.
  • Mengetahui pola desain MVC, MVP, dan MVVM pada pengembangan iOS.

💡 C. Simple Explanation (Analogi Restoran Berbintang)

Bayangkan sebuah restoran yang melayani pesanan makanan:

  • Pelayan (ViewController): Menghadapi pelanggan, mencatat menu yang dipilih pelanggan di layar, mengatur dekorasi meja, dan menampilkan piring makanan.
  • Kepala Pelayan / Maître d' (Presenter): Menerima pesanan dari pelayan, memvalidasi apakah pelanggan memenuhi syarat (misal: usia cukup untuk menu tertentu), lalu menyuruh bagian gudang mengambil bahan baku.
  • Bagian Pengadaan / Gudang (Service): Menghubungi supplier melalui telepon (Network API Request) dan mengambil bahan makanan dalam kardus (JSON Response).
  • Kardus Makanan Terdaftar (Model): Struktur data rapi yang berisi label bahan makanan, tanggal kadaluwarsa, dan takaran.
  • Piring & Hiasan Meja (View / TableViewCell): Elemen visual tempat menyajikan data agar terlihat menarik bagi pelanggan.

1. Presentation Layer (ViewController & IDBaseViewController)

Semua controller mewarisi base class 🦊 ios/IDSamirLoan/Application/SamirCommonModule/Classes/IDBase/IDBaseViewController.swift learn/iOS-Arch ↗.

Fitur standar yang disediakan otomatis oleh base controller:

  • Navigation Bar Styling: Properti idNavType (.idNavTypeWhite, .idNavTypeClear, .idNavTypeNormal).
  • Interactive Pop Gesture: Fungsi popGestureClose() untuk mematikan gesture swipe back saat pengisian formulir kritis (misal: verifikasi wajah atau input PIN) dan popGestureOpen() untuk mengaktifkannya kembali.
  • Duration Tracking: Otomatis merekam startTimeStamp saat viewWillAppear dan endTimeStamp saat viewWillDisappear untuk dikirim ke sistem pelaporan risiko fraud (IDCustomPointManager.reportRiskViewRealtime).
  • Empty & Error State: Callback id_clickEmptyBlock untuk reload saat jaringan bermasalah.

2. Presenter Layer (Presenter)

Presenter di SAMIR bertindak sebagai koordinator logika presentasi:

  • Validasi Input: Memeriksa format nomor KTP (16 digit), validasi nomor rekening, atau batas usia legal (wetherAgeInLegalRange di IDNewAuthPresenter).
  • State Machine & Polling: Mengelola status berkala (contoh: polling keputusan analisa kuota di IDAssessPresenter.startPolling).
  • Pelaporan Analitik: Memicu event klik tombol atau impresi layar ke IDCustomPointManager atau IDDataReportUtils.
Pola Komposisi Presenter: Mengapa di IDNewAuthPresenter Terdapat 2 Presenter Lain?

Di dalam 🦊 IDNewAuthPresenter.swift:L33-43 learn/iOS-Arch ↗, didefinisikan dua child presenter:

lazy var resourcePresenter: IDAuthResourcePresenter = { [unowned self] in
    let presenter = IDAuthResourcePresenter()
    presenter.currentVC = self.currentVC
    return presenter
}()

lazy var bankPresenter: IDAuthBankPresenter = { [unowned self] in
    let presenter = IDAuthBankPresenter()
    presenter.delegate = self
    return presenter
}()

Mengapa Dibuat Demikian?

  1. Pencegahan "God Presenter" (Separation of Concerns / SRP):
  • Alur KYC autentikasi V2 mencakup 5 langkah besar (.ocr, .basic, .job, .contact, .bank, .changeBank). Jika seluruh logika ditaruh di satu file, ukurannya bisa menembus lebih dari 3.000 baris.
  1. *Pola Komposisi (Composite Presenter Pattern)*:
  • IDNewAuthPresenter bertindak sebagai Orkestrator Utama (mengelola navigasi antarlangkah, tableview datasource/delegate, validasi form, dan submission).
  • resourcePresenter (Spesialis Kamus Data & Wilayah): Bertanggung jawab khusus mengunduh dan menyajikan data berjenjang (cascading selection) untuk provinsi, kota, kecamatan, serta kamus opsi (agama, jenis pekerjaan, status perkawinan).
  • bankPresenter (Spesialis Rekening Bank): Bertanggung jawab khusus mencari daftar nama bank, menyaring bank populer (hot banks), dan mengelola pencarian akun bank nasabah.
  1. Reusability: IDAuthResourcePresenter dan IDAuthBankPresenter merupakan modul independen yang sudah matang dan dapat digunakan ulang di luar layar KYC tanpa menduplikasi kode.

3. Service Layer (Service)

Service murni bertanggung jawab atas interaksi I/O jaringan:

  • Memanggil IDNetworkRequest.id_startPOSTRequest(...).
  • Mengurai response dictionary menggunakan pustaka KakaJSON:
  if let resultDict = req.responseObject as? [String: Any] {
      let model = resultDict.kj.model(IDAssessModel.self)
      success(model)
  }
  • Menangani pemetaan error jaringan ke format yang dimengerti Presenter.

4. Model Layer (Model)

Struct atau Class yang mengadopsi protokol Convertible dari KakaJSON:

  • Mendefinisikan schema payload backend.
  • Mendukung mapping custom key jika nama properti JSON berbeda dari nama properti Swift.

5. Kasus Khusus: LoanConfirmModule (Arsitektur Reaktif MVVM-Rx)

Path: 🦊 ios/IDSamirLoan/Application/SamirLoanModule/Classes/LoanConfirmModule/ learn/iOS-Arch ↗

Di modul ini, alur data tidak menggunakan delegate Presenter, melainkan stream reaktif berbasis Clean MVVM + RxSwift:

A. Kontrak Input-Output (LoanConfirmViewModelType)

Arsitektur ViewModel memisahkan secara tegas antara aksi pengguna (Input) dan state UI (Output):

  • LoanConfirmViewModelInput:

Menggunakan PublishSubject untuk menerima event UI: confirmTap, selectCoupon, selectProduct, toggleTermsAgreement, refreshTrial, submitCycleLoanOrder.

  • LoanConfirmViewModelOutput:

Menggunakan Driver<T> untuk aliran data yang diobservasi oleh View: isLoading, error, loanData, selectedCoupon, trialResult, canSubmit, showIncomeUpdate.

B. Kapan Memakai subscribe dan Kapan Memakai drive?
Skenario PenggunaanRekomendasiAlasan Teknis
Binding ke Elemen UI (UILabel, UIButton, HUD, TableView)drive1. Pasti dieksekusi di Main Thread (MainScheduler). Tidak perlu menulis .observe(on: MainScheduler.instance).
2. Tidak Pernah Error: Driver menjamin stream tidak akan putus akibat error uncaught, sehingga UI tidak membeku.
3. Sharing Replay Otomatis: Memiliki sifat share(replay: 1, scope: .whileConnected) sehingga multiple binding ke label/tombol tidak memicu duplicate network request.
Logika Data, Domain, Service, & Network APIsubscribe1. Dapat Berjalan di Background: Operasi I/O, parsing JSON, atau komputasi berat membutuhkan background thread (ConcurrentDispatchQueueScheduler).
2. Penanganan Error Alami: Perlu menangkap event .error(Error) dari HTTP request untuk retry atau logging.
3. Menerima Input di ViewModel: Observasi event PublishSubject di level internal ViewModel.

Aturan Praktis (Rule of Thumb):

  • Di dalam ViewController: Gunakan viewModel.output.someData.drive(...) saat memperbarui tampilan.
  • Di dalam Service / Internal ViewModel: Gunakan .subscribe(...) saat menangani pipeline asinkron dan error.
C. Inventaris Arsitektur Codebase: Mana yang Menggunakan viewModel vs presenter?

Berdasarkan audit komprehensif di seluruh direktori IDSamirLoan:

  1. Menggunakan ViewModel (MVVM + RxSwift):
  • HANYA 1 MODUL: SamirLoanModule/Classes/LoanConfirmModule/
  • LoanConfirmViewModel.swift & LoanConfirmViewModelType.swift
  • Dikonsumsi oleh LoanConfirmViewController_Rx.swift
  • Status: Modul ini merupakan satu-satunya area modern/reaktif di aplikasi, dibangun secara khusus untuk menangani kompleksitas kalkulasi bunga, tenor dinamis, dan kupon diskon.
  1. Menggunakan Presenter (Pola MVP / MVC Konvensional):
  • SELURUH MODUL LAINNYA:
  • SamirLoginModule: LoginV2Presenter, IDLoginPresenter
  • SamirAuthModule: IDNewAuthPresenter (V2), IDAuthResourcePresenter, IDAuthBankPresenter, IDAuthLivePresenter, IDAuthPointPresenter
  • SamirLoanModule (di luar confirm): IDLoanPresenter, IDAssessPresenter
  • SamirRepayModule: IDRepayPresenter
  • SamirMineModule: IDMinePresenter, IDMineCloseAccountPresenter
  • SamirCommonModule: IDBasePresenter

🪜 E. Step-by-Step Walkthrough: Alur Pengisian Formulir Kontak Darurat

Mari kita lihat bagaimana layer-layer ini bekerja sama saat user mengisi kontak darurat di SamirAuthModule:

  1. User Action: User memilih hubungan keluarga dan nomor kontak di 🦊 IDNewAuthContactViewController.swift learn/iOS-Arch ↗.
  2. Controller ke Presenter: Controller memanggil presenter.submitEmergencyContacts(data).
  3. Validasi Presenter: IDNewAuthPresenter memeriksa apakah nomor kontak valid dan tidak sama dengan nomor ponsel akun sendiri.
  4. Presenter ke Service: Jika valid, Presenter memanggil IDAuthAPI.saveContactInfo(...) di IDNetworkService.
  5. Eksekusi Jaringan: Service membungkus data ke JSON, menandatangani request via IDNetworkSignatureHandler, dan mengirim ke server.
  6. Response & UI Update:
  • Jika berhasil (code == "200"), Presenter menyuruh Controller: view.didSuccessSaveContacts().
  • Controller melakukan navigasi ke langkah berikutnya via router: IDRouterManager.id_perfromWithURLString(IDRouterSchemeConstants.Auth.bankCard.rawValue).

⚖️ F. Why It Matters (Trade-Offs & Analisis Desain)

  • Mengapa Pola Presenter Dipilih daripada MVVM Standar?

Presenter buatan sendiri tidak memerlukan pustaka pihak ketiga eksternal (seperti RxSwift atau Combine), sehingga mudah dipahami oleh developer dari berbagai latar belakang pengalaman.

  • Konsekuensi Monolitik pada Controller:

Meskipun logika bisnis sudah dipindahkan ke Presenter, beberapa ViewController (seperti IDHomeViewController) tetap membengkak hingga ribuan baris karena banyaknya konfigurasi tampilan programatik SnapKit dan manajemen subview popup.

🔬 G. Practical Example (Kode Programatik SnapKit di View)

Seluruh UI di SAMIR iOS dibangun secara programatik tanpa Storyboard/XIB. Contoh dari implementasi sel tabel verifikasi:

// IDNewAuthValueTableViewCell.swift
override func setupViews() {
    contentView.addSubview(titleLabel)
    contentView.addSubview(valueTextField)
    
    titleLabel.snp.makeConstraints { make in
        make.left.equalToSuperview().offset(16)
        make.centerY.equalToSuperview()
        make.width.equalTo(100)
    }
    
    valueTextField.snp.makeConstraints { make in
        make.left.equalTo(titleLabel.snp.right).offset(12)
        make.right.equalToSuperview().offset(-16)
        make.centerY.equalToSuperview()
        make.height.equalTo(44)
    }
}

⚠️ H. Common Mistakes & Debugging

  • Memory Leak pada Presenter / Closure:
  • Kesalahan: Presenter memegang referensi kuat (strong reference) ke ViewController, atau closure callback tidak menggunakan [weak self].
  • Pencegahan: Selalu gunakan weak var view: IDSomeViewProtocol? di Presenter dan [weak self] di blok network callback.
  • Memanggil Endpoint Jaringan Langsung dari ViewController:
  • Kesalahan: Menulis IDNetworkRequest.id_startPOSTRequest langsung di dalam viewDidLoad().
  • Aturan: Semua panggilan jaringan wajib diisolasi di layer Service dan dikoordinasikan oleh Presenter atau ViewModel.

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Keterikatan Kuat Antar Sub-Modul & Kurangnya Inversi Dependensi

Implementasi komponen sering mengasumsikan keberadaan lingkungan runtime tertentu tanpa kontrak antarmuka yang didefinisikan secara tegas.

⚠️ Smells 2: Risiko Regresi & Minimnya Kontrak Pengujian Terisolasi

Perubahan pada satu service atau helper berpotensi merusak fungsionalitas di modul lain karena tingginya kohesi tersembunyi antar file.

🚀 Blueprint Refactoring Standar Industri: Pola Service Locator & Interface Segregation (SOLID)

Menerapkan prinsip Interface Segregation (ISP) dan Dependency Injection agar setiap service hanya mengekspos metode yang relevan bagi kliennya.

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol SessionProvider: AnyObject {
    var currentToken: String? { get }
    var isAuthenticated: Bool { get }
}

public final class AppSessionManager: SessionProvider {
    public static let shared = AppSessionManager()
    public var currentToken: String?
    public var isAuthenticated: Bool { currentToken != nil }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
