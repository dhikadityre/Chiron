01 — Architecture Overview

Konsep Monolit Modular

📚 Modul: 01-architecture-overview 🎯 Scope: SAMIR Mobile (iOS Native UIKit & FChannel) ⏱️ Estimasi: 20 Menit 🏷️ Git Branch: learn/iOS-Arch

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumen ini menjelaskan gambaran arsitektur tingkat tinggi dari aplikasi SAMIR iOS (IDSamirLoan): mengapa sistem didesain sebagai Modular Monolith, bagaimana modul-modul independen berkomunikasi tanpa saling import, dan bagaimana arsitektur ini menyeimbangkan kecepatan kompilasi dengan isolasi domain bisnis.

Status Verifikasi: [Verified] (diverifikasi langsung dari arsitektur folder dan file konfigurasi modul).

🎯 A. Learning Objective

Setelah mempelajari dokumen ini, pembaca akan mampu:

  1. Mendefinisikan konsep arsitektur Modular Monolith dalam konteks pengembangan aplikasi iOS.
  2. Memahami 3 pilar utama arsitektur SAMIR iOS: Module Framework (CZSwiftModuleLib), Service Registry (SamirServiceModule), dan URL Router (CZSwiftRouterLib).
  3. Menjelaskan trade-off antara monolit modular berbasis folder vs framework dinamis (.framework) terpisah.

📋 B. Prerequisites

  • Sudah menyelesaikan kurikulum Level 1 dan Level 2.
  • Mengetahui konsep dasar Dependency Inversion dan Decoupling pada Object-Oriented Programming.

💡 C. Simple Explanation (Analogi Mall & Toko-Toko Terpisah)

Bayangkan sebuah pusat perbelanjaan (Mall):

  • Mall (Monolit): Semua berada dalam satu gedung fisik yang sama (satu binary aplikasi target IDSamirLoan).
  • Toko-Toko (Modul Bisnis): Di dalam mall terdapat toko buku, toko pakaian, dan restoran (SamirLoanModule, SamirAuthModule, SamirMineModule). Masing-masing toko memiliki tata letak dan staf sendiri.
  • Pusat Informasi & Interkom (Service Registry & Router):
    • Jika toko buku ingin menanyakan apakah seorang pelanggan adalah member VIP, staf toko buku tidak perlu berjalan ke kantor pusat keanggotaan; mereka cukup menghubungi Meja Layanan (IDServiceManager.loginService()?.isLogin()).
    • Jika seorang pelanggan ingin pergi dari restoran ke bioskop, ada papan petunjuk arah berbasis rute (samir://auth/identity).

Dengan cara ini, masing-masing toko dapat merenovasi ruangannya tanpa merusak struktur gedung mall.

1. Pilar 1: Kerangka Modul Runtime (CZSwiftModuleLib)

Modul-modul bisnis tidak di-import secara eksplisit oleh AppDelegate. Sebaliknya:

  • Setiap modul bisnis memiliki class modul yang mengadopsi protokol CZModuleProtocol (misal: IDSamirMainModule, IDSamirLoanModule).
  • Modul didaftarkan melalui konfigurasi XML di 🦊 IDModuleList.plist learn/iOS-Arch ↗.
  • Saat boot, CZModuleManager menggunakan NSClassFromString untuk menginstansiasi class modul secara dinamis.
  • Hasil: Modul tidak memiliki dependensi kompilasi terhadap AppDelegate!

2. Pilar 2: Pertukaran Data Lintas Modul (SamirServiceModule)

Jika modul A membutuhkan data atau aksi dari modul B (contoh: modul Pinjaman butuh info sesi login), modul A dilarang keras meng-import SamirLoginModule.

  • Modul login mendaftarkan IDLoginModuleServiceHandler ke 🦊 IDServiceList.plist learn/iOS-Arch ↗ yang mengadopsi protokol IDLoginModuleServiceProtocol.
  • Modul pinjaman cukup memanggil: 
  let isLoggedIn = IDServiceManager.loginService()?.isLogin() ?? false
  • CZModuleManager menginstansiasi handler tersebut secara lazy dan thread-safe (menggunakan antrean serial serviceCacheQueue).

3. Pilar 3: Navigasi Bebas Ketergantungan (SamirRouterModule)

Ketika user berada di halaman Beranda dan ingin membuka verifikasi identitas:

  • Alih-alih melakukan navigationController?.pushViewController(IDNewOCRViewController(), animated: true) (yang akan memaksa Beranda meng-import modul Auth), Beranda memanggil: 
  IDRouterManager.id_perfromWithURLString(IDRouterSchemeConstants.Auth.identity.rawValue)
  • CZRouterCenter mencocokkan skema samir://auth/identity dan mendispatch panggilan ke IDSamirAuthModuleRouterHandler.

🪜 E. Step-by-Step Walkthrough: Alur Komunikasi Lintas Modul

Mari kita telusuri bagaimana Beranda (SamirLoanModule) memicu login saat user yang belum login menekan tombol "Ajukan Pinjaman":

  1. Step 1 — Deteksi Sesi:

Presenter beranda memanggil protokol layanan:

let isLogin = IDServiceManager.loginService()?.isLogin() ?? false

  1. Step 2 — Trigger Login Action:

Jika isLogin == false, beranda memanggil:

IDServiceManager.loginService()?.loginAction()

  1. Step 3 — Presentasi Form Login:

IDLoginModuleServiceHandler.loginAction() mengeksekusi IDLoginManager.shared.loginAction().

IDLoginManager mengambil top ViewController di layar (UIViewController.cz.topViewController()) dan memunculkan IDLoginNavViewController secara modal.

  1. Step 4 — Login Berhasil:

Setelah user memasukkan OTP dan login berhasil, IDLoginManager mengirim notifikasi siaran IDN_SamirLoginModule_LoginSuccess_Notification.

  1. Step 5 — Reaksi Beranda:

IDHomeViewController yang mendengarkan notifikasi tersebut otomatis me-refresh data produk pinjaman (requstQueryProduct()).

Semua langkah di atas berjalan mulus tanpa ada satu baris pun import SamirLoginModule di dalam SamirLoanModule!

⚖️ F. Why It Matters: Mengapa Bukan Dynamic Frameworks Terpisah?

Banyak developer bertanya: "Mengapa modul-modul ini tidak dijadikan Framework (.framework) terpisah via CocoaPods / SPM?"

KarakteristikFolder-Based Modular Monolith (SAMIR)Dynamic Frameworks Terpisah
Waktu Peluncuran (Cold Start)Sangat Cepat (Semua kode berada dalam satu biner, tidak membebani dyld dynamic linker).Lebih Lambat (Setiap .framework menambah overhead waktu peluncuran aplikasi).
Isolasi KodeDitegakkan oleh Konvensi & Service Registry (developer dilarang mengimpor modul lain).Ditegakkan oleh Compiler (akses dibatasi oleh modifier public vs internal).
Kompleksitas ManajemenRendah (Satu proyek Xcode, sinkronisasi file otomatis).Tinggi (Perlu memelihara banyak Podspec, versi pod, dan linking script).
Ukuran BinerRamping (Tidak ada duplikasi header atau metadata framework per modul).Lebih Besar (Overhead struktur biner framework).

Keputusan arsitektur ini terbukti sangat efektif untuk aplikasi skala menengah hingga besar di industri finansial yang mementingkan waktu respon peluncuran aplikasi yang cepat bagi nasabah.

🔬 G. Practical Example: Pola Presenter di Setiap Modul

Setiap modul bisnis mengadopsi pola variasi MVP buatan sendiri:

  • IDHomeViewController: Mengatur view lifecycle dan event UI (tap tombol).
  • IDAssessPresenter: Menerima perintah dari controller, memformat data, dan memanggil network service.
  • IDLoanService: Mengeksekusi request jaringan IDNetworkRequest.id_startPOSTRequest.
  • IDProductModel: Struct / class representasi JSON dari KakaJSON.

Pengecualian: LoanConfirmModule menggunakan pola MVVM-Rx dengan LoanConfirmViewController_Rx dan LoanConfirmViewModel (didukung oleh driver reaktif RxCocoa).

⚠️ H. Common Mistakes & Debugging

  • Melakukan Import Antarmodul Secara Ilegal:
    • Kesalahan: Menulis import SamirLoginModule di dalam file milik SamirLoanModule.
    • Dampak: Menghancurkan batas modularitas (architectural erosion) dan berisiko menciptakan circular dependency.
    • Solusi: Selalu gunakan IDServiceManager.loginService() untuk mengakses kapabilitas login.
  • Menambahkan Route Duplikat:
    • Kesalahan: Menambahkan router baru dengan host yang sama pada modul berbeda.
    • Dampak: CZRouterCenter.addRouter memiliki baris assert(!self.isDuplicateRouter(router!)) yang akan membuat aplikasi langsung crash saat startup debug!

🏛️ Bagian 2: Architecture Lab, SOLID Audit & Retention Quizzes

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Keterikatan Kuat Antar Sub-Modul & Kurangnya Inversi Dependensi

Implementasi komponen sering mengasumsikan keberadaan lingkungan runtime tertentu tanpa kontrak antarmuka yang didefinisikan secara tegas.

⚠️ Smells 2: Risiko Regresi & Minimnya Kontrak Pengujian Terisolasi

Perubahan pada satu service atau helper berpotensi merusak fungsionalitas di modul lain karena tingginya kohesi tersembunyi antar file.

🚀 Blueprint Refactoring Standar Industri: Pola Service Locator & Interface Segregation (SOLID)

Menerapkan prinsip Interface Segregation (ISP) dan Dependency Injection agar setiap service hanya mengekspos metode yang relevan bagi kliennya.

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol SessionProvider: AnyObject {
    var currentToken: String? { get }
    var isAuthenticated: Bool { get }
}

public final class AppSessionManager: SessionProvider {
    public static let shared = AppSessionManager()
    public var currentToken: String?
    public var isAuthenticated: Bool { currentToken != nil }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
