Core Knowledge

Dokumen ini mengupas tuntas proses di balik layar (under the hood) dari 🦊 CZModuleManager.swift learn/iOS-Arch ↗ di lingkungan Production: mulai dari bootstrapping cold start, dynamic class reflection, resolusi namespace Swift (moduleName vs bundleName), mekanisme routing & URL filtering, koordinasi penanganan deeplink saat splash screen, hingga inter-module communication melalui thread-safe service locator.

Status Verifikasi: [Verified] (diverifikasi langsung dari CZModuleManager.swift, CZModuleProtocol.swift, CZRouterCenter.swift, Bundle+CZExtension.swift, IDSamirMainModule.swift, IDHomeViewController.swift, dan IDModuleList.plist).

🎯 A. Learning Objective

Setelah mempelajari dokumen ini, pembaca akan mampu:

  1. Menjelaskan siklus hidup internal CZModuleManager dari fase Cold Start hingga dispatch event runtime UIKit.
  2. Memahami mekanisme refleksi dinamis NSClassFromString, format namespace biner Swift, dan alasan teknis mengapa registerModule("\(moduleName).\(className)") selalu bernilai false di Production sementara fallback Bundle.cz.bundleName + ".\(className)" yang berhasil.
  3. Menyebutkan kondisi-kondisi di mana moduleObject dapat bernilai nil / false saat factory method create() dipanggil.
  4. Menjelaskan arsitektur pendaftaran routers() dan routerFilters() (CZRouterCenter) lengkap dengan contoh alur nyata: navigasi antarmodul, passing parameters, hingga back navigation.
  5. Menjelaskan use case aliasing / URL rewriting pada routerFilters untuk backward-compatibility deep link lama.
  6. Memahami koordinasi penundaan eksekusi Deeplink (Samir_DeepLink_Str) selama splash countdown 3 detik hingga dikonsumsi oleh Beranda.
  7. Menjelaskan mengapa serviceForProtocol dibuat, seberapa penting perannya (dipanggil 80+ kali di SAMIR), dan bagaimana serial queue menjamin thread-safety.

📌 C. Definisi & Konsep Kunci

1. Apa itu Cold Start?

Dalam pengembangan mobile iOS, siklus peluncuran aplikasi terbagi menjadi tiga kondisi:

  • Cold Start (Kondisi Mati Total):

Aplikasi diluncurkan ketika proses biner sama sekali belum ada di memori RAM perangkat.

  • Pemicu: Pengguna baru menyalakan HP, aplikasi baru saja ditutup paksa (force quit / swipe up) dari App Switcher, atau sistem operasi iOS mematikan proses di background untuk membebaskan RAM.
  • Rangkaian Eksekusi: Kernel OS memuat biner -> dyld -> 🦊 main.swift learn/iOS-Arch ↗ -> Inisialisasi APM TingYun -> 🦊 CZModuleManager.setup learn/iOS-Arch ↗ (baca plist & register seluruh modul/service) -> UIApplicationMain -> CZAppDelegate -> IDSamirMainModule (Window, Flutter prewarm, Splash Screen 3 detik).
  • Warm Start: Proses aplikasi masih ada di RAM (berada di background), lalu pengguna membuka kembali aplikasi. Sistem tidak mengulang main.swift maupun CZModuleManager.setup(), melainkan hanya memicu lifecycle applicationWillEnterForeground dan applicationDidBecomeActive.
  • Hot Start: Aplikasi baru diminimize sebentar dan OS langsung membawanya ke foreground tanpa reload state apa pun.

2. Analogi Pusat Pengendali Terminal Bandara

Bayangkan CZModuleManager sebagai Pusat Pengendali Terminal Bandara:

  • Manifest Maskapai (🦊 IDModuleList.plist learn/iOS-Arch ↗): Daftar resmi maskapai yang beroperasi di bandara (SamirMainModule, SamirLoanModule, SamirAuthModule, dll.).
  • Petugas Registrasi (registerAllModules): Memanggil nama maskapai. Jika dipanggil dengan kode internasional (moduleName) gagal karena semua maskapai bernaung di bawah satu bendera bandara lokal (bundleName = IDSamirLoan), petugas beralih menggunakan kode lokal.
  • Papan Petunjuk & Gate Boarding (routers): Setiap maskapai mendaftarkan pintu gate masing-masing (samir://auth/identity).
  • Layanan Pengalihan Tiket Lama (routerFilters): Mengarahkan penumpang yang membawa tiket lama dengan nomor gerbang usang ke gerbang baru secara otomatis tanpa tersesat.
  • Loket Layanan Bersama (serviceForProtocol): Tempat maskapai meminta layanan bersama (misal: verifikasi status login user) melalui antrean tertib dan aman (serviceCacheQueue.sync).

A. Apakah secara flow ia mendaftarkan moduleName atau bundleName?

[!IMPORTANT] Secara flow aktual di Production, yang berhasil didaftarkan selalu bundleName (IDSamirLoan.<ClassName>)!

Mari telusuri penyebab teknisnya:

  1. Di 🦊 IDModuleList.plist learn/iOS-Arch ↗:
  • moduleName (Key) = "SamirMainModule"
  • className (Value) = "IDSamirMainModule"
  1. Di Swift runtime, simbol class disimpan dengan format: <NamaTarget/Binary>.<NamaClass>.
  2. Dalam struktur proyek SAMIR iOS, modul SamirMainModule, SamirAuthModule, dll. tidak dikompilasi sebagai Dynamic Framework / CocoaPods terpisah, melainkan berada di dalam target aplikasi utama (🦊 IDSamirLoan.xcodeproj learn/iOS-Arch ↗).
  3. Akibatnya, namespace resmi class tersebut di memori biner adalah:

"IDSamirLoan.IDSamirMainModule" (bukan "SamirMainModule.IDSamirMainModule").

  1. Properti 🦊 Bundle.cz.bundleName learn/iOS-Arch ↗ mengambil CFBundleName dari Bundle.main, yang menghasilkan string "IDSamirLoan".
B. Pembedahan NSClassFromString dan Kondisi moduleObject Bernilai false
// CZModuleManager.swift:L80-L86
guard let moduleClass: AnyClass = NSClassFromString(moduleName) else {
    return false
}
guard let moduleObject: CZModuleProtocol = (moduleClass as! CZModuleProtocol.Type).create() else { 
    return false
}
  1. Apa itu NSClassFromString?

Fungsi runtime Objective-C / Foundation yang mengubah string nama lengkap class menjadi metatype class (AnyClass?) di memori. Jika nama class cocok dengan tabel simbol biner yang dimuat, ia mengembalikan tipe class-nya; jika tidak ditemukan, ia mengembalikan nil.

  1. Evaluasi Pemanggilan Pertama (moduleName.className):
   registerModule("SamirMainModule.IDSamirMainModule")

NSClassFromString pasti menghasilkan nil karena tidak ada binary framework bernama SamirMainModule. guard pertama langsung gagal dan me-return false.

  1. Evaluasi Pemanggilan Kedua (Fallback Bundle.cz.bundleName + ".\(className)"):
   registerModule("IDSamirLoan.IDSamirMainModule")

NSClassFromString berhasil menemukan AnyClass.

  1. Kapan moduleObject pada guard kedua bisa bernilai false / nil?

Metode protokol didefinisikan sebagai failable factory method:

   @objc public protocol CZModuleProtocol: UIApplicationDelegate {
       static func create() -> CZModuleProtocol?
   }

Nilai moduleObject bernilai nil jika:

  • Feature Flag / Kill Switch: Implementasi create() sengaja mengecek kondisi feature toggle dan me-return nil jika fitur sedang dimatikan.
  • Kegagalan Inisialisasi Dependensi Internal: Jika create() membutuhkan alokasi memori penting atau berkas konfigurasi lokal yang corrupt/gagal dimuat.
  • Unit Testing / Mocking: Di lingkungan pengujian otomatis, modul tertentu sengaja di-stub untuk mengembalikan nil agar tidak ikut berjalan.
  • Defensive Programming: Menjaga aplikasi agar tidak mengalami Null Pointer Exception / crash jika factory method mengembalikan nil.

(Di SAMIR saat ini, seluruh modul konkret mengembalikan instance valid, sehingga guard kedua selalu lolos).

C. Mengapa Arsitektur Fallback Ini Dibuat?

Arsitek 🦊 CZSwiftModuleLib learn/iOS-Arch ↗ merancangnya dengan prinsip Hybrid Architectural Compatibility:

  1. Dukungan Multi-Framework (Future-Ready): Jika suatu hari modul dipisahkan menjadi CocoaPods / Dynamic Framework independen (SamirMainModule.framework), pemanggilan pertama langsung berhasil tanpa perlu mengubah kode CZModuleManager.
  2. Dukungan Monolitik Flat (Saat Ini): Mengingat seluruh file modul saat ini masih tergabung dalam satu target biner aplikasi (IDSamirLoan), fallback Bundle.cz.bundleName menjamin dynamic loading tetap berjalan mulus tanpa runtime error.

3. Pendaftaran Router & Filter Router (CZRouterCenter)

Setiap kali modul berhasil dibuat (registerModule), CZModuleManager mendaftarkan routing modul ke 🦊 CZRouterCenter.shared learn/iOS-Arch ↗:

// CZModuleManager.swift:L131-L141
private func registerRouter(_ module: CZModuleProtocol) {
    if module.responds(to: NSSelectorFromString("routers")) {
        CZRouterCenter.shared.addRouters(module.routers?())
    }
}

private func registerFilterRouter(_ module: CZModuleProtocol) {
    if module.responds(to: NSSelectorFromString("routerFilters")) {
        CZRouterCenter.shared.addFilters(module.routerFilters?())
    }
}

4. Contoh Nyata Penggunaan routers di Production (End-to-End Flow)

Mari ambil contoh nyata: Pengguna menyelesaikan login OTP di Modul Login, lalu diarahkan ke Form Foto KTP di Modul Auth dengan membawa data, kemudian menekan tombol kembali (back).

Langkah 1: Modul Tujuan Mendaftarkan Rute

Di 🦊 IDSamirAuthModule.swift:L25-L46 learn/iOS-Arch ↗:

func routers() -> [CZRouter] {
    let router = CZRouter.initWithSchemes(["samir"], withHostParttern: "auth")
    let routerTable = CZRouterTable()
    let handler = IDSamirAuthModuleRouterHandler()
    
    // Mendaftarkan path /identity ke handler
    routerTable.registerHandler(handler, forPathPattern: IDSamirAuthRouterPath.Identity)
    router?.addRouterTable(routerTable)
    return [router!]
}

5. routerFilters: Mekanisme Aliasing & Usecase di Production

Method 🦊 filterRouterUrl learn/iOS-Arch ↗ menjalankan URL Rewriting / Aliasing:

  1. Memotong bagian basis URL (splitUrl) dari query string (urlParams).
  2. Jika splitUrl ada di kamus filterRouters, basis URL ditukar dengan target URL baru.
  3. Query parameters bawaan disambung kembali di belakangnya.
Usecase di Production:
  1. Backward Compatibility Deep Link Lama (Migrasi URL Promosi):

Jika tim marketing pernah menyebarkan banner promosi dengan link lama samir://old_promo?code=SAMIR2024, dan fitur tersebut kini dialihkan ke tab utama, daftarkan filter ["samir://old_promo": "samir://main/tab"]. Link otomatis di-rewrite menjadi samir://main/tab?code=SAMIR2024 tanpa mematahkan link di perangkat user.

  1. Normalisasi URL Singkat H5 Web Bridge:

Memetakan skema singkat dari script web H5 ke endpoint native yang lebih panjang.

7. Mengapa serviceForProtocol Dibuat dan Seberapa Penting?

A. Kenapa Router Saja Tidak Cukup?

Router sangat ideal untuk navigasi visual antarlayar (membuka ViewController). Namun, router tidak dapat digunakan untuk meminta data balikan bertipe kuat (strong-typed) tanpa UI:

  • "Apakah pengguna sedang login saat ini?" (isLogin() -> Bool)
  • "Berapa nomor HP atau custId pengguna yang sedang aktif?" (loginInfo()?.mobile)
  • "Jalankan fungsi logout token di latar belakang!" (postLoginOutRequest(...))

Jika modul lain langsung mengimpor SamirLoginModule, akan terjadi circular dependency dan pelanggaran arsitektur.

B. Solusi: Service Locator Pattern
  1. Definisi antarmuka protokol dibuat di 🦊 IDServiceManager.swift learn/iOS-Arch ↗:
   public protocol IDLoginModuleServiceProtocol: CZBaseServiceProtocol {
       func isLogin() -> Bool
       func loginInfo() -> IDLoginCodeDataModel?
       func loginAction()
   }
  1. Modul mana pun cukup memanggil fasad:
   let isLogin = IDServiceManager.loginService()?.isLogin() ?? false
  1. Di balik layar, 🦊 CZModuleManager.serviceForProtocol learn/iOS-Arch ↗ mencari class handler di 🦊 IDServiceList.plist learn/iOS-Arch ↗ (IDLoginModuleServiceHandler), menginstansiasinya secara lazy, menyimpannya di cache singleton secara aman via serviceCacheQueue.sync, lalu mengembalikannya sebagai protokol.
C. Seberapa Penting di SAMIR?

Sangat KRUSIAL.

Fasad ini dipanggil lebih dari 80 kali di seluruh layer aplikasi:

  • Flutter Native Channel (🦊 FlutterNativeChannel+method.swift:L35 learn/iOS-Arch ↗): Tab Flutter membaca sesi login native.
  • Pengajuan Pinjaman (🦊 LoanConfirmService.swift:L951 learn/iOS-Arch ↗): Mengambil token autentikasi nasabah.
  • Telemetri & APM (🦊 TYUtils.swift:L39 learn/iOS-Arch ↗): Melampirkan identitas user pada laporan performa.

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Pelanggaran SRP: God Object Coordinator pada Alur Startup

Class modul startup utama pada SAMIR Mobile iOS menangani terlalu banyak tanggung jawab: registrasi APM, inisialisasi jaringan, pemanasan runtime engine, serta registrasi push notifications secara monolitik.

⚠️ Smells 2: Pelanggaran DIP: Keterikatan Statis Singleton (0% Unit Testability)

Komponen memanggil static shared singleton secara langsung tanpa melalui abstraksi antarmuka (Dependency Inversion Principle), membuat pengujian terisolasi di automated unit test menjadi mustahil tanpa memicu efek samping jaringan dan APM produksi.

🚀 Blueprint Refactoring Standar Industri: Penerapan Composite Startup Task Architecture

Memecah alur peluncuran aplikasi menjadi serangkaian task mandiri yang mengimplementasikan protokol tunggal (Open/Closed Principle) dan dapat dieksekusi secara terkoordinasi (sync/async).

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol AppStartupTask {
    var identifier: String { get }
    var executionQueue: TaskExecutionQueue { get }
    func execute(with application: UIApplication, launchOptions: [UIApplication.LaunchOptionsKey: Any]?)
}

public final class AppStartupCoordinator {
    private let tasks: [AppStartupTask]
    public init(tasks: [AppStartupTask]) { self.tasks = tasks }
    
    public func launch(application: UIApplication, options: [UIApplication.LaunchOptionsKey: Any]?) {
        tasks.forEach { $0.execute(with: application, launchOptions: options) }
    }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
