02 — Application Lifecycle

Propagasi Event ke Seluruh Modul

📚 Modul: 02-application-lifecycle 🎯 Scope: SAMIR Mobile (iOS Native UIKit & FChannel) ⏱️ Estimasi: 20 Menit 🏷️ Git Branch: learn/iOS-Arch

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumen ini menjelaskan bagaimana siklus hidup aplikasi (Application Lifecycle) dikelola di SAMIR iOS: peran CZAppDelegate sebagai delegat tunggal UIKit, mekanisme relay event oleh CZModuleManager, dan bagaimana setiap modul bisnis menerima callback lifecycle secara terisolasi tanpa saling ketergantungan.

Status Verifikasi: [Verified] (diverifikasi langsung dari CZAppDelegate.swift, CZModuleManager.swift, dan IDModuleList.plist).

🎯 A. Learning Objective

Setelah mempelajari dokumen ini, pembaca akan mampu:

  1. Memahami arsitektur delegasi siklus hidup: UIApplication -> CZAppDelegate -> CZModuleManager -> [CZModuleProtocol].
  2. Menyebutkan 6 modul bisnis yang terdaftar di IDModuleList.plist dan urutan penerimaan event-nya.
  3. Menjelaskan mengapa modul tidak perlu memodifikasi AppDelegate saat membutuhkan penanganan event sistem (misal: push notification, backgrounding, open URL).
  4. Mengetahui bug/technical debt pada pengurutan prioritas modul di CZModuleManager.swift.

📋 B. Prerequisites

  • Sudah membaca 01-ios-entry-point.md.
  • Memahami protokol standar UIApplicationDelegate pada iOS.

💡 C. Simple Explanation (Analogi Siaran Radio Sentral)

Dalam arsitektur iOS konvensional, file AppDelegate.swift sering kali menjadi "God Object" raksasa beribu-ribu baris karena setiap library dan fitur (Facebook SDK, Firebase, Push Notification, Deep Link, APM) menumpuk kode inisialisasinya di sana.

Di SAMIR iOS, sistem menggunakan analogi Siaran Radio Sentral:

  • CZAppDelegate adalah pemancar sentral yang menangkap sinyal dari sistem operasi iOS (contoh: "Aplikasi baru saja dibuka!", "Ada notifikasi push masuk!", "Pengguna memencet tombol Home").
  • Pemancar ini tidak memproses sinyal sendiri; ia meneruskannya ke manajer modul (CZModuleManager).
  • CZModuleManager menyiarkan sinyal tersebut ke setiap "stasiun radio" modul fitur (IDSamirMainModule, IDSamirLoanModule, dll).
  • Setiap modul menangani sinyal tersebut sesuai urusannya masing-masing tanpa menyentuh kode modul lain.

💻 D. Actual Implementation (Bukti Kode Sumber)

1. CZAppDelegate: Delegat Sentral yang Ramping

Path: 🦊 ios/IDSamirLoan/Application/CZSwiftModuleLib/Classes/CZAppDelegate.swift learn/iOS-Arch ↗

Perhatikan bahwa CZAppDelegate hanya memiliki 88 baris kode! Tidak ada logika bisnis pinjaman di sini. Setiap fungsi delegat hanya meneruskan panggilan ke CZModuleManager.shared:

public class CZAppDelegate: UIResponder, UIApplicationDelegate {
    public lazy var window: UIWindow? = {
        return UIWindow(frame: UIScreen.main.bounds)
    }()

    public func application(_ application: UIApplication, didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey : Any]? = nil) -> Bool {
        return CZModuleManager.shared.application(application, didFinishLaunchingWithOptions: launchOptions)
    }

    public func applicationDidBecomeActive(_ application: UIApplication) {
        CZModuleManager.shared.applicationDidBecomeActive(application)
    }

    public func applicationDidEnterBackground(_ application: UIApplication) {
        CZModuleManager.shared.applicationDidEnterBackground(application)
    }

    public func application(_ application: UIApplication, didRegisterForRemoteNotificationsWithDeviceToken deviceToken: Data) {
        CZModuleManager.shared.application(application, didRegisterForRemoteNotificationsWithDeviceToken: deviceToken)
    }
    // ... metode delegat lainnya
}

2. CZModuleManager: Distribusi Event ke Modul

Path: 🦊 ios/IDSamirLoan/Application/CZSwiftModuleLib/Classes/CZModuleManager.swift learn/iOS-Arch ↗

CZModuleManager menyimpan daftar modul terdaftar di dalam array moduleContextArray: [CZModuleContext]. Ketika menerima event dari CZAppDelegate, ia melakukan perulangan (looping) ke semua modul:

public func application(_ application: UIApplication, didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey : Any]? = nil) -> Bool {
    var result = true
    for context in moduleContextArray {
        if context.moduleObject?.responds(to: #selector(application(_:didFinishLaunchingWithOptions:))) == true {
            let moduleResult = context.moduleObject?.application?(application, didFinishLaunchingWithOptions: launchOptions) ?? true
            if !moduleResult { result = false }
        }
    }
    return result
}

⚖️ F. Why It Matters: Audit Bug Prioritas Modul (CZModuleManager)

Saat melakukan analisis mendalam terhadap source code 🦊 ios/IDSamirLoan/Application/CZSwiftModuleLib/Classes/CZModuleManager.swift learn/iOS-Arch ↗, ditemukan sebuah anomali implementasi (technical debt):

// CZModuleManager.swift:L87-92
var moduleContext: CZModuleContext = CZModuleContext()
moduleContext.moduleClass = moduleClass
moduleContext.moduleName = NSStringFromClass(moduleClass)
moduleContext.moduleObject = moduleObject
// PERHATIAN: Nilai moduleContext.modulePriority TIDAK PERNAH disetel dari moduleObject.loadPriority!
moduleContextArray.append(moduleContext)

Pada baris 75:

moduleContextArray.sort { $0.modulePriority.rawValue > $1.modulePriority.rawValue }

Karena struct CZModuleContext menginisialisasi modulePriority dengan nilai default .normal (0), dan registerModule lupa memindahkan nilai moduleObject.loadPriority ke moduleContext.modulePriority, maka seluruh modul memiliki prioritas yang sama (.normal).

Akibatnya, fungsi sorting di atas menjadi no-op (tidak berpengaruh). Urutan eksekusi modul murni ditentukan oleh urutan dictionary yang dikembalikan oleh NSDictionary(contentsOf: url!) saat membaca IDModuleList.plist.

Untungnya: IDSamirMainModule tetap dieksekusi pertama kali di sebagian besar build karena posisinya di urutan pertama dictionary plist, namun ini adalah celah kerapuhan yang harus dipahami oleh senior engineer.

🔬 G. Practical Example (Menambahkan Penanganan Lifecycle di Modul Baru)

Jika tim developer ingin menambahkan modul analitik baru yang harus membersihkan cache setiap kali aplikasi masuk background:

  1. Buat class baru yang mengadopsi protokol CZModuleProtocol.
  2. Implementasikan method applicationDidEnterBackground(_:) di dalam class tersebut.
  3. Daftarkan class tersebut di IDModuleList.plist.
  4. Anda tidak perlu mengubah satu baris pun di CZAppDelegate.swift! Modul Anda akan otomatis menerima panggilan background saat aplikasi berjalan.

⚠️ H. Common Mistakes & Debugging

  • Typo Nama Class di Plist:
  • Jika nama class di IDModuleList.plist salah ketik (misal IDSamirAuthModuleX), NSClassFromString akan mengembalikan nil. Registrasi gagal secara diam-diam (silent failure) tanpa pesan error yang jelas.
  • Mengira SamirLoginModule Terdaftar di Lifecycle:
  • SamirLoginModule tidak menerima event didFinishLaunchingWithOptions. Jangan menaruh kode inisialisasi lifecycle di folder login!

🏛️ Bagian 2: Architecture Lab, SOLID Audit & Retention Quizzes

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Pelanggaran SRP: God Object Coordinator pada Alur Startup

Class modul startup utama pada SAMIR Mobile iOS menangani terlalu banyak tanggung jawab: registrasi APM, inisialisasi jaringan, pemanasan runtime engine, serta registrasi push notifications secara monolitik.

⚠️ Smells 2: Pelanggaran DIP: Keterikatan Statis Singleton (0% Unit Testability)

Komponen memanggil static shared singleton secara langsung tanpa melalui abstraksi antarmuka (Dependency Inversion Principle), membuat pengujian terisolasi di automated unit test menjadi mustahil tanpa memicu efek samping jaringan dan APM produksi.

🚀 Blueprint Refactoring Standar Industri: Penerapan Composite Startup Task Architecture

Memecah alur peluncuran aplikasi menjadi serangkaian task mandiri yang mengimplementasikan protokol tunggal (Open/Closed Principle) dan dapat dieksekusi secara terkoordinasi (sync/async).

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol AppStartupTask {
    var identifier: String { get }
    var executionQueue: TaskExecutionQueue { get }
    func execute(with application: UIApplication, launchOptions: [UIApplication.LaunchOptionsKey: Any]?)
}

public final class AppStartupCoordinator {
    private let tasks: [AppStartupTask]
    public init(tasks: [AppStartupTask]) { self.tasks = tasks }
    
    public func launch(application: UIApplication, options: [UIApplication.LaunchOptionsKey: Any]?) {
        tasks.forEach { $0.execute(with: application, launchOptions: options) }
    }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
