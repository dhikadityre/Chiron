03 — Startup Sequence & Initial Routing

Dari Ikon ke Layar Utama

📚 Modul: 03-startup-sequence-and-initial-routing 🎯 Scope: SAMIR Mobile (iOS Native UIKit & FChannel) ⏱️ Estimasi: 20 Menit 🏷️ Git Branch: learn/iOS-Arch

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumen ini membedah secara kronologis proses startup di dalam IDSamirMainModule, logika penentuan apakah splash screen ditampilkan atau dilewati (checkAppStartHide), inisialisasi SDK pihak ketiga, hingga penyusunan IDMainTabBarController.

Status Verifikasi: [Verified] (diverifikasi langsung dari IDSamirMainModule.swift, IDLaunchViewController.swift, dan IDMainTabBarController.swift).

🎯 A. Learning Objective

Setelah mempelajari dokumen ini, pembaca akan mampu:

  1. Menjelaskan 11 tahapan inisialisasi yang dijalankan di dalam IDSamirMainModule.application(_:didFinishLaunchingWithOptions:).
  2. Memahami bagaimana checkAppStartHide menentukan apakah user melihat IDLaunchViewController (countdown 3s) atau langsung masuk ke IDMainTabBarController.
  3. Menjelaskan bagaimana request konfigurasi aplikasi (app-configuration) diambil pada applicationDidBecomeActive untuk memperbarui pengaturan startup berikutnya.
  4. Memahami mekanisme eksekusi deep link tertunda (pending deep link) setelah peluncuran selesai.

📋 B. Prerequisites

  • Sudah membaca 01-ios-entry-point.md dan 02-application-lifecycle.md.
  • Mengetahui konsep UIWindow dan rootViewController pada UIKit.

💡 C. Simple Explanation (Analogi Masuk ke Toko Perhiasan)

Bayangkan Anda mengunjungi toko perhiasan:

  1. Pintu otomatis terbuka (didFinishLaunchingWithOptions).
  2. Petugas mengaktifkan pendingin ruangan dan kamera keamanan (Environment, Jaringan, Flutter Engine dihidupkan di latar belakang).
  3. Di depan pintu ada papan iklan promosi berdurasi 3 detik (IDLaunchViewController).
  • Jika Anda adalah pelanggan VIP yang sudah pernah menyetel opsi "Lewati Iklan" di kunjungan sebelumnya (APP_Start_Hide == "1"), papan iklan langsung disingkirkan.
  • Jika papan iklan aktif, Anda bisa menunggu 3 detik atau menekan tombol "Lewati".
  1. Pintu lobi utama terbuka penuh, menampilkan 3 etalase utama (IDMainTabBarController: Etalase Pinjaman, Etalase Tagihan, dan Meja Layanan Nasabah).
  2. Jika Anda datang karena membawa kupon khusus dari luar (Deep Link), staf toko langsung mengantar Anda ke etalase yang tertera di kupon tersebut.

    initTiktok()

    return true

2. Logika Pemilihan Layar Awal (`initWindow` & `checkAppStartHide`)

Path: 🦊 ios/IDSamirLoan/Application/SamirMainModule/Classes/IDModule/IDSamirMainModule.swift learn/iOS-Arch ↗

private func initWindow(_ application: UIApplication) {
    if let window = application.delegate?.window {
        window?.backgroundColor = .white
        if checkAppStartHide() {
            changeMainRootViewController(window: window)
        } else {
            changeLaunchViewController(window: window)
        }
    }
}

func checkAppStartHide() -> Bool {
    // 1. Periksa cache lokal di UserDefaults
    if let startHide = UserDefaults.standard.string(forKey: "APP_Start_Hide") {
        if startHide == "1" { return true }
        return false
    }
    // 2. Periksa cache konfigurasi server jika ada
    guard let appStartHide = IDServiceManager.mainService()?.getAppConfig()?.appStartHide else {
        return false
    }
    return appStartHide == "1"
}

Jika checkAppStartHide() == false, aplikasi memasang 🦊 IDLaunchViewController.swift learn/iOS-Arch ↗. Controller ini memulai hitung mundur 3 detik dengan tombol "Lewati Ns".

Saat hitung mundur selesai atau tombol ditekan, protokol IDLaunchViewProtocol.finishLaunch() dipanggil untuk mengganti root menjadi IDMainTabBarController().

3. Siklus `applicationDidBecomeActive` (Sinkronisasi Server)

Path: 🦊 ios/IDSamirLoan/Application/SamirMainModule/Classes/IDModule/IDSamirMainModule.swift learn/iOS-Arch ↗

public func applicationDidBecomeActive(_ application: UIApplication) {
    // Mengambil app-configuration terbaru tanpa tanda tangan (unsigned)
    IDMainManager.shared.requestAppConfig()
    AppConfigUtil.shared.requestConfig()

    IDAppsFlyerManager.shared.applicationDidBecomeActive(application)
    AppEvents.shared.activateApp()
    IDCustomPointManager.refreshConfig()
}

API endpoint app-configuration mengembalikan parameter global seperti appStartHide, nomor WhatsApp CS, tautan FAQ, dan konfigurasi A/B test login. Nilai appStartHide langsung disimpan ke UserDefaults.standard.set(..., forKey: "APP_Start_Hide") sehingga start berikutnya dapat langsung melewati splash.

🪜 E. Step-by-Step Walkthrough: Alur Lengkap dari Peluncuran Hingga Main Tab

📊 Diagram Alur #1
sequenceDiagram participant OS as iOS System participant Main as IDSamirMainModule participant FEng as FlutterEngineManager participant Launch as IDLaunchViewController participant Tab as IDMainTabBarController participant Deep as Deep Link Processor OS->>Main: application(_:didFinishLaunchingWithOptions:) Main->>FEng: prewarm() (Jalankan FlutterEngine single instance) Main->>Main: checkAppStartHide() alt appStartHide == "1" (Sudah di-cache) Main->>Tab: window.rootViewController = IDMainTabBarController() else appStartHide == "0" / Belum ada cache Main->>Launch: window.rootViewController = IDLaunchViewController() Note over Launch: Hitung mundur 3 detik / User tap "Lewati" Launch-->>Main: finishLaunch() dipanggil Main->>Tab: window.rootViewController = IDMainTabBarController() end Tab->>Tab: installPersistentFlutterHost() & viewDidLoad() Main->>Deep: Proses deep link tertunda (Samir_DeepLink_Str) jika ada
  1. Inisialisasi Dasar: Environment dimuat, jaringan disiapkan, dan FlutterEngineManager.shared.prewarm() mem-booting single runtime engine Flutter agar siap pakai.
  2. Evaluasi Tampilan Awal: Sistem memeriksa kunci APP_Start_Hide.
  3. Penyajian Splash: Jika belum disetel skip, layar splash tampil 3 detik.
  4. Transisi ke Tab Bar: Root window diganti ke IDMainTabBarController. TabBar memasang 3 tab native dan meng-embed view kontainer persisten Flutter di bawah tab bar.
  5. Eksekusi Deep Link Tertunda: Jika aplikasi dibuka melalui link atribusi AppsFlyer saat aplikasi dalam kondisi mati (cold start), link disimpan sementara di UserDefaults (Samir_DeepLink_Str) dan baru didispatch ke router setelah finishLaunch() selesai!

⚖️ F. Why It Matters (Trade-Offs & Catatan Arsitektur)

  • Mengapa Prewarm Flutter Dilakukan di Startup?

Memulai FlutterEngine membutuhkan waktu komputasi (spin up Dart VM sekitar 200–400ms). Dengan memanggil FlutterEngineManager.shared.prewarm() saat startup native, pengguna tidak akan merasakan lag atau kedipan layar kosong ketika mereka berpindah ke Tab Tagihan atau Tab Saya.

  • Mengapa Request app-configuration Ditaruh di applicationDidBecomeActive?

Setiap kali aplikasi kembali dari background ke foreground, status konfigurasi server (misal: penonaktifan darurat atau pembaruan nomor kontak darurat) harus selalu terbarui tanpa mengharuskan pengguna me-restart aplikasi.

🔬 G. Practical Example (Studi Kasus Penanganan Deep Link Cold Start)

Misalkan pengguna mengklik link promosi SMS samir://repay/historyOrder saat aplikasi sedang mati:

  1. iOS membangunkan aplikasi via open url.
  2. IDSamirMainModule.handleDeepLink menerima link tersebut.
  3. Karena tab bar belum siap dan user belum tentu login, link disimpan di UserDefaults.standard.set(link, forKey: "Samir_DeepLink_Str").
  4. Setelah finishLaunch() selesai dan pengguna terverifikasi login, method changeMainRootViewController membaca kembali cache tersebut dan mengeksekusi IDRouterManager.id_perfromWithURLString(...) untuk mengantar user langsung ke riwayat pinjaman.

⚠️ H. Common Mistakes & Debugging

  • Splash Screen Terus Muncul Berulang Kali di Staging:
  • Penyebab: Endpoint app-configuration di environment TEST mengembalikan appStartHide = "0" atau gagal terhubung.
  • Pengecekan: Periksa isi UserDefaults.standard.string(forKey: "APP_Start_Hide").
  • Flutter Tab Berkedip Hitam / Putih Saat Pertama Kali Dibuka:
  • Penyebab: FlutterEngineManager.shared.prewarm() gagal atau belum selesai dipanggil sebelum tab diakses. Pastikan pemanggilan prewarm() tetap berada di baris 59 IDSamirMainModule.swift.

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Pelanggaran SRP: God Object Coordinator pada Alur Startup

Class modul startup utama pada SAMIR Mobile iOS menangani terlalu banyak tanggung jawab: registrasi APM, inisialisasi jaringan, pemanasan runtime engine, serta registrasi push notifications secara monolitik.

⚠️ Smells 2: Pelanggaran DIP: Keterikatan Statis Singleton (0% Unit Testability)

Komponen memanggil static shared singleton secara langsung tanpa melalui abstraksi antarmuka (Dependency Inversion Principle), membuat pengujian terisolasi di automated unit test menjadi mustahil tanpa memicu efek samping jaringan dan APM produksi.

🚀 Blueprint Refactoring Standar Industri: Penerapan Composite Startup Task Architecture

Memecah alur peluncuran aplikasi menjadi serangkaian task mandiri yang mengimplementasikan protokol tunggal (Open/Closed Principle) dan dapat dieksekusi secara terkoordinasi (sync/async).

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol AppStartupTask {
    var identifier: String { get }
    var executionQueue: TaskExecutionQueue { get }
    func execute(with application: UIApplication, launchOptions: [UIApplication.LaunchOptionsKey: Any]?)
}

public final class AppStartupCoordinator {
    private let tasks: [AppStartupTask]
    public init(tasks: [AppStartupTask]) { self.tasks = tasks }
    
    public func launch(application: UIApplication, options: [UIApplication.LaunchOptionsKey: Any]?) {
        tasks.forEach { $0.execute(with: application, launchOptions: options) }
    }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
