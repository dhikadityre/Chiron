01 — iOS Entry Point

main.swift & Bootstrapping Awal

📚 Modul: 01-ios-entry-point 🎯 Scope: SAMIR Mobile (iOS Native UIKit & FChannel) ⏱️ Estimasi: 20 Menit 🏷️ Git Branch: learn/iOS-Arch

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumen ini menjelaskan baris kode pertama yang dieksekusi saat aplikasi SAMIR iOS dihidupkan oleh sistem operasi iOS: file main.swift, inisialisasi APM Tingyun sebelum runtime UIApplication berjalan, dan peralihan ke CZModuleHandler.

Status Verifikasi: [Verified] (diverifikasi langsung dari ios/IDSamirLoan/main.swift dan ios/IDSamirLoan/Application/main.m).

🎯 A. Learning Objective

Setelah mempelajari dokumen ini, pembaca akan mampu:

  1. Menunjukkan file titik masuk (entry point) sebenarnya di aplikasi SAMIR iOS.
  2. Memahami peran ApplicationLauncher dalam mengonfigurasi APM Tingyun di dalam autoreleasepool.
  3. Menjelaskan mengapa CZModuleHandler.ModuleManagerApplicationMain menggantikan pemanggilan standar @main atau UIApplicationMain.
  4. Mengidentifikasi bahwa Application/main.m adalah file mati (dead code) yang sepenuhnya dikomentari.

📋 B. Prerequisites

  • Sudah menyelesaikan kurikulum Level 1: Project Foundation.
  • Mengetahui konsep siklus hidup proses Unix / C (argc, argv, main() function) dan UIApplicationMain.

💡 C. Simple Explanation (Analogi Sakelar Utama Gedung)

Sebelum lampu, pendingin ruangan, dan lift di sebuah gedung dinyalakan:

  1. Petugas keamanan menyalakan generator darurat dan kamera CCTV terlebih dahulu (Tingyun APM diinisialisasi untuk memantau performa dan mendeteksi crash sejak detik ke-0).
  2. Manajer gedung membuka buku catatan daftar staf dan divisi yang bertugas hari ini (CZModuleManager membaca IDModuleList.plist dan IDServiceList.plist).
  3. Setelah semua divisi terdaftar, pintu utama gedung dibuka untuk umum (UIApplicationMain dihidupkan dengan CZAppDelegate).

Di SAMIR iOS, urutan ini diatur dengan sangat ketat di file main.swift.

2. Implementasi CZModuleHandler

Path: 🦊 ios/IDSamirLoan/Application/CZSwiftModuleLib/Classes/CZModuleHandler.swift learn/iOS-Arch ↗

public class CZModuleHandler: NSObject {
    public class func ModuleManagerApplicationMain(
        _ argc: Int32,
        argv: UnsafeMutablePointer<UnsafeMutablePointer<CChar>?>,
        moduleConfigurationFileName moduleFileName: String,
        serviceConfigurationFileName serviceFileName: String
    ) -> Int32 {
        // 1. Daftarkan seluruh modul dan service SEBELUM UIApplicationMain berjalan
        CZModuleManager.shared.setup(moduleFileName, servicePlistFileName: serviceFileName)
        
        // 2. Daftarkan CZAppDelegate sebagai delegat utama aplikasi
        let delegateClassName = NSStringFromClass(CZAppDelegate.self)
        
        // 3. Serahkan kendali ke UIKit loop
        return UIApplicationMain(argc, argv, nil, delegateClassName)
    }
}

3. Mengapa main.swift Dibaca Pertama Kali oleh Xcode? (Pertanyaan Kritis)

Banyak developer terbiasa dengan atribut @main atau @UIApplicationMain pada AppDelegate.swift. Mengapa di proyek ini file main.swift dieksekusi pertama kali?

  1. Aturan Standar Kompiler Swift untuk Entry Point:
  • Dalam bahasa Swift, file bernama khusus main.swift adalah satu-satunya file yang diizinkan memiliki ekspresi kode tingkat atas (top-level code execution).
  • Saat Swift compiler mengompilasi file-file biner, compiler otomatis menghasilkan fungsi entry point C standar int main(int argc, char *argv[]) di level Mach-O binary (LC_MAIN) yang langsung mengarahkan instruksi CPU pertama ke baris-baris teratas di dalam main.swift.
  1. Komentar Eksperimen @main:

Di baris 11-16 main.swift, terlihat developer pernah mencoba pola baru:

   //@main
   //struct IDSamirLoan {
   //    static func main() { ... }
   //}

Struktur ini dikomentari. Jika @main diaktifkan berdampingan dengan main.swift, compiler Swift akan melempar error konflik duplicate entry point.

  1. Apakah Benar main.swift yang Di-hit Pertama Kali?:

BENAR 100%. Begitu kernel iOS dan dynamic loader (dyld) selesai me-load binary aplikasi ke memori, kontrol eksekusi langsung masuk ke baris 35 main.swift:

   autoreleasepool {
       ApplicationLauncher.performLaunchSetup() // Inisialisasi APM Tingyun
   }
   let _ = CZModuleHandler.ModuleManagerApplicationMain(...)

Ini terjadi sebelum UIApplicationMain hidup dan sebelum CZAppDelegate.application(_:didFinishLaunchingWithOptions:) dipanggil!

  1. Proses Pengambilan Nilai di CZModuleManager.swift:L62-78:
   private func registerAllModules(_ plistFileName: String) {
       // 1. Temukan URL file plist di Main Bundle aplikasi
       let url = Bundle.main.url(forResource: plistFileName, withExtension: "plist")
       assert(url != nil, "App Missing Module Configuration File")
       
       // 2. Baca isi file plist ke Dictionary [String: String]
       if let contents = NSDictionary(contentsOf: url!) as? [String: String] {
           for (moduleName, className) in contents {
               // 3. Lakukan refleksi dinamis via NSClassFromString
               if registerModule("\(moduleName).\(className)") == false {
                   let _ = registerModule(Bundle.cz.bundleName + ".\(className)")
               }
           }
       }
   }
  • Key Plist: Nama Modul/Namespace (misal: SamirMainModule).
  • Value Plist: Nama Class Swift konkret (misal: IDSamirMainModule).
  • Objek modul kemudian diinstansiasi secara dinamis menggunakan (moduleClass as! CZModuleProtocol.Type).create().

🪜 E. Step-by-Step Walkthrough (Alur Eksekusi Entry Point)

📊 Diagram Alur #1
sequenceDiagram participant OS as iOS Kernel / Dyld participant Main as main.swift participant TY as Tingyun APM (TYUtils) participant MH as CZModuleHandler participant MM as CZModuleManager participant App as UIApplicationMain (CZAppDelegate) OS->>Main: Panggil main() executable binary Main->>TY: autoreleasepool -> ApplicationLauncher.performLaunchSetup() TY-->>Main: APM Aktif (App ID Test/Prod disetel) Main->>MH: CZModuleHandler.ModuleManagerApplicationMain(...) MH->>MM: CZModuleManager.shared.setup("IDModuleList", "IDServiceList") Note over MM: Membaca plist & instansiasi modul via NSClassFromString MM-->>MH: Modul & Service siap di memory MH->>App: UIApplicationMain(argc, argv, nil, "CZAppDelegate") Note over App: Main RunLoop dimulai & window diinisialisasi
  1. Step 1 — OS Kernel: Dyld meload binary aplikasi ke memori dan mengeksekusi instruksi top-level di main.swift.
  2. Step 2 — Inisialisasi APM: ApplicationLauncher.performLaunchSetup() dieksekusi di dalam autoreleasepool. SDK Tingyun mendeteksi apakah aplikasi berjalan di environment TEST atau PROD untuk menentukan App ID pelaporan performa.
  3. Step 3 — Registrasi Modul & Service: CZModuleHandler.ModuleManagerApplicationMain dipanggil dengan parameter nama file konfigurasi: "IDModuleList" dan "IDServiceList".
  4. Step 4 — Setup Singleton CZModuleManager: CZModuleManager.shared.setup(...) membaca plist konfigurasi, menginstansiasi class modul menggunakan NSClassFromString, dan mendaftarkan URL router masing-masing modul.
  5. Step 5 — Serah Terima ke UIKit: UIApplicationMain dipanggil dengan meneruskan nama class CZAppDelegate. Dari titik ini, UIKit mengambil alih siklus hidup aplikasi.

⚖️ F. Why It Matters (Trade-Offs & Catatan Arsitektur)

  • Mengapa Modul Harus Terdaftar Sebelum UIApplicationMain?

Jika modul baru didaftarkan di dalam application(_:didFinishLaunchingWithOptions:), ada risiko modul prioritas tinggi terlambat menerima notifikasi peluncuran sistem atau parameter peluncuran (launchOptions). Mendaftarkannya di CZModuleHandler menjamin saat CZAppDelegate pertama kali menerima event sistem, seluruh modul sudah berada dalam keadaan siap menerima panggilan.

  • Mengapa Tingyun Dijalankan di Luar UIKit RunLoop?

Jika terjadi crash sangat awal (misalnya kegagalan alokasi memori pada dynamic loader atau error saat membaca bundle plist), APM Tingyun sudah aktif dan mampu mencatat crash tersebut sebelum aplikasi terhenti.

🔬 G. Practical Example (Studi Kasus)

Jika seorang developer ingin menambahkan tracking performa baru yang harus berjalan sebelum tampilan apa pun dimuat, lokasi yang tepat untuk meletakkannya adalah di ApplicationLauncher.performLaunchSetup() di dalam main.swift. Namun, developer tidak boleh melakukan operasi berat (seperti request jaringan synchronous) di file ini karena sistem operasi iOS akan mematikan aplikasi (watchdog timeout) jika proses startup memakan waktu lebih dari beberapa detik.

⚠️ H. Common Mistakes & Debugging

  • Crash Fatal Saat Boot:
  • Gejala: Aplikasi langsung crash sesaat setelah splash screen muncul (sebelum UI sempat dirender).
  • Penyebab: Typo pada nama class di IDModuleList.plist atau assertion gagal di CZModuleManager.setup().
  • File yang harus diperiksa: ios/IDSamirLoan/Application/Configuration/Module/IDModuleList.plist dan breakpoint di CZModuleManager.registerAllModules.
  • Menghapus environment_preprocess.h:
  • File ini dihasilkan otomatis oleh skrip build. Jika hilang, jalankan Scheme IDSamirEnvironment atau build skema apa pun sekali lagi untuk membuatnya kembali.

🏛️ Bagian 2: Architecture Lab, SOLID Audit & Retention Quizzes

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Pelanggaran SRP: God Object Coordinator pada Alur Startup

Class modul startup utama pada SAMIR Mobile iOS menangani terlalu banyak tanggung jawab: registrasi APM, inisialisasi jaringan, pemanasan runtime engine, serta registrasi push notifications secara monolitik.

⚠️ Smells 2: Pelanggaran DIP: Keterikatan Statis Singleton (0% Unit Testability)

Komponen memanggil static shared singleton secara langsung tanpa melalui abstraksi antarmuka (Dependency Inversion Principle), membuat pengujian terisolasi di automated unit test menjadi mustahil tanpa memicu efek samping jaringan dan APM produksi.

🚀 Blueprint Refactoring Standar Industri: Penerapan Composite Startup Task Architecture

Memecah alur peluncuran aplikasi menjadi serangkaian task mandiri yang mengimplementasikan protokol tunggal (Open/Closed Principle) dan dapat dieksekusi secara terkoordinasi (sync/async).

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol AppStartupTask {
    var identifier: String { get }
    var executionQueue: TaskExecutionQueue { get }
    func execute(with application: UIApplication, launchOptions: [UIApplication.LaunchOptionsKey: Any]?)
}

public final class AppStartupCoordinator {
    private let tasks: [AppStartupTask]
    public init(tasks: [AppStartupTask]) { self.tasks = tasks }
    
    public func launch(application: UIApplication, options: [UIApplication.LaunchOptionsKey: Any]?) {
        tasks.forEach { $0.execute(with: application, launchOptions: options) }
    }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
