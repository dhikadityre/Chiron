📌 1. Ikhtisar & Koreksi Konseptual

Di aplikasi SAMIR Mobile iOS, sekilas terlihat seolah-olah Native dan Flutter sama-sama memiliki bottom navigation bar (TabBar). Namun pada implementasi sebenarnya:

Fakta Arsitektur: Hanya ada 1 TabBar fisik di layar, yaitu Native UITabBar.

Aplikasi menggunakan pola arsitektur Single Persistent Flutter Host (Overlay Pattern):

  • UITabBarController Native bertindak sebagai master container utama dengan 3 tab item:
    • Tab 0: IDHomeViewController (Native UIKit murni)
    • Tab 1: IDRepayViewController (Native Sentinel / Placeholder VC)
    • Tab 2: IDMineViewController (Native Sentinel / Placeholder VC)
  • Instance Tunggal FlutterEngine & SamirFlutterViewController dijalankan sejak awal aplikasi (prewarmed).
  • View Flutter tersebut diletakkan di dalam flutterContainerView dan disisipkan di atas view native tetapi tepat di bawah tabBar: 
  view.insertSubview(flutterContainerView, belowSubview: tabBar)
  view.bringSubviewToFront(tabBar)
  • Di sisi Flutter, halamannya tidak merender bottom navigation bar tersendiri, melainkan menampilkan kontainer IndexedStack yang memuat MineHomePage (/mine) dan RepayHomePage (/repay).

📌 3. Pembedahan showRoot vs showPage

Dua method ini memiliki tanggung jawab arsitektural yang berbeda secara mendasar:

                          ┌───────────────────────────┐
                          │   FlutterEngineManager    │
                          └─────────────┬─────────────┘
                                        │
                 ┌──────────────────────┴──────────────────────┐
                 ▼                                             ▼
       showRoot(route, reqId)                      showPage(route, "push")
       ──────────────────────                      ───────────────────────
       • Ganti Tab Root Flutter                    • Buka Sub-Halaman Baru
       • Target: IndexedStack                      • Target: Navigator Stack
       • Sinkron (tunggu frameReady)               • Asinkron (Fire & Forget)
       • requestID anti race-condition             • TabBar native disembunyikan
       • TabBar native tetap tampil                • Contoh: /mine/personal
       • Contoh: /mine atau /repay

A. FlutterEngineManager.shared.showRoot

Digunakan ketika user menekan tab bar native (Tagihan atau Saya).

  1. Tidak Menumpuk History: Mengubah FlutterRootController.selectedPath di Flutter yang memicu render pada IndexedStack.
  2. Anti-Flicker (frameReady): Native tidak langsung menampilkan view Flutter. Flutter merender frame terlebih dahulu: 
   WidgetsBinding.instance.ensureVisualUpdate();
   await WidgetsBinding.instance.endOfFrame;

Setelah frame selesai digambar GPU, Flutter membalas { frameReady: true, requestId: id }. Baru saat itulah flutterContainerView.isHidden = false dipasang di native.

  1. Anti-Race Condition (requestID): Menggunakan monotonic integer counter statis nextFlutterRootRequestID. Jika user menekan Tagihan → Saya → Tagihan dalam tempo kilat, respons render dari tab "Saya" yang datang terlambat akan ditolak karena ID-nya tidak cocok dengan flutterRootRequestID aktif.

B. FlutterEngineManager.shared.showPage

Digunakan saat native ingin membuka sub-halaman formulir/detail di Flutter:

host.showFlutterPage("/mine/personal", presentation: "push")
  1. Navigasi Stack: Memanggil Routers.push(route) di Flutter.
  2. Otomatis Sembunyikan TabBar: NativeRouteChrome di Flutter mendeteksi perpindahan ke rute non-root, lalu mengirim channel event setNativeTabBarHidden(true). Native mengubah tabBar.isHidden = true dan memperluas frame Flutter menjadi layar penuh (view.bounds).
  3. Nilai presentation:
    • "push" (default): Animasi slide horizontal standar ke stack navigator.
    • "replace": Menggantikan halaman saat ini (Routers.go) tanpa menumpuk tombol Back.

C. 💡 Mental Model Kunci: Analogi hidesBottomBarWhenPushed iOS Native

Cara paling sederhana dan intuitif memahami perbedaan ini dari sudut pandang iOS Engineer:

Ringkasan Mental Model:

  • showRoot (Mode Tab): Karena pengguna masih berada di level tab utama, mereka masih membutuhkan TabBar native untuk berpindah tab → TabBar TIDAK di-hide, dan tinggi layar Flutter dibatasi tepat di atas TabBar.
  • showPage (Mode Halaman Anak / Full-Screen): Pengguna masuk ke halaman detail/formulir, sehingga ekspektasi UX adalah tampilan layar penuh → TabBar native WAJIB di-hide, dan frame Flutter diperluas 100% memenuhi layar (view.bounds). Navigasi kembali diserahkan ke tombol Back di AppBar.

Pada aplikasi iOS UIKit konvensional, perilaku showPage ini setara persis dengan menyetel:

childViewController.hidesBottomBarWhenPushed = true

Namun karena Flutter berjalan di atas satu View Controller persisten yang sama (Single Persistent Flutter Host), efek tersebut disimulasikan secara dinamis melalui sinyal Platform Channel setNativeTabBarHidden = true.

📌 6. Peta Komunikasi Lengkap (Navigasi Dua Arah)

A. Native → Flutter

  1. Tab Switch: IDMainTabBarController.switchFlutterRoot(to:) → FlutterEngineManager.showRoot → MethodChannel "showFlutterRoute" (presentation: "root").
  2. Sub-Page Navigation: IDSamirMineRouterHandler → IDMainTabBarController.showFlutterPage → MethodChannel "showFlutterRoute" (presentation: "push").
  3. Data Refresh Signals: FlutterEngineManager.refreshMineHome() & refreshRepayHome().

B. Flutter → Native

  1. Buka Rute Native / Scheme / External: FlutterNativeChannelRoute.openNativeRoute(url, params) → FlutterNativeChannel+route.swift mengevaluasi:
    • External URL / Medsos: UIApplication.shared.open
    • Layanan H5 Web: IDBusinessWebViewController.loadUrlWithAuth
    • Aksi Native: customerAction, repayLoginAction, jumpDisclaimerPopup
    • Native Router Scheme: IDRouterManager.id_perfromWithURLString
  2. Tutup Halaman Flutter: FlutterNativeChannelRoute.closeFlutterPage() → Native memanggil topViewController?.navigationController?.popViewController() atau dismiss().
  3. Kontrol TabBar: FlutterNativeChannelRoute.setNativeTabBarHidden(hidden).

📌 7. Gotchas & Debugging Checklist

  1. TabBar Hilang Setelah Kembali dari Flutter:
    • Penyebab: Callback observer di Flutter tidak terpanggil atau route name tidak terdaftar di RootRoutes.tabPaths.
    • Mitigasi: Pastikan rute root terdaftar di RootRoutes.paths dan panggil prepareNativeChromeForTabSelection() setiap kali tab native dipilih.
  2. Layar Flutter Kosong (Blank/Stuck):
    • Penyebab: Lifecycle engine masih dalam status inactive atau request ID tidak sinkron dengan response completion.
    • Mitigasi: Periksa apakah FlutterEngineManager.shared.resume() dipanggil sebelum showFlutterRoute.
  3. Safe Area Inset Terpotong:
    • Penyebab: Perhitungan safe area guide native tidak dikirim ke Flutter saat tinggi tab bar berubah.
    • Mitigasi: Verifikasi fungsi updatePersistentSafeArea(top:bottom:) di SamirFlutterViewController.

📌 8. Pembedahan Teknis Engine & Host Invariants (Deep Dive Inisialisasi)

Bagian ini merangkum pembedahan teknis mendalam terhadap detail konfigurasi dan runtime yang sering menjadi pertanyaan arsitektur pada FlutterEngineManager.swift dan pubspec.yaml:

A. Mengapa Bundle Identifier Flutter Berbeda? (iosBundleIdentifier di pubspec.yaml)

Pada file flutter/pubspec.yaml:

  module:
    androidX: true
    androidPackage: com.sahabatmikro.flutter_module
    iosBundleIdentifier: com.sahabatmikro.flutterModule
  • Identitas Modul Add-to-App: Properti module: menegaskan bahwa proyek Flutter ini adalah embedded module, bukan aplikasi mandiri (standalone).
  • Kompilasi Wrapper iOS (.ios/): Saat Flutter toolchain membangun wrapper CocoaPods di direktori ephemeral .ios/, nilai com.sahabatmikro.flutterModule disematkan sebagai CFBundleIdentifier resmi untuk modul framework Flutter tersebut.
  • Mencegah Tabrakan Bundle ID: Identifier ini sengaja dibedakan dari Bundle ID aplikasi native utama (IDSamirLoan) agar tidak terjadi konflik identitas (bundle collision) di sistem build Apple/Xcode saat framework diintegrasikan melalui podhelper.rb di ios/Podfile.

B. Misteri "samir_single_flutter_engine": Mengapa Tidak Ditemukan di Flutter?

Pada file FlutterEngineManager.swift:

private let engine = FlutterEngine(name: "samir_single_flutter_engine")
  • Host-Side Identifier (Native Runtime): String ini merupakan parameter konstruktor bawaan FlutterEngine(name: String) dari framework resmi iOS (FlutterEngine.h).
  • Hanya Berlaku di Sisi Native iOS: String ini tidak pernah dikirim atau diekspos ke isolate Dart / proyek Flutter.
  • Tujuan Utama:
    • Thread Profiling & Tracing: Engine C++ Flutter menggunakannya untuk menamai thread internal (seperti io.flutter.1.ui) saat diinspeksi pada Xcode Debugger, Instruments, dan pelaporan crash log.
    • Identitas di Cache: Menjadi identifier pembeda jika aplikasi menggunakan FlutterEngineCache atau multi-engine. Di SAMIR, penamaan ini menegaskan pola arsitektur Single Shared Engine.

C. Anatomi SamirFlutterViewController: Mengapa Terlihat "Empty View"?

Pada file FlutterEngineManager.swift:

public final class SamirFlutterViewController: FlutterViewController
  • Bukan Empty View: Terlihat kosong pada kode Swift karena ia tidak menambahkan komponen UIKit standar (UILabel, UIButton, dll). Seluruh konten visual digambar langsung oleh Flutter Engine di atas canvas grafis GPU via CAMetalLayer (Metal surface).
  • Tanggung Jawab Khusus Subclass:
    • Anti-Flicker (backgroundColor): Menyetel latar belakang ke warna abu-abu muda (#F5F5F5) guna mencegah kedipan (flicker) hitam/putih sebelum frame pertama Flutter selesai dirender.
    • Bypass Layout Insets UIKit: Menyetel edgesForExtendedLayout = [.top, .bottom] dan extendedLayoutIncludesOpaqueBars = true agar viewport Flutter memenuhi area container secara presisi.
    • Safe Area Dinamis (updatePersistentSafeArea): Menghitung dan meneruskan penyesuaian safe area ke Flutter saat header atau status bar native berubah.
    • Visibilitas Status Bar Native (setNativeStatusBarOverlayHidden): Mengatur overlay status bar native (tag 100) saat rute Flutter aktif.
  • Siapa Saja Konsumennya?
    1. FlutterEngineManager: Menginisialisasi dan menyimpannya sebagai singleton privat.
    2. IDMainTabBarController: Mengambil view controller ini via installPersistentRoot untuk disisipkan ke dalam flutterContainerView.
    3. FlutterNativeChannel+route.swift: Memeriksa persistentRootViewController untuk menentukan target controller saat melakukan push/pop/modal navigasi.

D. Inisialisasi initialRoute: "/root" (Cold-Start Prewarm)

Pada baris 151 FlutterEngineManager.swift:

hasRun = engine.run(withEntrypoint: nil, initialRoute: "/root")
  • Target Rute Flutter: Di sisi Flutter (route_paths.dart dan routers.dart), rute "/root" mengarah ke FlutterRootPage.
  • Wadah Bersama (IndexedStack): FlutterRootPage membungkus MineHomePage (/mine) dan RepayHomePage (/repay) dalam satu stack widget permanen.
  • Tujuan Hardcoded di Startup: Saat native melakukan prewarm() di IDSamirMainModule, engine langsung memuat tree /root ke memori. Sehingga saat pengguna berpindah ke Tab Tagihan atau Tab Saya di IDMainTabBarController, tampilan langsung muncul seketika tanpa jeda cold-start (zero delay).

E. Protokol lifecycleChannel & State Baku (AppLifecycleState.resumed / .inactive)

engine.lifecycleChannel.sendMessage("AppLifecycleState.resumed")
engine.lifecycleChannel.sendMessage("AppLifecycleState.inactive")
  • Channel Resmi Bawaan: engine.lifecycleChannel adalah FlutterBasicMessageChannel<String> bawaan engine ("flutter/lifecycle").
  • Bukan String Bebas: String "AppLifecycleState.resumed" dan "AppLifecycleState.inactive" adalah protokol baku Flutter framework yang dipetakan langsung ke enum Dart AppLifecycleState. String custom di luar konvensi ini tidak akan diproses oleh binding Flutter.
  • Tujuan Penghematan Baterai & CPU:
    • Dalam arsitektur persistent host, view Flutter tidak dihancurkan (tidak pernah di-dealloc) saat pengguna membuka Tab Beranda (Native).
    • Memanggil inactive() mengirimkan "AppLifecycleState.inactive" untuk menghentikan render loop, timer animasi, dan ticker Flutter sehingga baterai dan CPU tidak terkuras di latar belakang.
    • Saat pengguna kembali ke Tab Flutter, pemanggilan resume() mengirimkan "AppLifecycleState.resumed" untuk mengaktifkan kembali rendering.

F. Filosofi precondition vs Clean Architecture: Fail-Fast & Invariant Enforcement

Pada baris 130–133 FlutterEngineManager.swift:

precondition(
    hasRun,
    "FlutterEngineManager.prewarm() must run before installing the Flutter host"
)
  • Cara Kerja precondition: Mengevaluasi kondisi runtime. Jika bernilai false, aplikasi akan langsung fatal error/crash seketika pada mode Debug maupun Release. Berbeda dengan assert yang diabaikan pada Release build, precondition bertindak sebagai penjaga batas invariant mutlak.
  • Hubungan dengan Clean Architecture & Fail-Fast:
    • Design by Contract (DbC): Clean Architecture menuntut batasan antarkomponen yang tegas. Sebuah View Controller host tidak boleh diinisialisasi jika dependensi intinya (Engine runtime) belum siap. Membiarkan aplikasi melanjutkan dalam status korup/cacat justru menciptakan undefined behavior.
    • Membedakan Programmer Invariant vs Recoverable Error:
      • Programmer Error / Invariant Violation (salah urutan pemanggilan method oleh developer): Tepat menggunakan precondition agar bug langsung tertangkap pada fase pengembangan.
      • Recoverable Error (jaringan putus, format JSON salah, pembatalan aksi): Wajib menggunakan mekanisme Error, Result, atau do-catch, bukan precondition.
  • Contoh Penggunaan Nyata: 
    // Memastikan dependensi kredensial atau batas buffer wajib terpenuhi saat startup
final class SecureNetworkPipeline {
    private let sessionToken: String
    
    init(token: String) {
        precondition(!token.isEmpty, "SecureNetworkPipeline requires an active token before construction.")
        self.sessionToken = token
    }
}

📌 9. Pembedahan Siklus Hidup & Urutan Proses di Balik Layar (Under-the-Hood Sequence)

Bagian ini menguraikan secara komprehensif bagaimana Flutter Engine berinteraksi dengan runtime iOS, apa saja yang dilakukan prewarm() pada tingkat thread & memori, serta alur milidetik di balik layar saat layar Flutter dimuat atau dibuka oleh pengguna.

A. Konsep Siklus Hidup (Lifecycle) Flutter di Host Native

Flutter pada dasarnya bukanlah kumpulan View UIKit standar, melainkan sebuah mesin rendering grafis mandiri yang menggambar seluruh pikselnya secara otonom di atas permukaan CAMetalLayer (Metal GPU pada iOS).

Mengapa Native Harus Mengatur Lifecycle Secara Eksplisit?

Dalam arsitektur Single Persistent Host SAMIR, SamirFlutterViewController tidak pernah di-destroy atau di-dealloc saat pengguna membuka Tab Beranda (Native). View-nya hanya disembunyikan (isHidden = true).

  • Tanpa intervensi sinyal native, Flutter Engine tidak mengetahui bahwa tampilannya sedang tidak terlihat di layar, sehingga engine akan terus mendengarkan VSync, mengeksekusi ticker animasi, dan mengonsumsi daya CPU.
  • AppLifecycleState.inactive: Dikirim saat tab Flutter tertutup. Engine mematikan ticker & frame rendering loop (scheduleFrame), menurunkan penggunaan CPU ke 0%.
  • AppLifecycleState.resumed: Dikirim sesaat sebelum kontainer Flutter ditampilkan kembali. Engine menghidupkan kembali VSync frame scheduling dan memicu onResume() pada PageLifecycleMixin.

Render loop stop, siap pakai seketika.
  1. Alokasi 3 Worker Thread C++ Flutter:
    • UI Task Runner: Thread yang mengeksekusi isolate Dart dan membangun Widget/Element/RenderObject tree.
    • Raster Task Runner (GPU): Thread yang menerjemahkan display list menjadi perintah instruksi grafis Metal.
    • IO Task Runner: Thread latar belakang untuk memuat font, gambar terkompresi, dan shader compilation.
  2. Booting Dart Virtual Machine (Dart VM): Heap memori Dart diinisialisasi. Waktu cold start VM (~200–400ms) dihabiskan pada fase splash startup, bukan saat interaksi pengguna.
  3. Pemuatan AOT Snapshot (App.framework): Biner kompilasi Ahead-Of-Time dimuat ke memori dan mengeksekusi fungsi main() di lib/main.dart.
  4. Eksekusi _bootstrap(): Menginisialisasi plugin monitoring APM Tingyun, membaca konfigurasi persistent di Global.init(), dan mengonfigurasi HTTP client Dio. Mendaftarkan handler platform channel via FlutterNativeRouteDispatcher.setup().
  5. Konstruksi Awal Rute "/root": Memanggil runApp(const MyApp()) dengan rute awal "/root". FlutterRootPage dimount bersama IndexedStack yang menampung instance awal MineHomePage dan RepayHomePage. Menunggu WidgetsBinding.instance.endOfFrame agar frame pertama selesai digambar ke offscreen buffer.
  6. Transisi Cepat ke Status inactive(): Begitu frame offscreen selesai, native langsung mengirim "AppLifecycleState.inactive". Engine standby di memori (~35 MB) tanpa membebani CPU.

  1. Pemicu Native (UITabBar): Tab selection memanggil updatePersistentFlutterHost(for:) di IDMainTabBarController.
  2. Pembangkitan Engine (resume): Native mengirim "AppLifecycleState.resumed" melalui engine.lifecycleChannel. SchedulerBinding di Flutter mengaktifkan kembali ticker VSync.
  3. Pengiriman Intent Rute (showRoot): Native menetapkan integer monotonic requestID (misal 101) dan memanggil MethodChannel "showFlutterRoute".
  4. Peralihan Indeks IndexedStack: Di sisi Flutter, FlutterRootController.select(route) mengubah indeks target. Karena anak widget sudah ada di RAM, tidak ada siklus re-inflation widget dari nol.
  5. Sinkronisasi Frame GPU (endOfFrame): Flutter memanggil WidgetsBinding.instance.ensureVisualUpdate() dan menahan eksekusi (await endOfFrame) sampai GPU Metal selesai menggambar frame rute baru.
  6. Pengambilan Data Asinkron: Sinyal refreshRepayHome() ditembakkan untuk memicu request HTTP API di background tanpa menahan transisi visual.
  7. Penyajian Mulus ke Layar Native: Flutter mengembalikan payload { requestId: 101, frameReady: true }. Native memvalidasi requestId, lalu menyetel flutterContainerView.isHidden = false dan menyesuaikan frame Safe Area.

D. Tiga Pilar Arsitektur: Zero-Delay, Anti-Flicker, dan Anti-Race Condition

Pilar Arsitektural Mekanisme Implementasi Masalah yang Dicegah
1. Zero Cold-Start Delay prewarm() di startup + IndexedStack di FlutterRootPage. Mencegah jeda hitam/loading 300–500ms saat pengguna pertama kali membuka tab Flutter.
2. Garansi Zero-Flicker Native menahan flutterContainerView.isHidden = true hingga Flutter mengonfirmasi await endOfFrame. Mencegah layar putih sesaat atau kedipan layout yang belum selesai digambar oleh GPU.
3. Anti Race-Condition Validasi monotonic integer requestID pada callback completion native. Mencegah salah tampilan halaman jika pengguna mengetuk tab berulang kali dalam tempo sangat cepat.
4. Asynchronous Data Fetch Pemisahan render layout awal dari fetching HTTP API (Dio). Mencegah UI tersendat (stutter/freeze) karena menunggu respons jaringan internet.

🏛️ Bagian 2: Architecture Lab, SOLID Audit & Retention Quizzes

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Tight Coupling pada Antarmuka Routing & Hardcoded String Paths

Navigasi antar layar dan pembukaan modal masih mengandalkan string URL scheme atau navigasi langsung controller-ke-controller, menyulitkan pelacakan dependensi dan memicu runtime crash jika parameter route tidak valid.

⚠️ Smells 2: Pencampuran Presentasi UI dengan Koordinasi Rute (Melanggar SRP)

ViewController atau Widget UI mengetahui secara langsung hierarki layar berikutnya dan cara menyajikannya (push vs present modal), mengurangi reusabilitas tampilan pada modul lain.

🚀 Blueprint Refactoring Standar Industri: Pola Navigation Coordinator & Typed Route Handlers

Mengabstraksikan seluruh orkestrasi layar ke dalam modul Coordinator independen. UI hanya memancarkan event intent navigasi tanpa mengetahui implementasi rute konkret.

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol Coordinator: AnyObject {
    var navigationController: UINavigationController { get set }
    func start()
}

public final class RepayFlowCoordinator: Coordinator {
    public var navigationController: UINavigationController
    public init(navigationController: UINavigationController) {
        self.navigationController = navigationController
    }
    public func start() {
        let vc = IDRepayViewController()
        navigationController.pushViewController(vc, animated: true)
    }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
