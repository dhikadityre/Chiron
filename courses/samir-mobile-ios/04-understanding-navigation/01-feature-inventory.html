📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumen ini mendokumentasikan secara lengkap seluruh fitur yang teridentifikasi dalam codebase SAMIR iOS, memetakan screen atau route URL terkait, kondisi akses (preconditions), data source API, komponen bersama, serta status verifikasinya.

Status Verifikasi: [Verified] (ditelusuri langsung dari route handlers, view controllers, dan presenter).

🎯 A. Learning Objective

Setelah mempelajari dokumen ini, pembaca akan mampu:

  1. Menginventarisasi 24 fitur yang ada di SAMIR iOS.
  2. Membedakan fitur yang dapat diakses publik, fitur yang memerlukan autentikasi login, fitur kondisional, dan fitur tooling internal.
  3. Mengetahui relasi antara rute URL router (samir://...), ViewController native, atau layar Flutter yang melayaninya.

📋 B. Prerequisites

  • Sudah membaca seluruh dokumen di Level 3: Architecture.
  • Mengetahui konsep URL Router dan state autentikasi pengguna.

💡 C. Simple Explanation (Katalog Menu Restoran)

Sebelum kita mempelajari rute perjalanan pengguna (navigation map), kita harus memiliki daftar inventaris dari seluruh "menu" dan "ruangan" yang ada di dalam aplikasi SAMIR:

  • Ada ruangan yang bebas dimasuki siapa saja (Layar Peluncuran, Beranda Tamu, Syarat & Ketentuan Umum).
  • Ada ruangan yang memerlukan tiket masuk / identitas (Formulir Pengajuan Pinjaman, Penilaian Kuota, Ikat Rekening Bank, Halaman Tagihan).
  • Ada ruangan khusus staf teknis (Konsol DebugUI).

Dokumen ini adalah katalog inventarisasi resmi seluruh ruangan tersebut.

🪜 E. Step-by-Step Walkthrough: Menelusuri Akses Fitur

Misalkan kita ingin menelusuri bagaimana fitur F10 (Foto KTP & OCR) dapat dijangkau oleh pengguna:

  1. Entry Point 1: Dari Beranda (IDHomeViewController), jika user belum pernah KYC dan menekan tombol "Ajukan Pinjaman", presenter memeriksa status autentikasi dan memanggil router: samir://auth/identity.
  2. Entry Point 2: Dari halaman Profil Saya (Flutter MinePersonalPage), jika kartu KTP belum diverifikasi, tombol "Verifikasi KTP" mengirim pesan via FlutterNativeChannel -> openNativeRoute("samir://auth/identity").
  3. Dispatcher: CZRouterCenter menangkap URL samir://auth/identity, mencocokkannya ke IDSamirAuthModuleRouterHandler, dan mendorong instance IDNewOCRViewController ke navigation controller teratas.

⚖️ F. Why It Matters (Audit Fitur Aktif vs Kode Warisan)

Dalam investigasi codebase ini, ditemukan bahwa:

  • SamirRepayRouterHandler.swift: Memiliki method kosong untuk /historyOrder, /order, dan /useCoupons. Fitur tagihan ini telah bermigrasi ke modul Flutter atau halaman H5 web (loadUrlWithAuth), sehingga handler router native lama telah didepresiasi secara de-facto.
  • Jangan berasumsi bahwa jika sebuah handler native ada, fitur tersebut aktif di native; selalu periksa apakah implementasinya kosong atau dialihkan ke Flutter/Web!

🔬 G. Practical Example (Pemeriksaan Precondition Login)

Setiap fitur yang membutuhkan login dilindungi oleh guard condition:

// FlutterNativeChannel+route.swift:L160-168
private func handleNativeSchemeRoute(url: String, result: @escaping FlutterResult) -> Bool {
    if isLoginRequiredNativeRoute(url), !(IDServiceManager.loginService()?.isLogin() ?? false) {
        mainThread {
            self.prepareNativeChromeForNavigation()
            IDServiceManager.loginService()?.loginAction()
            result(nil)
        }
        return true
    }
    // ... lanjutkan navigasi normal jika sudah login
}

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Tight Coupling pada Antarmuka Routing & Hardcoded String Paths

Navigasi antar layar dan pembukaan modal masih mengandalkan string URL scheme atau navigasi langsung controller-ke-controller, menyulitkan pelacakan dependensi dan memicu runtime crash jika parameter route tidak valid.

⚠️ Smells 2: Pencampuran Presentasi UI dengan Koordinasi Rute (Melanggar SRP)

ViewController atau Widget UI mengetahui secara langsung hierarki layar berikutnya dan cara menyajikannya (push vs present modal), mengurangi reusabilitas tampilan pada modul lain.

🚀 Blueprint Refactoring Standar Industri: Pola Navigation Coordinator & Typed Route Handlers

Mengabstraksikan seluruh orkestrasi layar ke dalam modul Coordinator independen. UI hanya memancarkan event intent navigasi tanpa mengetahui implementasi rute konkret.

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol Coordinator: AnyObject {
    var navigationController: UINavigationController { get set }
    func start()
}

public final class RepayFlowCoordinator: Coordinator {
    public var navigationController: UINavigationController
    public init(navigationController: UINavigationController) {
        self.navigationController = navigationController
    }
    public func start() {
        let vc = IDRepayViewController()
        navigationController.pushViewController(vc, animated: true)
    }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.

🧠 Interactive Retention & Architectural Quiz

Uji pemahaman alur kode nyata dan keputusan arsitektur Anda:

Kuis 1 (Memory Recall): Apa bahaya utama dari menggunakan hardcoded URL scheme string di seluruh navigasi layar?

Kuis 3 (Debugging & Maintenance): Apa yang harus dilakukan saat deep link masuk saat otentikasi pengguna belum selesai diverifikasi?
