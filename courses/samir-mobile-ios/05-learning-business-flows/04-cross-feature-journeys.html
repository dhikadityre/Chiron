04 — Cross-Feature Journeys

Interaksi Lintas Fitur & Transisi Runtime

📚 Modul: 04-cross-feature-journeys 🎯 Scope: SAMIR Mobile (iOS Native UIKit & FChannel) ⏱️ Estimasi: 20 Menit 🏷️ Git Branch: learn/iOS-Arch

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumen ini mendokumentasikan skenario perjalanan pengguna yang melibatkan interaksi lintas modul (cross-feature journeys): penanganan sesi kedaluwarsa di tengah pengisian formulir, lompatan dari halaman web H5 ke fitur native, integrasi deep link eksternal, serta pergantian runtime antara Native Swift dan Flutter Engine.

Status Verifikasi: [Verified] (diverifikasi langsung dari handler notifikasi, delegat jembatan JS, dan koordinator tab bar).

🎯 A. Learning Objective

Setelah mempelajari dokumen ini, pembaca akan mampu:

  1. Menjelaskan bagaimana aplikasi menyelamatkan state pengguna saat token sesi kedaluwarsa (10006) di tengah transaksi pinjaman.
  2. Memahami bagaimana halaman web H5 memicu aksi native melalui URL Scheme samir:// dan JSBridge.
  3. Memahami proses pergantian tab yang mulus antara Native Swift (Tab 0) dan Flutter (Tab 1 & 2) tanpa flicker layar.

📋 B. Prerequisites

  • Sudah membaca 02-authentication-and-session-flow.md dan 03-core-feature-flows.md.
  • Mengetahui konsep JavaScript Bridge (WKScriptMessageHandler) dan Flutter Platform View Container.

💡 C. Simple Explanation (Analogi Perjalanan Antarpulau)

Bayangkan Anda melakukan perjalanan wisata antarpulau:

  • Pulau Native (Beranda & KYC): Menggunakan mobil jalan raya (UIKit murni).
  • Pulau Web (Halaman Promo H5): Menggunakan perahu (WKWebView). Di atas perahu ada radio komunikasi (JSBridge) untuk meminta bantuan ke pangkalan di darat.
  • Pulau Flutter (Tagihan & Profil): Menggunakan kereta gantung canggih (Flutter Engine) yang terhubung ke stasiun utama mall.
  • Insiden Badai (Token Expired 10006): Jika di tengah jalan terjadi badai, tim penyelamat darurat otomatis memulangkan Anda ke posko awal (Tab 0 Beranda) dan meminta Anda memperbarui tanda pengenal (Modal Login).

Analisis Arsitektur:

Ketika error 10006 terjadi:

  1. IDNetworkRequest.p_handleReLoginError mencegat response sebelum blok failure callback presenter dipanggil.
  2. Sesi dibersihkan untuk mencegah request lain menggunakan token yang sudah mati.
  3. Navigation stack di-pop/reset secara paksa ke Beranda (Tab 0) untuk mencegah pengguna terus mengisi data di layar yang tidak lagi memiliki otorisasi.
  4. Form login muncul secara modal.

SKENARIO 2: Jembatan Web H5 Melompat ke Fitur Native (H5 to Native Jump)

Halaman H5 yang berjalan di 🦊 IDBusinessWebViewController.swift learn/iOS-Arch ↗ dapat memicu navigasi native melalui dua cara:

📊 Diagram Alur #2
sequenceDiagram participant H5 as H5 Web Page (JavaScript) participant WK as WKWebView participant Bridge as IDWebInjectJSBridge / IDWebViewJsHandler participant Router as IDRouterManager participant Native as IDNewOCRViewController alt Cara A: Menggunakan URL Scheme (samir://) H5->>WK: window.location.href = "samir://auth/identity" WK->>Bridge: decidePolicyFor navigationAction Bridge->>Router: IDRouterManager.id_perfromWithURLString("samir://auth/identity") Router->>Native: Push IDNewOCRViewController else Cara B: Menggunakan JavaScript Bridge (callApp) H5->>WK: window.webkit.messageHandlers.callApp.postMessage({ method: "showToast", paramsData: "Pesan dari Web" }) WK->>Bridge: idn_webView(..., withResponse: response) Bridge->>Bridge: IDWebCallAppHandler.toastMesage("Pesan dari Web") Bridge-->>H5: Toast muncul di atas layar native end
1. Cara A — Intersepsi Skema URL:

Jika link web mengarah ke URL ber-scheme samir:// (misal: tombol "Ambil Foto KTP" di halaman panduan web), delegat navigasi webview mencegat URL tersebut (decidePolicyFor navigationAction), membatalkan navigasi browser, dan meneruskannya ke IDRouterManager.id_perfromWithURLString(url).

2. Cara B — JavaScript Bridge Handler (AppHandlers.plist):

Pustaka menyuntikkan script bridge di IDWebInjectJSBridge:

  • showToast: Menampilkan toast native.
  • setH5Title: Mengubah judul navigation bar native sesuai judul halaman web.
  • back: Memanggil currentVC.idn_goback() untuk menutup browser.

SKENARIO 3: Deep Link Eksternal Menuju Layar Tagihan / Kupon

Ketika pengguna mengklik link promosi dari pesan WhatsApp atau push notification:

  1. Penerimaan Link: Link samir://repay/historyOrder atau https://m.samir.co.id/samir/repay/detail?bizId=123 diterima oleh IDSamirMainModule.
  2. Kondisi Autentikasi:
    • Jika isLogin() == true: Navigasi langsung didispatch ke router atau webview terotentikasi.
    • Jika isLogin() == false: Link disimpan di cache Samir_DeepLink_Str, form login dibuka, dan navigasi baru dieksekusi setelah event LoginSuccess diterima.
  3. Pembersihan Cache: Begitu layar tujuan terbuka, clearPushCache() dipanggil untuk mencegah navigasi ganda.

SKENARIO 4: Transisi Mulus Native Swift ke Layar Hybrid Flutter

Path: 🦊 ios/IDSamirLoan/Application/SamirMainModule/Classes/IDController/IDMainTabBarController.swift learn/iOS-Arch ↗

Bagaimana aplikasi berpindah dari Beranda Native (Tab 0) ke Tagihan Flutter (Tab 1) tanpa layar berkedip?

📊 Diagram Alur #3
sequenceDiagram participant User participant Tab as IDMainTabBarController participant FCont as flutterContainerView participant FEng as FlutterEngineManager participant FPage as FlutterRootPage (IndexedStack) User->>Tab: Tap Tab 1 ("Tagihan") Tab->>Tab: flutterRootRoute(for: selectedVC) -> return "/repay" Tab->>FEng: resume() Lifecycle Tab->>FEng: showRoot(route: "/repay", requestID: 101) FEng->>FPage: FlutterRootController.select("/repay") Note over FPage: Flutter me-render frame Repay di background FPage-->>FEng: frameReady == true FEng-->>Tab: Completion Handler Callback Tab->>FCont: flutterContainerView.isHidden = false Tab->>Tab: updatePersistentFlutterHostLayout() (Sinkronisasi safe area) Note over User: Layar Tagihan Flutter Tampil Mulus di Atas Native
Mekanisme Anti-Flicker:
  1. Persistent Container: View Flutter (flutterContainerView) tidak dibuat dan dihancurkan ulang setiap tab berpindah; ia disematkan secara permanen di bawah tabBar.
  2. Frame Ready Guard: Saat berpindah dari tab native ke tab Flutter, flutterContainerView tetap disembunyikan (isHidden = true) sampai Flutter mengirim konfirmasi frameReady == true. Ini mencegah pengguna melihat layar putih atau rendering kosong sesaat!
  3. Safe Area Sync: updatePersistentSafeArea(top:bottom:) secara presisi menghitung tinggi notch iPhone dan tinggi tab bar native agar layout Flutter tidak tertutup tombol fisik perangkat.

🪜 E. Step-by-Step Walkthrough: Menutup Halaman Flutter dari Native Navigation

Ketika user berada di halaman detail Flutter /mine/personal dan menekan tombol kembali di navigation bar:

  1. Flutter memanggil method channel closeFlutterPage.
  2. Native menangkap panggilan di 🦊 FlutterNativeChannel+route.swift learn/iOS-Arch ↗: 
   func closeFlutterPage(result: @escaping FlutterResult) {
       mainThread {
           guard let topVC = UIViewController.cz.topViewController() else { return }
           if let nav = topVC.navigationController, nav.viewControllers.count > 1 {
               nav.popViewController(animated: true)
           } else if topVC.presentingViewController != nil {
               topVC.dismiss(animated: true)
           }
           result(nil)
       }
   }
  1. Native secara otomatis memeriksa apakah halaman saat ini berada dalam tumpukan navigasi (popViewController) atau disajikan secara modal (dismiss).

⚖️ F. Why It Matters: Ketahanan Arsitektur Hybrid (Resilience)

Integrasi Native-Flutter yang tidak dirancang dengan baik sering kali mengalami masalah:

  • Memori membengkak jika membuat engine Flutter baru di setiap tab.
  • State UI hilang saat berpindah-pindah tab.

Dengan pola Single Prewarmed Engine + Persistent Container + IndexedStack yang diterapkan di SAMIR iOS, konsumsi memori tetap stabil dan performa antarmuka terasa seperti aplikasi native 100%.

🔬 G. Practical Example: Penanganan Tombol Back Fisik & Dialog Disclaimer

Ketika user berada di halaman profil Flutter dan mengklik tombol "Disclaimer Hukum":

  1. Flutter mengirim pesan jumpDisclaimerPopup ke native channel.
  2. Native mengeksekusi showMineDisclaimer(result:) di main thread.
  3. Dialog modal native IDNPopupController muncul di atas layar Flutter.
  4. Ketika user menekan tombol "Setuju", dialog native tertutup dan Flutter menerima callback konfirmasi.

⚠️ H. Common Mistakes & Debugging

  • Crash Saat Transisi Flutter ke Native:
    • Penyebab: Memanggil UI update dari thread background di MethodChannel.
    • Aturan: Semua interaksi navigasi dan UI dari Flutter channel wajib dibungkus di dalam mainThread { ... } atau DispatchQueue.main.async.
  • Safe Area Inset Salah pada Layar Dynamic Island (iPhone 14 Pro+):
    • Jika konten Flutter tertutup oleh Dynamic Island, periksa fungsi updatePersistentSafeArea di SamirFlutterViewController.

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: State Mutation Tersebar & Kurangnya Single Source of Truth

Status transaksi pinjaman dan otentikasi disimpan di beberapa singleton berbeda secara terpisah, rentan memicu race condition dan state inconsistency antar tab.

⚠️ Smells 2: Kurangnya Abstraksi Domain Layer (Business Logic Terikat ke UI)

Logika validasi kredit dan kalkulasi bunga dilakukan langsung di lapisan presentasi tampilan, menyulitkan pemeliharaan dan pengujian regresi.

🚀 Blueprint Refactoring Standar Industri: Pola Clean Architecture Use Case (Domain Interactor Pattern)

Mengisolasi logika bisnis finansial ke dalam Use Case murni yang bebas dari UIKit atau Widget Flutter, menjamin 100% testability dan integritas transaksi.

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol CalculateRepaymentUseCase {
    func execute(loanAmount: Double, tenorDays: Int) -> RepaymentCalculation
}

public final class DefaultCalculateRepaymentUseCase: CalculateRepaymentUseCase {
    public func execute(loanAmount: Double, tenorDays: Int) -> RepaymentCalculation {
        // Business rule murni terisolasi dari UI
        return RepaymentCalculation(principal: loanAmount, interest: loanAmount * 0.003 * Double(tenorDays))
    }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
