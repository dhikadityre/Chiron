01 — User Journey Overview

Gambaran Makro Siklus Pinjaman P2P

📚 Modul: 01-user-journey-overview 🎯 Scope: SAMIR Mobile (iOS Native UIKit & FChannel) ⏱️ Estimasi: 20 Menit 🏷️ Git Branch: learn/iOS-Arch

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumen ini memetakan perjalanan makro pengguna (macro customer journey) di aplikasi SAMIR iOS: siklus hidup nasabah dari pertama kali mengunduh aplikasi, mendaftar akun, melengkapi verifikasi identitas (e-KYC), menerima penilaian batas kredit (plafon kuota), mengonfirmasi pencairan pinjaman, hingga melunasi tagihan dan mengajukan pinjaman berulang (cycle loan).

Status Verifikasi: [Verified] (ditelusuri langsung dari implementasi logika bisnis di SamirLoginModule, SamirAuthModule, SamirLoanModule, dan SamirRepayModule).

🎯 A. Learning Objective

Setelah mempelajari dokumen ini, pembaca akan mampu:

  1. Menjelaskan 8 fase utama siklus hidup nasabah pada platform Fintech P2P Lending SAMIR.
  2. Memahami titik temu antara regulasi fintech (OJK / AFPI) dengan implementasi teknis di aplikasi (e-KYC, persetujuan kontrak digital, penilaian risiko perangkat).
  3. Mengidentifikasi transisi status nasabah dari Tamu (Guest) -> Terdaftar (Registered) -> Terverifikasi (KYC Complete) -> Memiliki Kuota (Approved Limit) -> Peminjam Aktif (Active Borrower).

📋 B. Prerequisites

  • Sudah membaca kurikulum Level 4: Understanding Navigation.
  • Mengetahui istilah dasar finansial seperti plafon kredit, tenor, suku bunga, dan virtual account.

💡 C. Simple Explanation (Analogi Pengajuan Pinjaman Mikro Tradisional)

Bayangkan seseorang yang membutuhkan dana tunai mendesak untuk modal usaha:

  1. Melihat Brosur: Nasabah datang melihat etalase pinjaman (Fase 1: Onboarding & Home).
  2. Membuka Rekening Anggota: Mengisi formulir pendaftaran dengan nomor ponsel (Fase 2: Registrasi OTP).
  3. Pemeriksaan Dokumen: Menunjukkan e-KTP fisik, mengisi data kantor tempat bekerja, menyerahkan kontak darurat keluarga, dan menunjukkan wajah asli di depan petugas (Fase 3: e-KYC & Liveness).
  4. Analisis Analis Kredit: Komite kredit menilai kelayakan nasabah dan menyetujui limit Rp 3.000.000 (Fase 4: Penilaian Kuota).
  5. Tanda Tangan Perjanjian: Nasabah memilih tenor 30 hari, menggunakan kupon diskon admin, membaca kontrak, dan menandatangani akad pinjaman digital (Fase 5: Konfirmasi Pinjaman).
  6. Uang Masuk ke Rekening: Dana ditransfer otomatis ke rekening bank nasabah (Fase 6: Pencairan).
  7. Bayar Angsuran: Pada hari jatuh tempo, nasabah mentransfer via Virtual Account (Fase 7: Pelunasan).
  8. Nasabah Loyal: Setelah lunas, limit kredit nasabah otomatis naik dan dapat dipinjam kembali secara instan (Fase 8: Pinjaman Berulang / Cycle).

🪜 E. Step-by-Step Walkthrough: 8 Fase Perjalanan Pengguna

Fase 1: Discovery & Onboarding (Eksplorasi)

  • Pengguna membuka aplikasi SAMIR iOS.
  • Aplikasi menampilkan IDLaunchViewController dengan hitung mundur 3 detik.
  • Pengguna tiba di IDHomeViewController (Tab 0) dalam mode Tamu (Guest Mode). Layar menampilkan kalkulator simulasi pinjaman dengan nilai default dan tombol ajukan.

Fase 2: Authentication & Registration (Registrasi Akun)

  • Pengguna menekan tombol "Ajukan Pinjaman".
  • Karena belum ada sesi login (IDServiceManager.loginService()?.isLogin() == false), modal LoginViewV2Controller muncul.
  • Pengguna menginput nomor ponsel (+62 / 08).
  • Pengguna menerima 6 digit kode OTP via SMS atau WhatsApp dan memasukkannya ke kolom verifikasi.
  • Sesi dibuat, kunci staticKey disimpan, dan pengguna kembali ke Beranda sebagai user terotentikasi.

Fase 3: Identity Verification / e-KYC (Kepatuhan Regulasi Finansial)

  • Sebelum pinjaman dapat dianalisis, regulasi OJK mewajibkan verifikasi identitas nasabah:
  1. OCR KTP (IDNewOCRViewController): Kamera memindai e-KTP asli. SDK Advance AI mengenali NIK dan Nama.
  2. Data Pribadi (IDNewAuthBasicViewController): Input agama, status perkawinan, tingkat pendidikan, dan alamat tempat tinggal.
  3. Pekerjaan (IDNewAuthJobViewController): Input profesi, nama instansi/perusahaan, dan estimasi penghasilan bulanan.
  4. Kontak Darurat (IDNewAuthContactViewController): Input 2 nomor telepon keluarga inti atau rekan kerja.
  5. Rekening Bank (IDNewBankViewController): Mengikat rekening bank yang namanya wajib cocok 100% dengan nama di e-KTP.
  6. Liveness Detection (IDAuthLiveViewController): Menggunakan SDK AAILiveness / TrustDecision untuk memastikan pemohon adalah manusia hidup dan bukan foto/video palsu.

Fase 4: Credit Risk Assessment & Quota Decision (Penilaian Kuota)

  • Pengguna diarahkan ke IDQuatoAssessViewController (samir://loan/creditAssess).
  • Aplikasi mengirim data profil risiko perangkat (blackBox dari SDK TrustDecision).
  • Presenter IDAssessPresenter menjalankan polling status analisa server (requstPollingStatus).
  • Hasil keputusan:
  • Disetujui: Plafon kuota (misal: Rp 1.000.000 s/d Rp 5.000.000) dan daftar produk pinjaman aktif.
  • Ditolak: Pengguna diberitahu tanggal kapan mereka dapat mengajukan kembali (cooling-off period).

Fase 5: Loan Product Selection & Confirmation (Akad Pinjaman Digital)

  • Pengguna masuk ke layar reaktif LoanConfirmViewController_Rx (samir://loan/confirm).
  • Pengguna menyesuaikan nominal pinjaman dan memilih tenor cicilan.
  • Pengguna dapat memilih voucher potongan biaya administrasi melalui samir://loan/voucherSelect.
  • Layar menampilkan rincian transparan: Nominal Pinjaman, Biaya Layanan, Bunga, Biaya Asuransi, Potongan Diskon, Tanggal Jatuh Tempo, dan Nominal Pencairan Bersih.
  • Pengguna membaca klausul perjanjian pinjaman online (IDConfirmContractPopupView) dan menyetujui akad digital.

Fase 6: Loan Disbursement (Pencairan Dana)

  • Begitu tombol "Cairkan Dana" ditekan, pesanan dibuat di backend.
  • Sistem perbankan mitra memproses transfer dana ke rekening bank yang telah diverifikasi di Fase 3.
  • Pengguna menerima notifikasi push keberhasilan pencairan.

Fase 7: Servicing & Repayment (Pemantauan & Pembayaran Tagihan)

  • Pengguna memantau jadwal cicilan di Tab 1 (Tagihan / Repay Home yang di-host di Flutter).
  • Mendekati tanggal jatuh tempo, pengguna mengklik tombol "Bayar".
  • Aplikasi menampilkan nomor Virtual Account (BCA, Mandiri, BNI, BRI, Permata) atau barcode retail (Alfamart / Indomaret).
  • Setelah pembayaran diterima, backend mengirim konfirmasi pelunasan secara realtime.

Fase 8: Retention & Repeat Borrowing (Pinjaman Berulang / Cycle Loan)

  • Setelah pinjaman pertama lunas dengan riwayat kredit yang baik, limit kuota pengguna otomatis dinaikkan.
  • Pengguna tidak perlu mengisi formulir KYC ulang! Pada pengajuan berikutnya, pengguna dapat langsung melompat dari Beranda ke Konfirmasi Pinjaman secara instan (one-click loan).

⚖️ F. Why It Matters: Mengapa Alur KYC Sangat Panjang?

Senior engineer harus memahami bahwa panjangnya alur KYC (6 langkah) bukan sekadar preferensi desain antarmuka, melainkan kewajiban regulasi perlindungan konsumen dan manajemen risiko kredit di Indonesia:

  • Nama di KTP dan Nama di Rekening Bank harus identik untuk mencegah pencucian uang (Anti-Money Laundering / AML).
  • Liveness detection wajib menggunakan SDK bersertifikasi ISO 30107 untuk mencegah penipuan identitas (Identity Theft).

🔬 G. Practical Example: Guard State di Beranda

Di file 🦊 ios/IDSamirLoan/Application/SamirLoanModule/Classes/IDPresenter/IDLoanPresenter.swift learn/iOS-Arch ↗, presenter mengevaluasi status pengguna saat tombol ajukan ditekan:

// Evaluasi state pengguna
if !isLogin {
    IDServiceManager.loginService()?.loginAction()
} else if userAuthStatus != .complete {
    // KYC belum selesai -> buka rute auth
    IDRouterManager.id_perfromWithURLString(IDRouterSchemeConstants.Auth.identity.rawValue)
} else if quotaStatus == .pendingAssessment {
    // Butuh analisa -> buka rute kredit assess
    IDRouterManager.id_perfromWithURLString(IDRouterSchemeConstants.Loan.creditAssess.rawValue)
} else {
    // Langsung konfirmasi
    IDRouterManager.id_perfromWithURLString(IDRouterSchemeConstants.Loan.confirm.rawValue)
}

⚠️ H. Common Mistakes & Debugging

  • Mengabaikan Kegagalan Liveness Detection:
  • Jika liveness gagal karena pencahayaan redup, SDK akan mengembalikan error score. Jangan pernah membypass pemeriksaan liveness di sisi klien karena backend akan selalu memverifikasi ulang hash gambar wajah (face comparison score).
  • Asumsi Pengguna Selalu Melakukan KYC Lengkap:
  • Banyak pengguna menutup aplikasi di tengah-tengah alur KYC (misal saat step kontak darurat). Aplikasi harus mampu mendeteksi progres terakhir (step) dan mengantar pengguna kembali ke langkah yang belum selesai saat aplikasi dibuka kembali.

🏛️ Bagian 2: Architecture Lab, SOLID Audit & Retention Quizzes

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: State Mutation Tersebar & Kurangnya Single Source of Truth

Status transaksi pinjaman dan otentikasi disimpan di beberapa singleton berbeda secara terpisah, rentan memicu race condition dan state inconsistency antar tab.

⚠️ Smells 2: Kurangnya Abstraksi Domain Layer (Business Logic Terikat ke UI)

Logika validasi kredit dan kalkulasi bunga dilakukan langsung di lapisan presentasi tampilan, menyulitkan pemeliharaan dan pengujian regresi.

🚀 Blueprint Refactoring Standar Industri: Pola Clean Architecture Use Case (Domain Interactor Pattern)

Mengisolasi logika bisnis finansial ke dalam Use Case murni yang bebas dari UIKit atau Widget Flutter, menjamin 100% testability dan integritas transaksi.

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol CalculateRepaymentUseCase {
    func execute(loanAmount: Double, tenorDays: Int) -> RepaymentCalculation
}

public final class DefaultCalculateRepaymentUseCase: CalculateRepaymentUseCase {
    public func execute(loanAmount: Double, tenorDays: Int) -> RepaymentCalculation {
        // Business rule murni terisolasi dari UI
        return RepaymentCalculation(principal: loanAmount, interest: loanAmount * 0.003 * Double(tenorDays))
    }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
