📌 Alur 1: Pipeline Request Jaringan, Penandatanganan Kriptografis, & Envelope Handling

1. THE "WHY" (Arsitektur & Motivasi)

  • Pola Arsitektur: Layered Client-Adapter Architecture (BusinessService -> IDNetworkRequest Facade -> IDNetworkSignatureHandler -> LibNetSignGenerator C-Wrapper -> CZNetworkCenter -> CZAlamofireBridge -> Alamofire.Session).
  • Alasan Pemisahan & Decoupling:
    1. Security Binary Isolation: Logika pembuatan hash sign diisolasi di binary vendor framework tertutup (LibNetSignGenerator.framework), melindungi algoritma penandatanganan dari reverse engineering terhadap Swift source code.
    2. Transport Layer Decoupling: Wrapper CZAlamofireBridge mengisolasi pihak ketiga (Alamofire). Jika dependensi networking diperbarui atau diganti, seluruh modul bisnis tingkat atas tidak terdampak.
    3. Centralized Envelope & Session Interception: Pembongkaran format {code, msg, result} serta penanganan sesi kadaluarsa (code == "10006") dilakukan secara terpusat di IDNetworkRequest, mengeliminasi boilerplate kode error handling di ratusan controller.

2. THE TRIGGER & CHAIN REACTION (Alur Eksekusi)

  • Entry Point: Pemanggilan service bisnis oleh presenter atau viewModel, contoh: IDLoanService.requestProductDetail(...) yang mengeksekusi IDNetworkRequest.id_startPOSTRequest(...).
  • Execution Chain:
    1. Service memanggil IDNetworkRequest.id_startPOSTRequest(requestUrl, params: params, success: ..., failure: ...).
    2. Properti getter cz_requestArguments di IDNetworkRequest membaca parameter bisnis dan memanggil ApiParamsHelper.getDefaultParams() untuk menyuntikkan 18 parameter umum (account_id, mid, timestamp, uuid, version, dll.).
    3. IDNetworkRequest memeriksa varian request: memanggil IDNetworkSignatureHandler.getNormalRequestParamsWithSign(allRequestProperties).
    4. IDNetworkSignatureHandler mengurutkan dictionary, mengubahnya menjadi JSON string, lalu memanggil method ObjC NetworkRequestSignWrapper.ns_encrypt(forNormal: jsonStr, staticKey: IDNetworkManager.shared.static_key).
    5. Framework LibNetSignGenerator menghitung hash dan mengembalikan nilai string ke field "sign" pada dictionary request.
    6. IDNetworkRequest.startWithCompletionBlock memanggil CZBaseRequest.start(), yang mendaftarkan instance request ke CZNetworkCenter.sharedInstance().addRequest(self).
    7. CZNetworkCenter membangun URLRequest dan mendelegasikannya ke CZAlamofireBridge.startDataRequest(urlRequest: ..., sessionConfiguration: ..., validatesDomainName: ...).
    8. CZAlamofireBridge mengeksekusi request HTTP melalui instance Alamofire.Session.
    9. Saat HTTP response diterima, handleRequestResult di CZNetworkCenter meneruskan data mentah ke IDNetworkRequest.p_handleSuccessRequest.
    10. IDNetworkRequest memvalidasi envelope JSON:
      • Jika code == "200", panggil callback success(self) dengan responseObject berisi objek result.
      • Jika code == "10006", eksekusi reloginWhenRequestError() (reset sesi & arahkan ke layar login).
      • Jika kode error lain, bangun instance NSError dengan cz_errorMessage dan panggil failure(self).

📌 Alur 2: Konfirmasi Pinjaman, Perhitungan Biaya Realtime (Rx), & Pengajuan Order Formal

1. THE "WHY" (Arsitektur & Motivasi)

  • Pola Arsitektur: Clean MVVM-Rx (Model-View-ViewModel with Reactive Extensions & Unidirectional Data Flow).
  • Alasan Pemisahan & Decoupling:
    1. Strict Input/Output Decoupling: View Controller hanya berinteraksi melalui interface LoanConfirmViewModelInput (PublishSubject) dan LoanConfirmViewModelOutput (Driver), mencegah View memanipulasi state internal secara langsung.
    2. Thread Safety via Driver: Output UI dijamin terikat pada MainScheduler dan tidak dapat mengemisikan error stream termination, mencegah kegagalan rendering dan crash antarmuka pada formulir finansial kritis.
    3. Decoupled Pricing Engine: Logika perhitungan bunga, diskon kupon, dan breakdown biaya pinjaman diisolasi di LoanConfirmServiceProtocol, memungkinkan unit testing kalkulasi kredit tanpa instansiasi view.

2. THE TRIGGER & CHAIN REACTION (Alur Eksekusi)

  • Entry Point: Pengguna membuka halaman konfirmasi pinjaman, memilih kartu tenor produk, memilih voucher kupon, mencentang persetujuan akad, atau menekan tombol konfirmasi pencairan.
  • Execution Chain:
    1. Saat layar dimuat, LoanConfirmViewController_Rx.viewDidLoad memanggil input.refreshTrial.onNext(()).
    2. LoanConfirmViewModel mengaktifkan _isLoading.accept(true) dan memanggil service.requestLoanConfirmDetails(bizId: ...).
    3. LoanConfirmService memanggil IDNetworkRequest ke endpoint product/confirm/details; data kuota dan kupon yang diterima disimpan ke _loanData (BehaviorRelay).
    4. Driver output.loanData mengemisikan nilai ke View, memperbarui tampilan limit pinjaman dan daftar kartu produk cicilan.
    5. Pengguna mengetuk pilihan tenor pinjaman -> View memicu input.selectProduct.onNext((product, index)).
    6. ViewModel memperbarui _selectedProduct.accept(product) dan memicu perhitungan ulang simulasi biaya melalui service.requestTrialCalculation(...).
    7. Service memanggil endpoint product/confirm/calculateTrial; hasil kalkulasi baru diterima dan dipancarkan ke _trialResult.
    8. Driver output.trialResult dan output.receivedAmount memperbarui label "Jumlah Diterima Bersih", biaya admin, dan bunga cicilan secara realtime.
    9. Pengguna mencentang persetujuan akad & regulasi SEOJK -> View memicu input.toggleTermsAgreement.onNext(true).
    10. ViewModel mengevaluasi kombinasi state via Observable.combineLatest; Driver output.canSubmit mengemisikan true langsung ke btnConfirm.rx.isEnabled.
    11. Pengguna menekan tombol "Ajukan Pinjaman" -> View memicu input.submitCycleLoanOrder.onNext((lat, lng, usageKey, path)).
    12. ViewModel memvalidasi koordinat GPS, mengaktifkan _isLoading.accept(true), dan memanggil service.submitCycleFormalOrder(...).
    13. Service mengirim request bertanda tangan ke product/confirm/cycleOrder; respon IDCycleFormalOrderModel dengan status "AUDITING" dipancarkan ke _cycleLoanOrderSuccess.
    14. Driver output.cycleLoanOrderSuccess diterima LoanConfirmViewController_Rx, menampilkan dialog status sukses dan merutekan navigasi kembali ke Tab Beranda (Tab 0).

📌 Alur 3: Navigasi Antar-Modul & Resolusi Deep-Link Ter-decouple (CZRouter)

1. THE "WHY" (Arsitektur & Motivasi)

  • Pola Arsitektur: Mediator / URL-Based Dynamic Router Pattern (CZSwiftRouterLib).
  • Alasan Pemisahan & Decoupling:
    1. Zero Compile-Time Coupling: Modul fitur (seperti SamirMainModule dan SamirAuthModule) tidak saling meng-import file satu sama lain, memangkas dependency cycle dan mempercepat proses build.
    2. Universal Navigation Pipeline: Format URL tunggal (samir://<module>/<path>?params) melayani deep link push notification, banner WebView H5, dan perpindahan layar kode internal secara identik.
    3. Decentralized Route Handlers: Setiap modul mendaftarkan domain jalurnya sendiri (IDSamirAuthModuleRouterHandler) ke tabel rute saat bootstrap modul tanpa memodifikasi registry sentral.

2. THE TRIGGER & CHAIN REACTION (Alur Eksekusi)

  • Entry Point: Pemanggilan in-app via IDRouterManager.open(routerUrl) atau penanganan deep link sistem di AppDelegate.application(_:open:options:).
  • Execution Chain:
    1. Pemanggil mengeksekusi URL navigasi target: IDRouterManager.open("samir://auth/identity?step=1&status=RENEW").
    2. IDRouterManager meneruskan URL string ke CZRouterCenter.sharedInstance().open(url: routerUrl).
    3. CZRouterCenter mengurai string menjadi objek CZRouterRequest: skema samir://, path /auth/identity, dan query parameters ["step": "1", "status": "RENEW"].
    4. CZRouterCenter mencocokkan pola regex path pada CZRouterTable.
    5. Regex pencocokan mengidentifikasi bahwa prefix /auth/* terdaftar untuk kelas IDSamirAuthModuleRouterHandler.
    6. CZRouterCenter mengeksekusi method handle(_ router: CZRouterProtocol?) pada instance IDSamirAuthModuleRouterHandler.
    7. Handler mengevaluasi switch-case pada properti router?.path, menemukan kecocokan dengan IDSamirAuthRouterPath.Identity.
    8. Handler membaca dictionary router?.params dan menginstansiasi view controller target: let vc = IDNewOCRViewController(); vc.step = step; vc.status = status.
    9. Handler memanggil helper navigasi openVC(vc).
    10. Helper menelusuri hierarchy view controller aktif via UIViewController.cz.topViewController()?.navigationController.
    11. Navigation controller aktif mengeksekusi pushViewController(vc, animated: true) dan transisi layar selesai tanpa caller mengetahui kelas target konkret.

📌 Alur 4: Transisi Layar Native ke Persistent Flutter Container & Shared Session Bridge

1. THE "WHY" (Arsitektur & Motivasi)

  • Pola Arsitektur: Prewarmed Single-Engine Persistent Host Bridge (FlutterEngineManager + FlutterNativeChannel + MethodChannel RPC).
  • Alasan Pemisahan & Decoupling:
    1. Memory & CPU Conservation: Alih-alih membuat FlutterViewController baru di setiap navigasi (~30-40MB RAM per engine), aplikasi menggunakan 1 single prewarmed engine yang aktif sejak booting.
    2. Zero-Flicker Screen Switch: Container Flutter (flutterContainerView) disisipkan tepat di bawah TabBar native. Transisi antara Tab Native (Tab 0: Home) dan Tab Flutter (Tab 1: Repay, Tab 2: Mine) hanya melakukan toggle isHidden setelah Flutter mengirimkan sinyal frameReady, mengeliminasi efek layar berkedip putih/hitam.
    3. Single Source of Truth (SSOT) Session: Flutter tidak mengelola token otentikasi atau hashing tanda tangan sendiri; seluruh parameter perangkat dan staticKey dipinjam dari Native via method channel getNativeRequestParams.

2. THE TRIGGER & CHAIN REACTION (Alur Eksekusi)

  • Entry Point: Pengguna mengetuk Tab 1 ("Tagihan" / IDRepayViewController) atau Tab 2 ("Akun Saya" / IDMineViewController) pada native bottom TabBar.
  • Execution Chain:
    1. IDMainTabBarController menangkap delegasi pemilihan tab dan memanggil flutterRootRoute(for: selectedViewController).
    2. Jika tab yang dipilih adalah IDRepayViewController, fungsi mengembalikan rute "/repay".
    3. IDMainTabBarController mengeksekusi switchFlutterRoot(to: "/repay") dan membuat penomoran unik requestID.
    4. Method memanggil FlutterEngineManager.shared.resume(), lalu memicu FlutterNativeChannel.shared.showFlutterRoute("/repay", presentation: "root", requestID: requestID).
    5. FlutterNativeChannel mengeksekusi methodChannel?.invokeMethod("showFlutterRoute", arguments: ["route": "/repay", "presentation": "root", "requestId": requestID]) melalui channel samir_native_channel.
    6. Modul Flutter menerima RPC di FlutterRootPage, mengubah indeks aktif pada widget IndexedStack, dan me-render frame tampilan Repay.
    7. Flutter mengembalikan callback payload {"frameReady": true, "requestId": requestID} ke native iOS.
    8. Native completion block memverifikasi bahwa requestID cocok dengan tab aktif saat ini, lalu mengubah status flutterContainerView.isHidden = false dan memanggil FlutterEngineManager.shared.setPersistentRootVisible(true).
    9. Ketika halaman Flutter membutuhkan komunikasi HTTP: Modul Dart mengirimkan RPC getNativeRequestParams melalui samir_native_channel.
    10. FlutterNativeChannel.getNativeRequestParams di iOS memanggil ApiParamsHelper.getDefaultParams() dan menyisipkan staticKey = IDNetworkManager.shared.static_key, lalu mengembalikan dictionary parameter lengkap ke Flutter.

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: State Mutation Tersebar & Kurangnya Single Source of Truth

Status transaksi pinjaman dan otentikasi disimpan di beberapa singleton berbeda secara terpisah, rentan memicu race condition dan state inconsistency antar tab.

⚠️ Smells 2: Kurangnya Abstraksi Domain Layer (Business Logic Terikat ke UI)

Logika validasi kredit dan kalkulasi bunga dilakukan langsung di lapisan presentasi tampilan, menyulitkan pemeliharaan dan pengujian regresi.

🚀 Blueprint Refactoring Standar Industri: Pola Clean Architecture Use Case (Domain Interactor Pattern)

Mengisolasi logika bisnis finansial ke dalam Use Case murni yang bebas dari UIKit atau Widget Flutter, menjamin 100% testability dan integritas transaksi.

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol CalculateRepaymentUseCase {
    func execute(loanAmount: Double, tenorDays: Int) -> RepaymentCalculation
}

public final class DefaultCalculateRepaymentUseCase: CalculateRepaymentUseCase {
    public func execute(loanAmount: Double, tenorDays: Int) -> RepaymentCalculation {
        // Business rule murni terisolasi dari UI
        return RepaymentCalculation(principal: loanAmount, interest: loanAmount * 0.003 * Double(tenorDays))
    }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
