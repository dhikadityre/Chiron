03 — Core Feature Flows

Rincian Alur Bisnis Fitur Inti

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumen ini mendokumentasikan secara mendalam 4 alur bisnis inti aplikasi SAMIR iOS: Alur Verifikasi Identitas (e-KYC), Alur Penilaian Kuota Kredit & Polling Status, Alur Konfirmasi Pinjaman (RxSwift), serta Alur Pembayaran Tagihan (Repayment).

Status Verifikasi: [Verified] (ditelusuri langsung dari presenter, view controller, service network, dan kontrak API).

🎯 A. Learning Objective

Setelah mempelajari dokumen ini, pembaca akan mampu:

  1. Menjelaskan secara teknis urutan 6 langkah verifikasi e-KYC dan data yang dikirim pada setiap endpoint.
  2. Memahami mekanisme polling asynchronous pada penilaian kuota kredit di IDAssessPresenter.
  3. Membedah arsitektur reaktif dan pembuatan pesanan pinjaman di LoanConfirmViewController_Rx.
  4. Menelusuri alur pemilihan metode pembayaran (Virtual Account / Gerai Retail) hingga update status pelunasan.

📋 B. Prerequisites

  • Sudah membaca 01-user-journey-overview.md dan 02-authentication-and-session-flow.md.
  • Mengetahui cara kerja asynchronous polling dan Observer pattern di RxSwift.

💡 C. Simple Explanation

Bayangkan 4 pilar utama di sebuah bank digital:

  1. Pilar 1 (Verifikasi Identitas): Memastikan pemohon pinjaman adalah warga negara Indonesia yang sah dengan KTP asli dan wajah nyata.
  2. Pilar 2 (Penilaian Risiko): Komputer cerdas bank menganalisis kemampuan finansial pemohon dan menentukan berapa juta rupiah yang boleh dipinjam.
  3. Pilar 3 (Konfirmasi Akad): Nasabah menandatangani perjanjian pinjaman digital, melihat jadwal jatuh tempo, dan meminta pencairan dana.
  4. Pilar 4 (Pelunasan Tagihan): Nasabah mendapatkan kode pembayaran untuk mentransfer cicilan tepat waktu.

FITUR INTI 1: Alur Verifikasi Identitas (e-KYC Sequence)

📊 Diagram Alur #1

Rincian Teknis Per Step:
  1. Step 1 — OCR KTP (IDNewOCRViewController):
  • Tindakan: Membuka kamera dengan overlay panduan kartu KTP.
  • Validasi: Pemeriksaan blur dan pantulan cahaya (CZCheckData).
  • Endpoint: thirdData/v2/ocr/recognition.
  • Hasil: Data nama dan NIK diisi otomatis di form untuk dikonfirmasi oleh pengguna.
  1. Step 2 — Data Pribadi (IDNewAuthBasicViewController):
  • Tindakan: Mengisi form picker tingkat pendidikan, agama, dan provinsi/kota/kecamatan.
  • Validasi: Usia legal peminjam wajib berada dalam rentang 18–60 tahun (wetherAgeInLegalRange).
  • Endpoint: customer/renewMemInfo.
  1. Step 3 — Pekerjaan (IDNewAuthJobViewController):
  • Tindakan: Memilih jenis pekerjaan (Karyawan Swasta, PNS, Wiraswasta), lama bekerja, dan rentang pendapatan.
  • Endpoint: customer/renewMemInfo.
  1. Step 4 — Kontak Darurat (IDNewAuthContactViewController):
  • Tindakan: Memasukkan 2 nomor telepon darurat keluarga/pasangan.
  • Validasi: Nomor tidak boleh sama dengan nomor login pengguna dan kedua kontak tidak boleh identik.
  1. Step 5 — Ikat Rekening Bank (IDNewBankViewController):
  • Tindakan: Mengambil daftar bank mitra via bankCard/ynBankList.
  • Validasi Kritis: Backend memvalidasi apakah nama pemilik rekening bank sesuai dengan nama pada e-KTP. Jika berbeda, proses ditolak (Anti-Fraud / Anti-Money Laundering Rule).
  • Endpoint: bankCard/bindCard.
  1. Step 6 — Verifikasi Wajah Liveness (IDAuthLiveViewController):
  • Tindakan: Mengambil token lisensi via auth/ticket/v1/generate-token, lalu mengaktifkan modul kamera deteksi gerakan wajah vendor (AAILiveness).
  • Endpoint: comment/upload/living dan comment/liveness/decision.

Rincian Teknis Polling:

Path: 🦊 ios/IDSamirLoan/Application/SamirLoanModule/Classes/IDPresenter/IDAssessPresenter.swift learn/iOS-Arch ↗

  • Konfigurasi Dinamis: Interval polling dan batas maksimum percobaan tidak di-hardcode di aplikasi klien, melainkan dikontrol dari response server (pollConfig.interval dan pollConfig.totalCount).
  • Pembersihan Timer: Ketika pengguna menekan tombol back atau tampilan ditutup (viewWillDisappear / detachView), method stopPolling() wajib dipanggil agar timer tidak bocor di latar belakang (memory leak prevention).

Rincian Arsitektur Reaktif (Low-Level Execution):
  • Input Disconnect: Controller tidak pernah memanggil fungsi mutasi state secara langsung di ViewModel. Seluruh aksi pengguna dialirkan melalui PublishSubject di interface LoanConfirmViewModelInput.
  • Thread Isolation & Driver: Seluruh state UI yang diekspos oleh LoanConfirmViewModelOutput dijamin berjalan di MainScheduler menggunakan operator .asDriver(onErrorJustReturn:), mengeliminasi bug UI freeze atau crash threading.
  • State Relay: ViewModel menggunakan BehaviorRelay internal untuk menyimpan snapshot data terakhir, sehingga jika terjadi re-layout view, data tidak perlu di-fetch ulang dari server.

FITUR INTI 4: Alur Pembayaran Tagihan (Repayment Flow)

Path: 🦊 flutter/lib/pages/repay/home/repay_home_page.dart learn/iOS-Arch ↗ dan 🦊 SamirCommonModule/Classes/FChannel/FlutterNativeChannel+route.swift learn/iOS-Arch ↗

  1. Penyajian Data Tagihan:
  • Tab 1 (Tagihan) dirender oleh Flutter RepayHomePage.
  • Modul Flutter meminta data sesi dan parameter native melalui method channel getNativeRequestParams.
  • Menampilkan total tagihan yang belum lunas, tanggal jatuh tempo, dan rincian denda keterlambatan (jika ada).
  1. Pemilihan Metode Pembayaran:
  • Nasabah memilih channel pembayaran:
  • Virtual Account Bank: BCA, Mandiri, BNI, BRI, Permata, CIMB Niaga.
  • Gerai Retail: Alfamart, Indomaret.
  1. Penyajian Kode Bayar:
  • Layar menampilkan 16 digit nomor Virtual Account dan panduan langkah transfer (via ATM, Mobile Banking, atau Internet Banking).
  • Terdapat tombol "Salin Kode" yang terhubung ke clipboard sistem.
  1. Verifikasi Pelunasan:
  • Begitu transfer terdeteksi oleh sistem payment gateway, server mengirimkan notifikasi.
  • Flutter me-refresh tampilan tagihan menjadi "Lunas" dan status Beranda kembali membuka limit kuota untuk pinjaman berikutnya.

🪜 E. Step-by-Step Walkthrough: Validasi Nama Bank pada Alur KYC

Salah satu aturan bisnis paling ketat di SAMIR adalah validasi kepemilikan rekening:

  1. Di IDNewOCRViewController, nama nasabah diekstrak dari KTP: misalkan "BUDI SANTOSO".
  2. Di IDNewBankViewController, nasabah memilih Bank Mandiri dan menginput nomor rekening 1400012345678.
  3. Sebelum mengizinkan pengikatan, aplikasi memanggil endpoint bankCard/bindCard.
  4. Backend melakukan inkuiri nama pemilik rekening ke sistem interbank switching:
  • Jika nama bank mengembalikan "BUDI SANTOSO" -> Validasi Lolos.
  • Jika nama bank mengembalikan "SITI AMINAH" (nama istri/saudara) -> Validasi Ditolak.
  1. Antarmuka menampilkan pesan error: "Nama pemilik rekening bank harus sama persis dengan nama pada KTP Anda demi keamanan pencairan dana."

⚖️ F. Why It Matters: Pemisahan Bisnis Proved di Kode vs Spekulasi

  • Terbukti di Kode (Verified):
  • Kode membuktikan adanya batas usia legal 18–60 tahun (validateInputLength dan wetherAgeInLegalRange).
  • Kode membuktikan adanya polling status kredit dengan konfigurasi interval dinamis dari server.
  • Kode membuktikan pembuatan pesanan pinjaman berjalan di LoanConfirmService dengan tanda tangan LibNetSignGenerator.
  • Interpretasi / Perlu Konfirmasi Product Owner (Unverified):
  • Algoritma pasti credit scoring di server (kriteria apa yang membuat seorang nasabah mendapat limit Rp 1 juta vs Rp 5 juta) berada di backend dan tidak dapat dilihat dari source code klien.

🔬 G. Practical Example: Pemilihan Voucher di Alur Konfirmasi

Pengguna dapat memilih kupon diskon di IDVoucherSelectViewController. Kupon memiliki aturan validitas:

  • Hanya dapat digunakan jika nominal pinjaman memenuhi syarat minimal (minApplyAmount).
  • Hanya dapat digunakan sebelum tanggal kedaluwarsa kupon (expireTime).

Presenter menghitung pengurangan biaya:

Total Biaya Layanan = Biaya Layanan Normal - Nilai Kupon

dan mengupdate label pada LoanConfirmViewController_Rx secara reaktif.

⚠️ H. Common Mistakes & Debugging

  • Mengabaikan Kode Error Spesifik KYC:
  • Endpoint OCR sering kali mengembalikan error kode jika foto KTP buram atau terpotong. Selalu pastikan error message dari server (msg) ditampilkan ke toast pengguna agar mereka tahu harus mengambil foto ulang dengan lebih jelas.
  • Kondisi Balapan pada Polling Kuota:
  • Memulai polling baru tanpa menghentikan timer polling sebelumnya dapat memicu request ganda ke server. Selalu panggil stopPolling() sebelum memulai siklus polling baru.

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: State Mutation Tersebar & Kurangnya Single Source of Truth

Status transaksi pinjaman dan otentikasi disimpan di beberapa singleton berbeda secara terpisah, rentan memicu race condition dan state inconsistency antar tab.

⚠️ Smells 2: Kurangnya Abstraksi Domain Layer (Business Logic Terikat ke UI)

Logika validasi kredit dan kalkulasi bunga dilakukan langsung di lapisan presentasi tampilan, menyulitkan pemeliharaan dan pengujian regresi.

🚀 Blueprint Refactoring Standar Industri: Pola Clean Architecture Use Case (Domain Interactor Pattern)

Mengisolasi logika bisnis finansial ke dalam Use Case murni yang bebas dari UIKit atau Widget Flutter, menjamin 100% testability dan integritas transaksi.

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol CalculateRepaymentUseCase {
    func execute(loanAmount: Double, tenorDays: Int) -> RepaymentCalculation
}

public final class DefaultCalculateRepaymentUseCase: CalculateRepaymentUseCase {
    public func execute(loanAmount: Double, tenorDays: Int) -> RepaymentCalculation {
        // Business rule murni terisolasi dari UI
        return RepaymentCalculation(principal: loanAmount, interest: loanAmount * 0.003 * Double(tenorDays))
    }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
