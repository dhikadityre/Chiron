02 — Authentication & Session Flow

Alur Otentikasi & Sesi Pengguna

📚 Modul: 02-authentication-and-session-flow 🎯 Scope: SAMIR Mobile (iOS Native UIKit & FChannel) ⏱️ Estimasi: 20 Menit 🏷️ Git Branch: learn/iOS-Arch

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumen ini menjelaskan secara teknis dan mendalam alur autentikasi, siklus hidup sesi, mekanisme pengiriman dan verifikasi OTP, proteksi 2FA, enkripsi data sesi ke disk menggunakan CryptoKit.AES.GCM, hingga sinkronisasi sesi ke modul Flutter Hybrid.

Status Verifikasi: [Verified] (diverifikasi langsung dari IDLoginManager.swift, IDLoginPresenter.swift, IDLogin_service.swift, dan IDNLoginViewController.swift).

🎯 A. Learning Objective

Setelah mempelajari dokumen ini, pembaca akan mampu:

  1. Menelusuri alur otentikasi sejak user menekan tombol login hingga sesi tersimpan secara aman di sandbox.
  2. Memahami mekanisme A/B testing tampilan halaman login (isNewLoginPage()).
  3. Menjelaskan bagaimana staticKey diperoleh saat login dan mengapa kunci ini mutlak diperlukan oleh seluruh panggilan API berikutnya.
  4. Memahami implementasi enkripsi AES-GCM 256-bit pada file penyimpanan idn_userFile.plist.
  5. Memahami alur pembersihan sesi saat user melakukan logout manual atau saat sesi kedaluwarsa.

📋 B. Prerequisites

  • Sudah membaca 01-user-journey-overview.md.
  • Mengetahui konsep kriptografi simetris (AES-GCM) dan autentikasi dua faktor (2FA).

💡 C. Simple Explanation (Analogi Kunci Kamar Hotel Pintar)

Bayangkan Anda menginap di hotel pintar modern:

  1. Lobi Resepsionis (Form Login OTP): Anda memberikan nomor telepon dan menerima kode rahasia melalui SMS/WhatsApp untuk membuktikan bahwa Anda pemilik nomor tersebut.
  2. Kartu Kunci Digital (staticKey): Setelah resepsionis memverifikasi kode Anda, resepsionis tidak memberi Anda kunci fisik biasa, melainkan kartu chip pintar (staticKey).
  3. Membuka Semua Pintu (Tanda Tangan API / Signature): Setiap kali Anda ingin masuk ke kamar, lift, atau kolam renang (Request Endpoint Pinjaman), sensor hotel mewajibkan kartu chip pintar tersebut ditempelkan (sign dihitung menggunakan staticKey). Tanpa kartu chip ini, pintu mana pun tidak akan terbuka!
  4. Brankas Kamar (Enkripsi Disk idn_userFile.plist): Informasi pribadi Anda (nama, ID nasabah) disimpan di dalam brankas besi kamar yang dikunci rapat dengan kode sandi khusus perangkat (CryptoKit AES-GCM).

1. Inisiasi Login & A/B Testing Tampilan

Path: 🦊 ios/IDSamirLoan/Application/SamirLoginModule/Classes/IDPresenter/IDLoginManager.swift learn/iOS-Arch ↗

Aplikasi memiliki konfigurasi A/B testing dinamis untuk halaman login dari endpoint app/config/abtest/loginPage:

func __loginAction(fromVC: UIViewController) {
    let containerVC = IDContainerViewController()
    self.currentVC = containerVC
    // ...
    if isNewLoginPage() {
        let loginVC = LoginViewV2Controller()
        let nav = IDLoginNavViewController.init(rootViewController: loginVC)
        self.currentVC?.present(nav, animated: true)
    } else {
        let loginVC = IDNLoginViewController()
        let nav = IDLoginNavViewController.init(rootViewController: loginVC)
        self.currentVC?.present(nav, animated: true)
    }
}

2. Request OTP & Penanganan Multi-Channel

User dapat meminta OTP melalui 3 channel:

  • SMS: Default (type: .sms), memanggil customer/v2/sendSmsCode.
  • WhatsApp: Jika SMS terkendala (type: .whatsapp).
  • Voice Call: Panggilan telepon otomatis yang membacakan kode (type: .voice).

Setelah OTP dikirim, presenter mencatat timestamp cooldown di getCodeTimerStamp untuk mencegah user melakukan spam tombol OTP sebelum 60 detik berlalu.

3. Struktur Model Sesi (`IDLoginCodeModel`)

Setelah verifikasi sukses, backend mengembalikan objek sesi penting:

  • mid: Master Identifier akun nasabah.
  • userNo: Nomor unik pengguna di core banking.
  • mobile: Nomor telepon yang terdaftar.
  • staticKey: Kunci rahasia dinamis yang wajib digunakan sebagai seed untuk menandatangani semua request HTTP berikutnya!

4. Penyimpanan Sesi Aman (`CryptoKit.AES.GCM`)

Path: 🦊 ios/IDSamirLoan/Application/SamirLoginModule/Classes/IDPresenter/IDLoginManager.swift learn/iOS-Arch ↗

Alih-alih menyimpan token di UserDefaults (yang rentan diintip di perangkat yang ter-jailbreak), aplikasi mengenkripsi seluruh model data menggunakan AES-GCM 256-bit:

public func saveUserModel(_ model: IDLoginCodeModel) {
    do {
        // 1. Serialisasi model ke data binary via NSKeyedArchiver
        let data = try NSKeyedArchiver.archivedData(withRootObject: model as Any, requiringSecureCoding: false)
        
        // 2. Enkripsi menggunakan CryptoKit AES-GCM
        let encryptedData = try encryptUserModelData(data)
        
        // 3. Simpan di ApplicationSupportDirectory (idn_userFile.plist)
        let url = NSURL.fileURL(withPath: getUseFilePah())
        try encryptedData.write(to: url)

        self.userModel = model
        
        // 4. Bersihkan kunci plaintext lama dari UserDefaults demi keamanan
        UserDefaults.cz.remove(IDStorageKey.idn_mid)
        UserDefaults.cz.remove(IDStorageKey.idn_mobile)
        
        // 5. Daftarkan identitas user ke SDK analitik
        IDAppsFlyerManager.shared.setAFCustomerId(model.midStr)
        IDTiktokManager.shared.identify(externalId: model.midStr)
        TYUtils.setUserIdentifier(model.midStr)
    } catch {
        CZPrint("userModel archive error", error)
    }
}

private func userModelEncryptionKey() -> SymmetricKey {
    // Kunci simetris diturunkan dari SHA256 Bundle Identifier
    let keyMaterial = "IDSamirLoan.LoginUser.AES256.v1.\(Bundle.cz.appBundleIdentifier)"
    let digest = SHA256.hash(data: Data(keyMaterial.utf8))
    return SymmetricKey(data: Data(digest))
}

File yang disimpan memiliki header penanda: ID_LOGIN_USER_AES256_V1\n. Saat aplikasi dibuka kembali, __decodeUserModel() membaca file ini dan mendekripsinya secara otomatis.

5. Alur Logout Manual

Path: 🦊 ios/IDSamirLoan/Application/SamirLoginModule/Classes/IDPresenter/IDLoginManager.swift learn/iOS-Arch ↗

Ketika user menekan tombol "Keluar Akun" di halaman Pengaturan:

  1. Panggil endpoint server customer/cancel untuk membatalkan token di database backend.
  2. removeUserInfoWhenLoginOut():
  • Menghapus file idn_userFile.plist dari direktori ApplicationSupport dan Caches.
  • Menghapus BIZ_ID dan countdown OCR dari UserDefaults.
  • Mengosongkan static_key di IDNetworkManager.
  • Memanggil IDTiktokManager.shared.logout() dan TYUtils.clearTYUserIdentifier().
  1. Menyiarkan notifikasi IDN_SamirLoginModule_LoginOut_Notification.
  2. Seluruh tab (termasuk Flutter Mine dan Repay) mendengarkan notifikasi ini dan mereset tampilannya ke mode Tamu.

🪜 E. Step-by-Step Walkthrough: Alur Verifikasi Dua Langkah (2FA)

Jika sistem mendeteksi percobaan login dari perangkat baru atau lokasi yang tidak biasa, respon endpoint customer/login akan mengembalikan kode instruksi 2FA:

  1. Presenter login mendeteksi flag 2FA pada response server.
  2. Form login tidak ditutup, melainkan mendorong layar IDCodeViewController.
  3. Pengguna diminta memasukkan PIN keamanan atau kode otentikasi sekunder.
  4. Method postVerifyCode2FA dipanggil ke endpoint customer/verifyCode2FA.
  5. Jika verifikasi 2FA sukses, baru saveUserModel dieksekusi dan pengguna dianggap sah memiliki sesi aktif.

⚖️ F. Why It Matters: Peran Sentral `staticKey`

Senior engineer harus memahami bahwa staticKey adalah jantung dari seluruh komunikasi backend SAMIR:

  • Setiap kali Anda memanggil API apa pun di modul Pinjaman, Auth, atau Repay, pustaka IDNetworkSignatureHandler mengambil:
  IDNetworkManager.shared.static_key
  • Kunci ini dioper ke framework tertutup LibNetSignGenerator.framework untuk membuat string heksadesimal sign.
  • Jika staticKey kosong (karena belum login atau file sesi rusak), request bertanda tangan akan ditolak oleh backend dengan kode error autentikasi.

@objc private func handleLoginSuccessNotification() {

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: State Mutation Tersebar & Kurangnya Single Source of Truth

Status transaksi pinjaman dan otentikasi disimpan di beberapa singleton berbeda secara terpisah, rentan memicu race condition dan state inconsistency antar tab.

⚠️ Smells 2: Kurangnya Abstraksi Domain Layer (Business Logic Terikat ke UI)

Logika validasi kredit dan kalkulasi bunga dilakukan langsung di lapisan presentasi tampilan, menyulitkan pemeliharaan dan pengujian regresi.

🚀 Blueprint Refactoring Standar Industri: Pola Clean Architecture Use Case (Domain Interactor Pattern)

Mengisolasi logika bisnis finansial ke dalam Use Case murni yang bebas dari UIKit atau Widget Flutter, menjamin 100% testability dan integritas transaksi.

✅ Rekomendasi Solusi Arsitektur Bersih
public protocol CalculateRepaymentUseCase {
    func execute(loanAmount: Double, tenorDays: Int) -> RepaymentCalculation
}

public final class DefaultCalculateRepaymentUseCase: CalculateRepaymentUseCase {
    public func execute(loanAmount: Double, tenorDays: Int) -> RepaymentCalculation {
        // Business rule murni terisolasi dari UI
        return RepaymentCalculation(principal: loanAmount, interest: loanAmount * 0.003 * Double(tenorDays))
    }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
