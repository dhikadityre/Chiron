🎯 A. Learning Objective

Setelah mempelajari modul ini, Anda akan mampu:

  1. Menjelaskan 11 tahapan inisialisasi yang dijalankan di dalam IDSamirMainModule.application(_:didFinishLaunchingWithOptions:).
  2. Memahami implementasi fungsi FlutterEngineManager.shared.prewarm() dan mengapa precondition(hasRun) akan crash jika prewarm dilewati.
  3. Memahami bagaimana checkAppStartHide menentukan apakah user melihat IDLaunchViewController (countdown 3s) atau langsung masuk ke IDMainTabBarController.
  4. Menjelaskan bagaimana request konfigurasi aplikasi (app-configuration) diambil pada applicationDidBecomeActive untuk memperbarui pengaturan startup berikutnya.
  5. Memahami mekanisme eksekusi deep link tertunda (pending deep link) melalui Samir_DeepLink_Str setelah peluncuran selesai.

📋 B. Prerequisites

  • Sudah membaca fondasi siklus hidup aplikasi di 01-ios-entry-point.md dan 02-application-lifecycle.md.
  • Memahami konsep UIWindow dan hierarki rootViewController pada UIKit iOS.

💡 C. Simple Explanation (Analogi Masuk ke Toko Perhiasan)

Bayangkan Anda mengunjungi sebuah toko perhiasan eksklusif di pusat kota:

  1. Pintu otomatis terbuka: Petugas menyambut kedatangan Anda (application(_:didFinishLaunchingWithOptions:)).
  2. Sistem pendukung dinyalakan di latar belakang: Petugas mengaktifkan AC, lampu etalase, dan kamera keamanan (initEnvironment, IDNetworkManager, dan FlutterEngineManager.shared.prewarm() dihidupkan sebelum pengunjung melangkah ke dalam).
  3. Papan iklan promosi 3 detik di depan pintu (IDLaunchViewController):
    • Jika Anda adalah pelanggan VIP yang sudah pernah menyetel opsi "Lewati Iklan" di kunjungan sebelumnya (APP_Start_Hide == "1" di cache UserDefaults), papan iklan langsung disingkirkan.
    • Jika papan iklan aktif, Anda bisa menunggu 3 detik atau menekan tombol "Lewati Ns".
  4. Pintu lobi utama terbuka penuh (IDMainTabBarController): Menampilkan 3 etalase utama (Etalase Pinjaman Native, Etalase Tagihan Flutter, dan Meja Layanan Nasabah Flutter).
  5. Membawa kupon khusus dari luar (Deep Link): Jika Anda datang membawa kupon promosi dari SMS/WhatsApp, staf toko menahan kupon tersebut di saku (Samir_DeepLink_Str), lalu begitu Anda selesai melewati pintu depan, staf langsung mengantar Anda ke etalase yang tertera di kupon.

1. Inisialisasi Cold-Start IDSamirMainModule: Urutan Eksekusi 11 SDK & Penyiapan Runtime Sistem

Ketika aplikasi pertama kali dibuka (Cold-Start), method berikut dipanggil oleh CZAppDelegate:

public func application(_ application: UIApplication, didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey : Any]? = nil) -> Bool {

1.b. Pembedahan Mendalam FlutterEngineManager: Prewarming Runtime Dart VM & Penjagaan Fatal Crash Precondition

Mengapa tahap inisialisasi di IDSamirMainModule wajib memanggil FlutterEngineManager.shared.prewarm()? Mari kita buka implementasi aslinya di 🦊 FlutterEngineManager.swift — prewarm() & Engine Lifecycle learn/iOS-Arch ↗ : 

public final class FlutterEngineManager {
    public static let shared = FlutterEngineManager()

    // 1. Single Engine instance yang dipakai bersama oleh seluruh layar Flutter
    private let engine = FlutterEngine(name: "samir_single_flutter_engine")
    private var viewController: SamirFlutterViewController?
    private weak var persistentContainerView: UIView?
    private var hasRun = false

    private init() {}

    /// Starts the single engine before the persistent host is installed.
    public func prewarm() {
        startEngineIfNeeded()
        inactive()
    }

    private func startEngineIfNeeded() {
        assert(Thread.isMainThread, "FlutterEngine must be started on the main thread")
        guard !hasRun else { return }

        // Memulai eksekusi Dart VM dan me-load entrypoint awal di route '/root'
        hasRun = engine.run(withEntrypoint: nil, initialRoute: "/root")
        guard hasRun else {
            assertionFailure("Failed to start the single FlutterEngine")
            return
        }

        // Memasang binary messenger handler untuk komunikasi 2 arah Native <-> Flutter
        FlutterNativeChannel.shared.setup(with: engine.binaryMessenger)
        GeneratedPluginRegistrant.register(with: engine)
    }

    public func inactive() {
        guard hasRun else { return }
        // Mengistirahatkan rendering Flutter sampai user membuka Tab Tagihan / Profil
        engine.lifecycleChannel.sendMessage("AppLifecycleState.inactive")
    }
}
💥 Penjagaan Kritis (Assertion & Precondition Fatal Crash)

Di dalam fungsi sharedViewController() pada FlutterEngineManager.swift, arsitek SAMIR memasang penjagaan precondition ketat untuk mencegah container Flutter dimuat sebelum engine siap:

🦊 FlutterEngineManager.swift — sharedViewController() learn/iOS-Arch ↗ 
private func sharedViewController() -> SamirFlutterViewController {
    precondition(
        hasRun,
        "FlutterEngineManager.prewarm() must run before installing the Flutter host"
    )
    if let viewController {
        return viewController
    }
    let viewController = SamirFlutterViewController(
        engine: engine,
        nibName: nil,
        bundle: nil
    )
    self.viewController = viewController
    return viewController
}

Jika pemanggilan FlutterEngineManager.shared.prewarm() pada tahap startup di IDSamirMainModule dilewati atau gagal dieksekusi, maka begitu IDMainTabBarController dimuat dan memanggil installPersistentRoot, aplikasi akan seketika mengalami Fatal Crash karena hasRun masih bernilai false!

2. Logika Pemilihan Layar Awal (initWindow & checkAppStartHide): Evaluasi Cache Lokal vs Remote Config

Method berikut menentukan apakah pengguna harus menunggu countdown 3 detik di IDLaunchViewController atau langsung dialihkan ke IDMainTabBarController:

🦊 IDSamirMainModule.swift — initWindow() & checkAppStartHide() learn/iOS-Arch ↗ 
private func initWindow(_ application: UIApplication) {
    if let window = application.delegate?.window {
        window?.backgroundColor = .white
        if checkAppStartHide() {
            changeMainRootViewController(window: window)
        } else {
            changeLaunchViewController(window: window)
        }
    }
}

private func changeMainRootViewController(window: UIWindow?) {
    window?.rootViewController = IDMainTabBarController()
    window?.makeKeyAndVisible()
}

private func changeLaunchViewController(window: UIWindow?) {
    launchViewController = IDLaunchViewController()
    window?.rootViewController = launchViewController
    launchViewController?.launchProtocol = self
    window?.makeKeyAndVisible()
}

func checkAppStartHide() -> Bool {
    // 1. Periksa cache lokal di UserDefaults
    if let startHide = UserDefaults.standard.string(forKey: "APP_Start_Hide") {
        if startHide == "1" { return true }
        return false
    }
    // 2. Periksa cache konfigurasi server jika ada
    guard let appStartHide = IDServiceManager.mainService()?.getAppConfig()?.appStartHide else {
        return false
    }
    return appStartHide == "1"
}

3. Sinkronisasi Latar Belakang (applicationDidBecomeActive): Pembaruan Konfigurasi Global & Reaktivasi SDK

Method ini dieksekusi setiap kali aplikasi masuk ke foreground (baik cold-start maupun kembali dari background):

🦊 IDSamirMainModule.swift — applicationDidBecomeActive(_:) learn/iOS-Arch ↗ 
public func applicationDidBecomeActive(_ application: UIApplication) {
    // Mengambil app-configuration terbaru tanpa tanda tangan (unsigned)
    IDMainManager.shared.requestAppConfig()
    AppConfigUtil.shared.requestConfig()

    IDAppsFlyerManager.shared.applicationDidBecomeActive(application)
    AppEvents.shared.activateApp()
    IDCustomPointManager.refreshConfig()
}

API endpoint app-configuration mengembalikan parameter global seperti appStartHide, nomor WhatsApp Customer Service, tautan FAQ, dan konfigurasi A/B test login. Nilai appStartHide langsung disimpan ke UserDefaults.standard.set(..., forKey: "APP_Start_Hide") sehingga peluncuran berikutnya dapat langsung melewati splash screen.

📊 Sequence Diagram: Startup Sequence & Initial Routing Lifecycle
sequenceDiagram autonumber participant OS as iOS System participant Main as IDSamirMainModule participant FEng as FlutterEngineManager participant Launch as IDLaunchViewController participant Tab as IDMainTabBarController participant Deep as Deep Link Processor OS->>Main: application(_:didFinishLaunchingWithOptions:) Main->>FEng: prewarm() (Booting Dart VM di background) Main->>Main: checkAppStartHide() alt appStartHide == "1" (Sudah di-cache di UserDefaults) Main->>Tab: window.rootViewController = IDMainTabBarController() else appStartHide == "0" / Belum ada cache Main->>Launch: window.rootViewController = IDLaunchViewController() Note over Launch: Hitung mundur 3 detik / User tap "Lewati Ns" Launch-->>Main: finishLaunch() dipanggil via protokol Main->>Tab: window.rootViewController = IDMainTabBarController() end Tab->>Tab: installPersistentFlutterHost() & pasang 3 tab native Main->>Deep: Proses deep link tertunda (Samir_DeepLink_Str) jika ada
  1. Inisialisasi Dasar: Environment dimuat, jaringan disiapkan, dan FlutterEngineManager.shared.prewarm() mem-booting single runtime engine Flutter agar siap pakai.
  2. Evaluasi Tampilan Awal: Sistem memeriksa kunci APP_Start_Hide pada UserDefaults.
  3. Penyajian Splash: Jika belum disetel skip, layar splash tampil selama 3 detik.
  4. Transisi ke Tab Bar: Root window diganti ke IDMainTabBarController. TabBar memasang 3 tab native dan meng-embed view kontainer persisten Flutter di bawah tab bar.
  5. Eksekusi Deep Link Tertunda: Jika aplikasi dibuka melalui link atribusi AppsFlyer saat aplikasi dalam kondisi mati (cold start), link disimpan sementara di UserDefaults (Samir_DeepLink_Str) dan baru didispatch ke router setelah finishLaunch() selesai.

⚡ F. Why It Matters (Trade-Offs & Catatan Arsitektur)

  • Mengapa Prewarm Flutter Dilakukan di Startup?
    Memulai FlutterEngine membutuhkan waktu komputasi (spin up Dart VM sekitar 200–400ms). Dengan memanggil FlutterEngineManager.shared.prewarm() saat startup native, pengguna tidak akan merasakan lag atau kedipan layar kosong putih/hitam ketika berpindah ke Tab Tagihan atau Tab Profil.
  • Mengapa Request app-configuration Ditaruh di applicationDidBecomeActive?
    Setiap kali aplikasi kembali dari background ke foreground, status konfigurasi server (misal: pengumuman darurat, pemeliharaan sistem, atau pembaruan nomor kontak darurat) harus selalu terbarui tanpa mengharuskan pengguna me-restart aplikasi.

🧪 G. Practical Example (Studi Kasus Penanganan Deep Link Cold Start)

Misalkan pengguna mengklik tautan promosi SMS samir://repay/historyOrder saat aplikasi sedang mati total:

  1. iOS membangunkan aplikasi via method application(_:open:options:) atau AppsFlyer delegate.
  2. IDSamirMainModule.didResolveDeepLink menerima link tersebut.
  3. Karena tab bar belum siap dan user belum tentu login, link disimpan sementara di UserDefaults.standard.set(link, forKey: "Samir_DeepLink_Str").
  4. Setelah finishLaunch() selesai dan pengguna terverifikasi login, method finishLaunch() membaca kembali cache tersebut dan mengeksekusi IDRouterManager.id_perfromWithURLString(...) untuk mengantar user langsung ke layar riwayat pinjaman.

⚠️ Splash Screen Terus Muncul Berulang Kali di Staging

Penyebab: Endpoint app-configuration di environment TEST mengembalikan appStartHide = "0" atau koneksi staging timeout.
Pengecekan: Periksa isi UserDefaults.standard.string(forKey: "APP_Start_Hide") via debugger LLDB dengan perintah:
po UserDefaults.standard.string(forKey: "APP_Start_Hide")

⚠️ Flutter Tab Berkedip Hitam / Putih Saat Pertama Kali Dibuka

Pengecekan: Pastikan pemanggilan FlutterEngineManager.shared.prewarm() tetap dieksekusi di dalam IDSamirMainModule.swift sebelum initWindow() dijalankan.

🏛️ Bagian 2: Chiron Architecture Lab (SOLID Audit & Refactoring)

Senior Architect

Setelah menguasai fakta dan alur kode nyata di Bagian 1, mari kita audit kualitas arsitektur inisialisasi startup SAMIR iOS menggunakan standar industri modern (SOLID, Clean Architecture, Testability).

🏛️ Audit SOLID & Clean Architecture: Menemukan 3 Titik Lemah Kritis pada IDSamirMainModule Existing

⚠️ Smells 1: Pelanggaran Keras Single Responsibility Principle (SRP)

Class IDSamirMainModule bertindak sebagai God Object Coordinator. Class ini memikul 5 tanggung jawab yang sama sekali berbeda:

  • Inisialisasi APM, Crash, dan SDK Pelacak Pihak Ketiga (Tingyun, Facebook, TikTok, TrustDecision).
  • Konfigurasi hierarki UIWindow UIKit (mengganti Root ViewController).
  • Manajemen state persistensi dan cache UserDefaults (APP_Start_Hide, Samir_DeepLink_Str).
  • Delegasi protokol push notification Apple (APNs) dan Firebase Messaging.
  • Parsing deep link atribusi dan routing URL scheme.

Dampak: Setiap kali ada penambahan SDK analitik baru atau perubahan flow splash screen, file monolitik ini harus diedit, meningkatkan risiko regresi bagi seluruh siklus startup aplikasi.

⚠️ Smells 2: Pelanggaran Dependency Inversion (DIP) & 0% Testability

Modul utama terikat erat (tightly-coupled) pada implementasi konkret static singleton pihak ketiga: TYUtils.initTY(), FlutterEngineManager.shared, IDNetworkManager.initNetwork(), AppsFlyerLib.shared(), dan UserDefaults.standard.

Dampak: Tingkat Testability kode ini adalah 0% (Untestable). Anda tidak dapat menulis Unit Test di XCTest untuk menguji logika penentuan rute startup tanpa memicu koneksi HTTP sungguhan, inisialisasi framework Tingyun, dan pencemaran analitik produksi.

⚠️ Smells 3: Main Thread Congestion & Launch Latency

Seluruh 11 langkah inisialisasi dijalankan secara sinkron pada Main Thread sebelum method mengembalikan nilai true. Jika salah satu SDK (misal: pembacaan disk config atau inisialisasi kriptografi) mengalami lag 150ms, waktu peluncuran aplikasi (Time To First Meaningful Paint) akan melonjak drastis.

🚀 Blueprint Refactoring Standar Industri: Mengubah God Object Menjadi Pipeline Composite Startup Task yang 100% Mockable

Standar arsitektur industri (Google, Apple, Uber) menyelesaikan inisialisasi aplikasi monolitik menggunakan pola Composite Startup Task Pipeline.

✅ Blueprint Solusi: Abstraksi AppStartupTask Protocol

Pisahkan setiap inisialisasi SDK menjadi unit task independen yang terisolasi dan mengadopsi satu protokol kontrak: 

import Foundation
import UIKit

// 1. Protokol Kontrak Task Peluncuran
public enum TaskExecutionQueue {
    case mainQueueSync
    case backgroundAsync
}

public protocol AppStartupTask {
    var identifier: String { get }
    var executionQueue: TaskExecutionQueue { get }
    func execute(with application: UIApplication, launchOptions: [UIApplication.LaunchOptionsKey: Any]?)
}

// 2. Concrete Task: Prewarm Flutter Engine
public final class PrewarmFlutterEngineTask: AppStartupTask {
    private let engineManager: FlutterEngineManagerProtocol
    
    public init(engineManager: FlutterEngineManagerProtocol = FlutterEngineManager.shared) {
        self.engineManager = engineManager
    }
    
    public var identifier: String { "PrewarmFlutterEngineTask" }
    public var executionQueue: TaskExecutionQueue { .mainQueueSync }
    
    public func execute(with application: UIApplication, launchOptions: [UIApplication.LaunchOptionsKey : Any]?) {
        engineManager.prewarm()
    }
}

// 3. Concrete Task: Setup Analytics SDKs (Background Queue)
public final class AnalyticsStartupTask: AppStartupTask {
    public var identifier: String { "AnalyticsStartupTask" }
    public var executionQueue: TaskExecutionQueue { .backgroundAsync }
    
    public func execute(with application: UIApplication, launchOptions: [UIApplication.LaunchOptionsKey : Any]?) {
        // Facebook, AppsFlyer, TikTok dieksekusi di background thread
        Settings.shared.isAdvertiserTrackingEnabled = true
    }
}

// 4. Coordinator Bersih & 100% Mockable di XCTest
public final class AppStartupCoordinator {
    private let tasks: [AppStartupTask]
    
    public init(tasks: [AppStartupTask]) {
        self.tasks = tasks
    }
    
    public func launch(application: UIApplication, options: [UIApplication.LaunchOptionsKey: Any]?) {
        for task in tasks {
            switch task.executionQueue {
            case .mainQueueSync:
                task.execute(with: application, launchOptions: options)
            case .backgroundAsync:
                DispatchQueue.global(qos: .userInitiated).async {
                    task.execute(with: application, launchOptions: options)
                }
            }
        }
    }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Di unit test XCTest, Anda cukup menyuntikkan array MockStartupTask tanpa memicu framework analitik produksi.
  • Open/Closed Principle (OCP): Menambah SDK baru hanya memerlukan pembuatan class baru tanpa mengubah kode IDSamirMainModule.
  • Performa Startup Kilat: Task analitik non-kritis langsung dialihkan ke background thread.
