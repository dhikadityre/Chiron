Core Knowledge

Dokumentasi ini memberikan gambaran komprehensif mengenai peran modul SAMIR Flutter (flutter_app_project) di dalam ekosistem aplikasi mobile finansial SAMIR P2P Lending, konsep integrasi Add-to-App, pembagian tanggung jawab antara Native dan Flutter, serta profil teknis modul.

Status Verifikasi: [Verified] (diverifikasi langsung dari 🦊 flutter/pubspec.yaml learn/Flutter-Arch ↗, 🦊 flutter/lib/main.dart learn/Flutter-Arch ↗, dan 🦊 ios/Podfile learn/Flutter-Arch ↗).

🎯 A. Learning Objective

Setelah menyelesaikan dokumen ini, pembaca akan mampu:

  1. Menjelaskan peran modul Flutter SAMIR sebagai modul Add-to-App yang di-embed ke dalam aplikasi host native iOS dan Android.
  2. Mengidentifikasi fitur dan halaman mana saja yang didelegasikan ke Flutter (Tab Tagihan/Repay dan Tab Saya/Mine).
  3. Menyebutkan profil teknis modul (Nama paket, versi Flutter/Dart SDK, orientasi, dan bahasa antarmuka).
  4. Memahami batasan dan interaksi modul Flutter dengan aplikasi host native.

📋 B. Prerequisites

Tidak ada prasyarat teknis khusus. Pembaca hanya perlu memahami konsep dasar mobile app development dan arsitektur hybrid.

💡 C. Simple Explanation (Analogi & Konsep Sederhana)

Bayangkan sebuah pusat perbelanjaan modern (Aplikasi Host Native):

  • Lantai 1 (Beranda / Pengajuan Pinjaman) dan Ruang Verifikasi KTP (e-KYC) dikelola langsung oleh tim internal gedung dengan standar pengamanan ketat (Native Swift di iOS dan Native Kotlin di Android).
  • Namun, Layanan Pelanggan (Saya / Mine) dan Loket Kasir / Tagihan (Repay) menggunakan sistem waralaba yang terstandar dari mitra spesialis (Modul Flutter).
  • Pengunjung gedung tidak menyadari perbedaan ini karena loket tersebut terpasang rapi di dalam gedung tanpa sekat yang mencolok.

Dengan pendekatan Flutter Add-to-App, tim engineering SAMIR tidak perlu menulis ulang logika perhitungan denda, daftar tagihan, nomor virtual account, dan menu bantuan pengguna dua kali untuk iOS dan Android. Satu codebase Flutter melayani kedua platform secara presisi.

2. Pembagian Tanggung Jawab Fitur (Native vs Flutter)

Aplikasi SAMIR memiliki 3 Tab utama di root dashboard:

┌────────────────────────────────────────────────────────┐
│                   IDMainTabBarController               │
├───────────────────┬───────────────────┬────────────────┤
│      Tab 0        │      Tab 1        │      Tab 2     │
│  Beranda (Home)   │  Tagihan (Repay)  │   Saya (Mine)  │
│   [Native Swift]  │  [Flutter Engine] │ [Flutter Engine│
└───────────────────┴───────────────────┴────────────────┘
  • Tab 0 (Beranda / Home):
  • Platform: Native Swift (IDHomeViewController).
  • Fungsi: Penilaian limit pinjaman, simulasi kredit, pengajuan awal, dan pengecekan verifikasi KYC.
  • Tab 1 (Tagihan / Repay):
  • Platform: Flutter Module (RepayHomePage).
  • Host Native: IDRepayViewController membungkus FlutterViewController.
  • Fungsi: Menampilkan daftar kontrak pinjaman yang sedang berjalan, status pelunasan, jadwal angsuran, nomor kode bayar / Virtual Account (VA), dan pop-up insentif pembayaran.
  • Tab 2 (Saya / Mine):
  • Platform: Flutter Module (MineHomePage).
  • Host Native: IDMineViewController membungkus FlutterViewController.
  • Fungsi: Profil nasabah, riwayat pesanan pinjaman (/samir/loan-record), daftar kupon (/samir/coupon/list), pusat bantuan FAQ (/samir/faq), pengaturan akun (samir://mine/setting), dan kanal pengaduan customer service.

🪜 E. Step-by-Step Walkthrough (Siklus Hidup Modul)

  1. Host Bootstrapping:

Saat aplikasi host (misal iOS) dinyalakan, IDSamirMainModule menginisialisasi singleton FlutterEngineManager dan menjalankan run(withEntrypoint: nil) untuk melakukan proses prewarming engine.

  1. Flutter Initialization:

Engine mengeksekusi main() di 🦊 flutter/lib/main.dart learn/Flutter-Arch ↗. Flutter menyiapkan binding, menginisialisasi environment, HTTP client, dan listener MethodChannel.

  1. Notify Native Ready:

Setelah frame pertama selesai digambar (WidgetsBinding.instance.endOfFrame), Flutter memanggil method channel flutterReady ke native host.

  1. Tab Attachment:

Ketika user membuka Tab Tagihan atau Tab Saya, UIViewController native hanya melampirkan view dari FlutterEngine yang sudah aktif, tanpa membuat ulang engine baru.

  1. Bidirectional Communication:

Jika user menekan menu yang membutuhkan aksi native (misal: verifikasi e-KTP atau pembukaan browser luar), Flutter mengirimkan sinyal navigasi ke host via FlutterNativeChannelRoute.openNativeRoute().

⚖️ F. Why It Matters (Trade-Offs & Implikasi Teknis)

  • Mengapa Single Engine Add-to-App?

Menjalankan dua engine Flutter terpisah untuk Tab 1 dan Tab 2 akan melipatgandakan penggunaan memori RAM (sekitar 30–50 MB per engine tambahan) dan menyebabkan inkonsistensi status login. Dengan menggunakan satu engine bersama yang dikendalikan oleh FlutterRootPage dan IndexedStack, penggunaan memori sangat hemat dan pergantian tab berlangsung instan (0 ms freeze).

  • Mengapa Sesi Otentikasi Dikuasai Native?

Aplikasi finansial menyimpan kredensial sensitif di iOS Keychain dengan enkripsi tingkat perangkat keras (CryptoKit AES-GCM). Flutter tidak menyimpan token secara permanen di storage lokal, melainkan menerima salinan data sesi di memori RAM via MethodChannel getRootPageData.

🔬 G. Practical Example (Skenario Penggunaan Nyata)

Ketika user telah login di Native Home (Tab 0) dan kemudian menekan Tab Tagihan (Tab 1):

  1. Native IDRepayViewController tampil di layar.
  2. Native mengirim pesan showFlutterRoute dengan rute /repay melalui MethodChannel.
  3. Flutter menerima pesan tersebut di FlutterNativeRouteDispatcher._showFlutterRoute() dan menginstruksikan FlutterRootController.select('/repay').
  4. IndexedStack di FlutterRootPage langsung menampilkan RepayHomePage dan memicu refresh data tagihan terbaru.

⚠️ H. Common Mistakes & Debugging

  • Kesalahan Menjalankan Flutter Secara Terpisah (flutter run):
  • Modul ini dirancang dengan asumsi host native menyediakan parameter perangkat dan environment via MethodChannel. Menjalankan modul secara standalone tanpa native host akan menggunakan data fallback (AppEnv.devAppId, host dummy).
  • Kesalahan State Desinkronisasi:
  • Jika token login di native telah di-refresh atau dihapus (logout), tetapi native lupa memanggil sinyal refresh ke Flutter, layar Flutter mungkin menampilkan data usang hingga sinyal refreshMineHome atau refreshRepayHome dipicu.

🏛️ Bagian 2: Architecture Lab, SOLID Audit & Retention Quizzes

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Keterikatan Kuat Antar Sub-Modul & Kurangnya Inversi Dependensi

Implementasi komponen sering mengasumsikan keberadaan lingkungan runtime tertentu tanpa kontrak antarmuka yang didefinisikan secara tegas.

⚠️ Smells 2: Risiko Regresi & Minimnya Kontrak Pengujian Terisolasi

Perubahan pada satu service atau helper berpotensi merusak fungsionalitas di modul lain karena tingginya kohesi tersembunyi antar file.

🚀 Blueprint Refactoring Standar Industri: Pola Service Locator & Interface Segregation (SOLID)

Menerapkan prinsip Interface Segregation (ISP) dan Dependency Injection agar setiap service hanya mengekspos metode yang relevan bagi kliennya.

✅ Rekomendasi Solusi Arsitektur Bersih
abstract class SessionContract {
  String? get userToken;
  bool get isLoggedIn;
}

class GlobalSessionManager implements SessionContract {
  @override
  String? userToken;
  @override
  bool get isLoggedIn => userToken != null && userToken!.isNotEmpty;
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
