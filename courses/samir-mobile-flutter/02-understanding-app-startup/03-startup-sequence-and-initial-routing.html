03 — Startup Sequence & Initial Routing

Penentuan Rute Awal Flutter

📚 Modul: 03-startup-sequence-and-initial-routing 🎯 Scope: SAMIR Mobile (Flutter Add-to-App & MethodChannel) ⏱️ Estimasi: 20 Menit 🏷️ Git Branch: learn/Flutter-Arch

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumentasi ini menjelaskan urutan boot modul SAMIR Flutter saat engine dihidupkan, bagaimana nilai rute awal dibaca dari host native melalui PlatformDispatcher.instance.defaultRouteName, logika penentuan rute di _initialLocation, serta pemrosesan permintaan rute dinamis melalui FlutterNativeRouteDispatcher._showFlutterRoute.

Status Verifikasi: [Verified] (diverifikasi langsung dari 🦊 flutter/lib/common/router/routers.dart learn/Flutter-Arch ↗ dan 🦊 flutter/lib/common/platform/flutter_native_route_dispatcher.dart learn/Flutter-Arch ↗).

🎯 A. Learning Objective

Setelah menyelesaikan dokumen ini, pembaca akan mampu:

  1. Memahami bagaimana host native menyalurkan rute awal (initial route) ke dalam Flutter Engine.
  2. Menganalisis fungsi _initialLocation di dalam routers.dart.
  3. Menjelaskan mengapa rute /mine dan /repay dialihkan ke rute internal /root (RoutePaths.rootContainer).
  4. Mengetahui struktur pesan showFlutterRoute dari native (route, presentation, requestId) dan bagaimana race condition dicegah.

📋 B. Prerequisites

Telah membaca 01-flutter-entry-point.md dan 02-module-lifecycle-and-host-sync.md.

💡 C. Simple Explanation (Analogi & Konsep Sederhana)

Bayangkan Anda menaiki lift di gedung bertingkat:

  • Jika penumpang menekan tombol lantai sebelum pintu lift tertutup (defaultRouteName), lift langsung meluncur ke lantai tersebut saat dinyalakan.
  • Jika penumpang menekan "Lantai Tagihan" atau "Lantai Profil", resepsionis lift menyadari bahwa kedua ruangan ini berada di dalam aula lantai dasar yang sama (/root). Lift membawa Anda ke aula tersebut, lalu membuka sekat partisi yang sesuai.
  • Jika ada banyak tombol lantai ditekan secara cepat berturut-turut oleh orang yang berbeda, sistem komputer lift mencatat nomor urut permintaan (requestId) dan hanya melayani permintaan yang paling mutakhir, mengabaikan perintah lama yang sudah terlambat.

💻 D. Actual Implementation (Bukti di Kode Sumber)

1. Logika Pembacaan _initialLocation

Pada 🦊 flutter/lib/common/router/routers.dart learn/Flutter-Arch ↗ (baris 50–65):

String get _initialLocation {
  final String route = PlatformDispatcher.instance.defaultRouteName;
  if (FlutterRootController.supports(route)) {
    FlutterRootController.select(route);
    NativeRouteChrome.setCurrentLocation(route);
    return RoutePaths.rootContainer;
  }
  if (route.startsWith('/') && route != '/') {
    // Keep the native chrome state aligned when iOS/Android starts Flutter
    // directly on a secondary route.
    NativeRouteChrome.setCurrentLocation(route);
    return route;
  }
  NativeRouteChrome.setCurrentLocation(RoutePaths.rootContainer);
  return RoutePaths.rootContainer;
}

Alur keputusan rute awal:

  1. Periksa defaultRouteName: Nilai ini dikirim oleh native saat memanggil FlutterEngine.run(withEntrypoint: nil, initialRoute: "/repay").
  2. Kondisi A (Root Tab Match): Jika rute adalah tab root (/mine atau /repay), panggil FlutterRootController.select(route) dan kembalikan /root. Ini memastikan FlutterRootPage dimuat dengan index tab yang benar.
  3. Kondisi B (Secondary Route): Jika rute adalah halaman khusus (misal deep link ke /mine/personal), buka rute tersebut secara langsung dan beri tahu NativeRouteChrome untuk menyembunyikan tab bar native.
  4. Kondisi Fallback: Jika tidak ada parameter atau bernilai /, buka /root.

2. Penanganan Panggilan Rute dari Host (showFlutterRoute)

Setelah engine berjalan, host native dapat meminta perpindahan rute kapan saja melalui method channel showFlutterRoute.

Diimplementasikan pada 🦊 flutter/lib/common/platform/flutter_native_route_dispatcher.dart learn/Flutter-Arch ↗ (baris 51–103):

static Future<Map<String, Object?>> _showFlutterRoute(Object? arguments) async {
  final _NativeRouteRequest? request = _NativeRouteRequest.from(arguments);
  if (request == null) {
    return const <String, Object?>{'frameReady': false};
  }

  if (request.isRoot) {
    return _showRootTab(request);
  }

  if (Routers.currentLocation == request.route) {
    await NativeRouteChrome.syncForRoutePath(request.route);
    return request.response(frameReady: true);
  }

  if (request.shouldReplace) {
    await Routers.go(request.route);
    return request.response(frameReady: true);
  }
  await Routers.push<void>(request.route);
  return request.response(frameReady: true);
}

3. Pencegahan Race Condition dengan _latestRootRequestId

Saat pengguna mengetuk tab Tagihan dan tab Saya secara bergantian dengan cepat di antarmuka native, event MethodChannel dapat tiba tidak berurutan karena latensi thread:

static Future<Map<String, Object?>> _showRootTab(_NativeRouteRequest request) async {
  final int requestId = request.requestId ?? ++_latestRootRequestId;
  if (requestId < _latestRootRequestId) {
    // Permintaan usang! Batalkan dan jangan ubah tab
    return <String, Object?>{'requestId': requestId, 'frameReady': false};
  }
  _latestRootRequestId = requestId;
  await Routers.go(request.route);

  WidgetsBinding.instance.ensureVisualUpdate();
  await WidgetsBinding.instance.endOfFrame;

  final bool isLatest = requestId == _latestRootRequestId;
  final bool isSelected = FlutterRootController.isSelected(request.route);
  if (isLatest && isSelected) {
    if (request.route == RoutePaths.mineHome) {
      FlutterNativePageSignal.refreshMineHome();
    } else if (request.route == RoutePaths.repayHome) {
      FlutterNativePageSignal.refreshRepayHome();
    }
  }
  return <String, Object?>{
    'requestId': requestId,
    'frameReady': isLatest && isSelected,
  };
}

⚖️ F. Why It Matters (Trade-Offs & Implikasi Teknis)

  • Mengapa Harus Ada requestId?

Pada sistem hybrid, thread UI iOS/Android dan thread Dart UI Flutter berjalan secara asynchronous. Jika user mengetuk Tab A lalu dengan cepat mengetuk Tab B, pesan Tab A bisa saja diproses setelah pesan Tab B jika terjadi antrean di message loop platform channel. Tanpa requestId, layar bisa melompat mundur secara keliru ke Tab A.

  • Mengapa Root Tab Menggunakan Routers.go Bukan Routers.push?

Menggunakan push untuk tab bar akan menumpuk halaman di atas halaman lain tanpa batas (stack leak), menghabiskan memori RAM. Sebaliknya, go membersihkan tumpukan rute child dan kembali ke kontainer utama /root.

🔬 G. Practical Example (Skenario Penggunaan Nyata)

Jika tim marketing mengirimkan push notification dengan deep link samir://repay, aplikasi native akan mengarahkan pengguna ke tab 1 dan mengirimkan pesan method channel:

{
  "route": "/repay",
  "presentation": "replace",
  "requestId": 104
}

Flutter menerima payload ini, memastikan 104 >= _latestRootRequestId, mengalihkan FlutterRootController ke /repay, memicu sinyal refreshRepayHome(), dan mengembalikan { "requestId": 104, "frameReady": true } ke native host.

⚠️ H. Common Mistakes & Debugging

  • Mendaftarkan Rute Root Langsung ke Daftar routes di GoRouter:
    • Jika /repay dan /mine dideklarasikan sebagai GoRoute terpisah yang masing-masing mengembalikan widget baru tanpa IndexedStack, setiap kali user berpindah tab, state form, scroll position, dan cache data akan musnah. Keduanya wajib dikonsolidasikan di bawah rute /root.

🏛️ Bagian 2: Architecture Lab, SOLID Audit & Retention Quizzes

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Pelanggaran SRP: God Object Coordinator pada Alur Startup

Class modul startup utama pada SAMIR Mobile Flutter menangani terlalu banyak tanggung jawab: registrasi APM, inisialisasi jaringan, pemanasan runtime engine, serta registrasi push notifications secara monolitik.

⚠️ Smells 2: Pelanggaran DIP: Keterikatan Statis Singleton (0% Unit Testability)

Komponen memanggil static shared singleton secara langsung tanpa melalui abstraksi antarmuka (Dependency Inversion Principle), membuat pengujian terisolasi di automated unit test menjadi mustahil tanpa memicu efek samping jaringan dan APM produksi.

🚀 Blueprint Refactoring Standar Industri: Penerapan Composite Startup Task Architecture

Memecah alur peluncuran aplikasi menjadi serangkaian task mandiri yang mengimplementasikan protokol tunggal (Open/Closed Principle) dan dapat dieksekusi secara terkoordinasi (sync/async).

✅ Rekomendasi Solusi Arsitektur Bersih
abstract class AppStartupTask {
  String get identifier;
  Future<void> execute();
}

class StartupTaskCoordinator {
  final List<AppStartupTask> tasks;
  StartupTaskCoordinator(this.tasks);

  Future<void> runAll() async {
    for (final task in tasks) {
      await task.execute();
    }
  }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
