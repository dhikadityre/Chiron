04 — Change Impact Analysis

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumentasi ini menyediakan panduan analisis dampak perubahan (Change Impact Analysis) dan daftar periksa wajib (pre-commit / pre-PR checklist) bagi engineer sebelum melakukan commit atau mengajukan pull request pada modul SAMIR Flutter (flutter_app_project).

Status Verifikasi: [Verified] (diverifikasi langsung dari inspeksi arsitektur hybrid Add-to-App monorepo SAMIR).

🎯 A. Learning Objective

Setelah menyelesaikan dokumen ini, pembaca akan mampu:

  1. Memprediksi radius dampak (blast radius) saat mengubah file tertentu di dalam modul Flutter.
  2. Memahami risiko perubahan pada layer Platform Bridge terhadap kompilasi native iOS dan Android.
  3. Menjalankan 5 langkah verifikasi lokal wajib sebelum membuat pull request.
  4. Mencegah regresi tanda tangan request yang dapat melumpuhkan seluruh transaksi API.

📋 B. Prerequisites

Telah membaca Level 1: Pondasi hingga Level 7: Debugging.

💡 C. Simple Explanation (Analogi & Konsep Sederhana)

Bayangkan merenovasi instalasi pipa gas di dalam gedung apartemen bertingkat:

  • Jika Anda hanya mengganti kran air di wastafel dapur sendiri (mengubah padding di mine_home_header.dart), dampaknya hanya terasa di dapur Anda sendiri.
  • Namun, jika Anda menyentuh katup pipa gas utama di basemen (sign_utils.dart atau flutter_native_channel.dart), kesalahan kecil pada drat pipa dapat mematikan pasokan gas ke seluruh 500 unit apartemen di gedung tersebut.
  • Dokumen ini adalah prosedur checklist teknisi sebelum memutar katup pipa utama gedung.

📌 E. Checklist Verifikasi Pra-Commit (Pre-PR Checklist)

Sebelum Anda membuat branch commit atau pull request ke develop / main, jalankan checklist 5 langkah berikut:

Langkah 1: Static Code Analysis

Pastikan tidak ada error tipe atau pelanggaran linter:

cd Mobile/Develop/samir-mobile-develop/flutter
flutter analyze

Kriteria Lolos: Terminal menampilkan No issues found!.

Langkah 2: Format Kode Seragam

Pastikan format indentasi Dart mengikuti standar tim:

dart format .

Langkah 3: Verifikasi Tanda Tangan Request (Kritis!)

Jika Anda menyentuh file di bawah common/http/ atau common/constants/:

  1. Jalankan aplikasi di simulator.
  2. Buka Tab Tagihan atau Tab Saya.
  3. Periksa konsol debug: pastikan API merespon dengan BaseResponse.code == '200'.
  4. Jika muncul error Sign Invalid atau Timestamp Invalid, jangan sekali-kali melakukan commit!

Langkah 4: Uji Sinkronisasi Tab Bar Native

  1. Buka Tab Saya (/mine) -> pastikan Tab Bar native tampil.
  2. Masuk ke halaman Verifikasi Data Diri (/mine/personal) -> pastikan Tab Bar native menghilang seketika tanpa kedipan.
  3. Tekan tombol Back -> pastikan Tab Bar native muncul kembali dengan mulus.

Langkah 5: Kompilasi Host iOS

Pastikan integrasi Add-to-App di sisi iOS tidak rusak akibat perubahan Flutter:

cd Mobile/Develop/samir-mobile-develop/ios
pod install
xcodebuild -workspace IDSamirLoan.xcworkspace -scheme TEST -configuration Debug -sdk iphonesimulator clean build CODE_SIGNING_ALLOWED=NO

Kriteria Lolos: ** BUILD SUCCEEDED **.

⚖️ F. Why It Matters (Trade-Offs & Implikasi Teknis)

  • Menghindari Kerusakan Kompilasi di CI/CD:

Pada repositori monorepo seperti SAMIR, pipeline GitLab CI akan menjalankan automated build untuk host iOS dan Android. Menambahkan dependensi Flutter baru tanpa memperbarui Podfile.lock di iOS akan menggagalkan pipeline seluruh tim mobile engineering.

  • Biaya Regresi di Lingkungan Produksi:

Bug pada file UI (seperti teks terpotong) dapat diperbaiki dengan cepat. Namun, bug pada sign_utils.dart yang lolos ke rilis App Store akan membuat ribuan nasabah tidak dapat membayar pinjaman atau melihat profil mereka, berpotensi memicu denda regulasi dari OJK.

⚠️ G. Common Mistakes & Debugging

  • Mengubah Nama Method Channel Hanya di Sisi Flutter:
  • Mengubah FlutterNativeChannelMethod.requestRepayBenefitPopup tanpa mengoordinasikan dengan engineer iOS yang memelihara FlutterNativeChannel+method.swift.
  • Melakukan Commit File .ios/ atau .android/:
  • File di dalam flutter/.ios/ dan flutter/.android/ bersifat lokal (git ignored). Jangan pernah memaksakan commit file-file ini ke git repo.

🧠 H. Knowledge Check

  1. File apa di modul Flutter yang memiliki tingkat risiko perubahan paling kritis terhadap seluruh API backend?
  2. Perintah terminal apa yang wajib dijalankan untuk memastikan kode Dart bebas dari peringatan linter?
  3. Mengapa penambahan plugin baru di pubspec.yaml mewajibkan eksekusi pod install di folder ios/?

Latihan Observasi:

Buka file 🦊 flutter/lib/common/router/route_paths.dart learn/Flutter-Arch ↗. Periksa apakah ada rute yang digunakan secara bersamaan oleh file lain di luar folder router/.

🏛️ Bagian 2: Architecture Lab, SOLID Audit & Retention Quizzes

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Keterikatan Kuat Antar Sub-Modul & Kurangnya Inversi Dependensi

Implementasi komponen sering mengasumsikan keberadaan lingkungan runtime tertentu tanpa kontrak antarmuka yang didefinisikan secara tegas.

⚠️ Smells 2: Risiko Regresi & Minimnya Kontrak Pengujian Terisolasi

Perubahan pada satu service atau helper berpotensi merusak fungsionalitas di modul lain karena tingginya kohesi tersembunyi antar file.

🚀 Blueprint Refactoring Standar Industri: Pola Service Locator & Interface Segregation (SOLID)

Menerapkan prinsip Interface Segregation (ISP) dan Dependency Injection agar setiap service hanya mengekspos metode yang relevan bagi kliennya.

✅ Rekomendasi Solusi Arsitektur Bersih
abstract class SessionContract {
  String? get userToken;
  bool get isLoggedIn;
}

class GlobalSessionManager implements SessionContract {
  @override
  String? userToken;
  @override
  bool get isLoggedIn => userToken != null && userToken!.isNotEmpty;
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.

🧠 Interactive Retention & Architectural Quiz

Uji pemahaman alur kode nyata dan keputusan arsitektur Anda:

Kuis 1 (Memory Recall): Berdasarkan standar Clean Architecture, apa peran utama dari domain layer pada modul FLUTTER?

Kuis 2 (Architectural Decision): Mengapa penerapan Dependency Inversion Principle (DIP) sangat krusial dalam pembuatan unit test?

Kuis 3 (Debugging & Maintenance): Apa keuntungan utama membatasi dependensi antar modul ke arah satu arah (Unidirectional Dependency)?
