01 — Error Handling

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumentasi ini menjelaskan strategi penanganan kesalahan (error handling) pada modul SAMIR Flutter (flutter_app_project), menguraikan hierarki eksepsi Dio di dalam 🦊 flutter/lib/common/http/http_client.dart learn/Flutter-Arch ↗, pembedaan antara kesalahan jaringan (transport error) dan kode error bisnis (business code), mekanisme notifikasi visual melalui Toast, serta penanganan error kritis 10006.

Status Verifikasi: [Verified] (diverifikasi langsung dari inspeksi kode 🦊 flutter/lib/common/http/http_client.dart learn/Flutter-Arch ↗ dan 🦊 flutter/lib/common/utils/toast.dart learn/Flutter-Arch ↗).

🎯 A. Learning Objective

Setelah menyelesaikan dokumen ini, pembaca akan mampu:

  1. Membedakan 3 tingkatan kesalahan: Transport Level (Dio), Protocol Level (HTTP Status), dan Application Business Level (BaseResponse.code).
  2. Menjelaskan logika fungsi _createErrorResponse() dalam membungkus DioException.
  3. Mengetahui cara kerja notifikasi visual showToast yang dapat dipanggil tanpa BuildContext.
  4. Menjelaskan penanganan kesalahan otentikasi (Error 10006) vs kesalahan validasi bisnis umum.

📋 B. Prerequisites

Telah membaca Level 6: Jaringan & Keamanan.

💡 C. Simple Explanation (Analogi & Konsep Sederhana)

Bayangkan Anda memesan makanan melalui telepon ke restoran:

  1. Kesalahan Jaringan (Transport Error): Sinyal telepon terputus atau nomor restoran sibuk (DioExceptionType.connectionTimeout). Anda tahu masalahnya ada pada saluran kabel telepon.
  2. Kesalahan Protokol (HTTP Error): Operator restoran mengangkat telepon tetapi salah menyambungkan ke saluran fax (HTTP 502 / 404).
  3. Kesalahan Bisnis (Business Error): Saluran telepon jernih, pesanan Anda diterima, namun koki mengatakan: "Maaf, menu sup ayam hari ini sudah habis" (BaseResponse.code != '200'). Telepon berhasil, tetapi transaksi tidak dapat diproses.

1. Tiga Tingkatan Kesalahan di SAMIR Flutter

│    - Ditangani oleh: _getResponse()                    │

2. Pembungkus Eksepsi Dio: _createErrorResponse()

File 🦊 flutter/lib/common/http/http_client.dart learn/Flutter-Arch ↗ (baris 151–183):

BaseResponse<dynamic> _createErrorResponse(dynamic error) {
  String errorCode;
  String errorMsg;

  if (error is DioException) {
    switch (error.type) {
      case DioExceptionType.badResponse:
        if (error.response != null && error.response!.data != null) {
          try {
            final dynamic data = error.response!.data;
            if (data is Map<String, dynamic>) {
              return BaseResponse<dynamic>.fromJson(data);
            }
          } catch (_) {
            // Fallback jika parsing JSON gagal
          }
        }
        errorCode = 'Network';
        errorMsg = error.message ?? 'unknown';
        break;
      default:
        errorCode = 'Network';
        errorMsg = error.message ?? 'unknown';
        break;
    }
  } else {
    errorCode = 'Network';
    errorMsg = error.toString();
  }

  return BaseResponse<dynamic>(code: errorCode, msg: errorMsg, data: null);
}

Keuntungan arsitektur ini:

  • Mengubah eksepsi tingkat rendah Dart yang berpotensi memicu unhandled crash menjadi objek BaseResponse yang ramah tipe data.
  • Layer Service tidak perlu menangani puluhan tipe exception yang berbeda; cukup memeriksa BaseResponse.code.

3. Filter Respon Bisnis: _getResponse()

Pada http_client.dart (baris 133–149):

dynamic _getResponse(Response<dynamic> response) {
  final BaseResponse<dynamic> baseResponse = BaseResponse<dynamic>.fromJson(
    response.data is Map<String, dynamic>
        ? response.data as Map<String, dynamic>
        : null,
  );
  if (baseResponse.code == '200') {
    // Sukses, kembalikan data payload
  } else {
    if (baseResponse.code == '10006') {
      Global.clearUser();
      Routers.gotoLogin();
    }
    showToast(baseResponse.msg);
  }
  return baseResponse.data;
}

4. Notifikasi Toast Global

File 🦊 flutter/lib/common/utils/toast.dart learn/Flutter-Arch ↗ memanfaatkan navigatorKey dari GoRouter:

  • showToast(String? message) dapat dipanggil dari mana saja di dalam kode Dart tanpa perlu meneruskan objek BuildContext.
  • Toast muncul di bagian tengah-bawah layar dengan latar belakang gelap transparan dan teks putih kontras tinggi selama 2 detik.

🪜 E. Step-by-Step Walkthrough: Penanganan Error Koneksi Terputus

  1. Pengguna membuka tab Tagihan saat berada di dalam terowongan kereta bawah tanah (sinyal hilang total).
  2. RepayHomeService mengeksekusi POST ke ServerApi.repayList.
  3. Dio mendeteksi socket gagal terhubung dan melempar DioExceptionType.connectionError.
  4. HttpClient.post menangkap error di blok catch (e).
  5. _createErrorResponse membungkus error menjadi BaseResponse(code: 'Network', msg: 'No internet connection').
  6. showToast('No internet connection') menampilkan pesan peringatan di layar.
  7. RepayHomePage mendeteksi data null dan menampilkan kartu status kosong dengan tombol "Coba Lagi" (AppRefreshIndicator).

⚖️ F. Why It Matters (Trade-Offs & Implikasi Teknis)

  • Menjamin UI Tidak Pernah Mengalami "Freeze":

Jika exception jaringan tidak ditangkap di layer client, Future di layer widget akan berada dalam status uncompleted atau melempar runtime error ke zona root (FlutterError.onError). Pengguna akan terjebak melihat spinner berputar tanpa henti. Dengan pola _createErrorResponse, loading overlay selalu dijamin tertutup di blok finally/interceptor.

🔬 G. Practical Example (Skenario Penggunaan Nyata)

Jika nasabah memasukkan nominal pembayaran melebihi sisa pokok pinjaman:

  • Backend merespon dengan status HTTP 200, tetapi payload:

{"code": "30041", "msg": "Nominal pembayaran melebihi total sisa pinjaman", "data": null}.

  • _getResponse() mendeteksi code != '200'.
  • Pesan "Nominal pembayaran melebihi total sisa pinjaman" langsung dimunculkan ke nasabah via Toast.
  • Nasabah langsung memahami kesalahan input tanpa kebingungan teknis.

⚠️ H. Common Mistakes & Debugging

  • Mengabaikan Respon Bernilai Null di Service:
  • Karena _getResponse() mengembalikan baseResponse.data yang dapat bernilai null saat error terjadi, class model yang mem-parsing data wajib memiliki factory null-safe: RepayHomeModel.fromJson(responseData is Map ? responseData : null).

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Keterikatan Kuat Antar Sub-Modul & Kurangnya Inversi Dependensi

Implementasi komponen sering mengasumsikan keberadaan lingkungan runtime tertentu tanpa kontrak antarmuka yang didefinisikan secara tegas.

⚠️ Smells 2: Risiko Regresi & Minimnya Kontrak Pengujian Terisolasi

Perubahan pada satu service atau helper berpotensi merusak fungsionalitas di modul lain karena tingginya kohesi tersembunyi antar file.

🚀 Blueprint Refactoring Standar Industri: Pola Service Locator & Interface Segregation (SOLID)

Menerapkan prinsip Interface Segregation (ISP) dan Dependency Injection agar setiap service hanya mengekspos metode yang relevan bagi kliennya.

✅ Rekomendasi Solusi Arsitektur Bersih
abstract class SessionContract {
  String? get userToken;
  bool get isLoggedIn;
}

class GlobalSessionManager implements SessionContract {
  @override
  String? userToken;
  @override
  bool get isLoggedIn => userToken != null && userToken!.isNotEmpty;
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
