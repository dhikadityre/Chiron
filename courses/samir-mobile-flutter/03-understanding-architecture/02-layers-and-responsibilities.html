📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumentasi ini merinci pembagian tanggung jawab dari setiap lapisan (layer) dalam arsitektur modul SAMIR Flutter (flutter_app_project), mendefinisikan batas kontrak (boundary) antar-lapisan, serta menguraikan class dan file konkret yang mengimplementasikannya.

Status Verifikasi: [Verified] (diverifikasi langsung dari inspeksi kode monorepo SAMIR di Mobile/Develop/samir-mobile-develop/flutter/lib).

🎯 A. Learning Objective

Setelah menyelesaikan dokumen ini, pembaca akan mampu:

  1. Menyebutkan 4 lapisan tanggung jawab utama dalam modul Flutter SAMIR.
  2. Memahami batas pemisah antara Presentation Layer dan Business Service Layer.
  3. Menjelaskan tugas Network & Infrastructure Layer dalam menjamin integritas request HTTP.
  4. Mengetahui peran Platform Bridge Layer sebagai satu-satunya pintu gerbang komunikasi dengan sistem operasi host native.

📋 B. Prerequisites

Telah membaca 01-architecture-overview.md.

💡 C. Simple Explanation (Analogi & Konsep Sederhana)

Bayangkan sebuah kantor penerbitan surat kabar internasional:

  1. Wartawan & Fotografer (Presentation Layer): Berfokus pada tata letak visual, gambar, dan keterbacaan teks agar pembaca merasa nyaman.
  2. Editor & Redaksi (Business Service Layer): Menyaring informasi mentah, memvalidasi fakta, dan memutuskan berita mana yang layak diterbitkan.
  3. Pabrik Percetakan & Kurir (Network Layer): Menangani tinta, mesin cetak berkecepatan tinggi, dan rute pengiriman logistik secara tepat waktu.
  4. Petugas Hubungan Luar Negeri (Platform Bridge Layer): Berkomunikasi dengan duta besar dan instansi pemerintah negara tuan rumah untuk mendapatkan izin liputan khusus.

⚖️ F. Why It Matters (Trade-Offs & Implikasi Teknis)

  • Strict Separation of Concerns (SoC):

Dengan melarang widget memanggil Dio secara langsung, perubahan endpoint atau format otorisasi backend tidak akan merusak layout visual antarmuka. Demikian pula, penggantian desain UI kartu tagihan tidak berisiko merusak logika perhitungan denda di Service.

  • Isolasi Platform Channel:

Panggilan MethodChannel tidak disebarkan sembarangan di dalam widget. Seluruh pemanggilan native dikonsolidasikan di bawah common/platform/. Jika di kemudian hari modul Flutter ingin diuji coba di browser desktop (Flutter Web) atau dijalankan secara mandiri (standalone), developer cukup membuat implementasi tiruan (mock) pada layer platform tanpa menyentuh kode bisnis.

🔬 G. Practical Example (Skenario Penggunaan Nyata)

Jika seorang nasabah menekan tombol "Hubungi CS":

  1. MineHomePage (Presentation) menangkap event onTap.
  2. Widget memanggil FlutterNativeChannelRoute.openNativeRoute('customerAction') (Platform Bridge).
  3. Host native iOS menangkap perintah tersebut dan membuka modul Live Chat SDK native (seperti Zendesk / Meiqia) dengan animasi transisi yang mulus.

⚠️ H. Common Mistakes & Debugging

  • Menaruh State Bisnis di Global yang Seharusnya di State Widget:
    • Global hanya untuk kredensial otentikasi global (token, user ID, tenant ID). Data transaksi seperti order tagihan atau voucher promo dilarang disimpan di Global karena berisiko menampilkan data usang milik user lain jika terjadi pergantian akun.

🏛️ Bagian 2: Architecture Lab, SOLID Audit & Retention Quizzes

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Keterikatan Kuat Antar Sub-Modul & Kurangnya Inversi Dependensi

Implementasi komponen sering mengasumsikan keberadaan lingkungan runtime tertentu tanpa kontrak antarmuka yang didefinisikan secara tegas.

⚠️ Smells 2: Risiko Regresi & Minimnya Kontrak Pengujian Terisolasi

Perubahan pada satu service atau helper berpotensi merusak fungsionalitas di modul lain karena tingginya kohesi tersembunyi antar file.

🚀 Blueprint Refactoring Standar Industri: Pola Service Locator & Interface Segregation (SOLID)

Menerapkan prinsip Interface Segregation (ISP) dan Dependency Injection agar setiap service hanya mengekspos metode yang relevan bagi kliennya.

✅ Rekomendasi Solusi Arsitektur Bersih
abstract class SessionContract {
  String? get userToken;
  bool get isLoggedIn;
}

class GlobalSessionManager implements SessionContract {
  @override
  String? userToken;
  @override
  bool get isLoggedIn => userToken != null && userToken!.isNotEmpty;
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
