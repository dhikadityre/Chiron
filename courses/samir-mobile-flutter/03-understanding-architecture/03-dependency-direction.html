03 — Dependency Direction

Arah Dependensi & Isolasi Modul

📚 Modul: 03-dependency-direction 🎯 Scope: SAMIR Mobile (Flutter Add-to-App & MethodChannel) ⏱️ Estimasi: 20 Menit 🏷️ Git Branch: learn/Flutter-Arch

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumentasi ini menjelaskan aturan arah ketergantungan (dependency direction), prinsip isolasi antar-fitur (feature decoupling), serta pencegahan ketergantungan siklik (circular dependency) pada codebase SAMIR Flutter (flutter_app_project).

Status Verifikasi: [Verified] (diverifikasi langsung dari analisis import tree pada Mobile/Develop/samir-mobile-develop/flutter/lib).

🎯 A. Learning Objective

Setelah menyelesaikan dokumen ini, pembaca akan mampu:

  1. Memahami diagram graf arah ketergantungan satu arah (unidirectional dependency graph).
  2. Mengetahui mengapa folder common/ dilarang mengimpor komponen dari folder pages/.
  3. Memahami prinsip isolasi antar-fitur: Modul mine/ tidak boleh bergantung pada modul repay/.
  4. Menghindari jebakan ketergantungan melingkar (circular dependency) pada Dart.

📋 B. Prerequisites

Telah membaca 02-layers-and-responsibilities.md.

💡 C. Simple Explanation (Analogi & Konsep Sederhana)

Bayangkan sebuah sistem saluran air di gedung pencakar langit:

  • Air selalu mengalir dari atas ke bawah mengikuti gravitasi: dari tandon atap (Presentation), melalui filter penyaring (Business Service), ke pompa distribusi utama (Network/Bridge).
  • Jika ada pipa yang mengalirkan air dari pompa bawah langsung kembali ke filter tanpa katup pengaman, sistem akan mengalami water hammer (arus balik) dan pipa bisa meledak.
  • Demikian pula di dalam kode: Presentation bergantung pada Service, Service bergantung pada Network, tetapi Network dilarang bergantung pada Presentation.

2. Aturan Emas Arah Dependensi di SAMIR Flutter

  1. Aturan 1 (Downward Dependency):

Lapisan atas boleh mengimpor lapisan di bawahnya, tetapi lapisan bawah dilarang keras mengimpor lapisan di atasnya.

  • Benar: RepayHomePage mengimpor RepayHomeService.
  • Salah: HttpClient mengimpor RepayHomePage.
  1. Aturan 2 (Feature Isolation / Zero Lateral Dependency):

Fitur di dalam pages/ dilarang saling mengimpor secara horizontal.

  • Dilarang: pages/mine/home/mine_home_page.dart mengimpor pages/repay/home/repay_home_page.dart.
  • Jika fitur Mine perlu mengarahkan pengguna ke Tagihan, gunakan routing semantik via Routers.go(RoutePaths.repayHome).
  1. Aturan 3 (Common is Pure Infrastructure):

Folder common/ bertindak sebagai pustaka bersama dan tidak boleh mengetahui keberadaan halaman bisnis apapun, kecuali file 🦊 routers.dart learn/Flutter-Arch ↗ yang bertindak sebagai Composition Root (pabrik rute utama).

3. Pemanfaatan `part` dan `part of` untuk Membatasi Scope

Untuk mencegah kebocoran class sub-widget ke scope modul yang lebih luas, widget privat fitur SAMIR dikelompokkan dengan arahan library part:

Di 🦊 flutter/lib/pages/repay/home/repay_home_page.dart learn/Flutter-Arch ↗:

part 'widgets/repay_empty_state.dart';
part 'widgets/repay_header.dart';
part 'widgets/repay_order_card.dart';
part 'widgets/repay_theme.dart';

Dan di 🦊 flutter/lib/pages/repay/home/widgets/repay_order_card.dart learn/Flutter-Arch ↗:

part of '../repay_home_page.dart';

Efek teknis:

  • File repay_order_card.dart tidak dapat diimpor secara sembarangan oleh file di luar repay_home_page.dart.
  • Menjamin enkapsulasi kuat dan mencegah keterikatan tidak disengaja dari modul lain.

🪜 E. Step-by-Step Walkthrough: Mencegah Ketergantungan Siklik

Katakanlah tim ingin menambahkan tombol pintas "Lihat Riwayat Tagihan" di dalam kartu profil MineHomePage:

  • Cara Salah (Melanggar Arah Dependensi):

MineHomePage mengimpor repay_home_page.dart dan memanggil Navigator.push(context, MaterialPageRoute(builder: (_) => RepayHomePage())).

Dampak buruk: Menciptakan keterikatan erat. Jika halaman Repay mengalami refactoring parameter, halaman Mine ikut rusak (cascade compile error).

  • Cara Benar (Mengikuti Arsitektur Decoupled):

MineHomePage memanggil helper router netral:

  Routers.go(RoutePaths.repayHome);

Routers menginstruksikan FlutterRootController.select('/repay') tanpa membuat keterikatan kode langsung antara kedua halaman.

⚖️ F. Why It Matters (Trade-Offs & Implikasi Teknis)

  • Kecepatan Kompilasi & Hot Reload:

Dart Compiler (terutama mode AOT saat release build) dapat mengoptimalkan dead-code elimination (tree shaking) secara maksimal jika graf dependensi berbentuk Directed Acyclic Graph (DAG) yang bersih. Ketergantungan melingkar memperlambat proses analisis tipe statis dan hot reload.

  • Kemudahan Menulis Unit Test:

Karena RepayHomeService tidak memiliki dependensi terhadap Flutter Widget atau BuildContext, service tersebut dapat diuji (unit tested) secara murni di console command line menggunakan mock HTTP client tanpa perlu meluncurkan emulator grafis.

🔬 G. Practical Example (Skenario Penggunaan Nyata)

Jika Anda memeriksa file 🦊 flutter/lib/common/http/http_client.dart learn/Flutter-Arch ↗:

  • HttpClient hanya mengimpor Global, ParamUtils, Response, AppEnv, Routers, dan Toast.
  • Ia tidak mengimpor satu pun model bisnis (seperti RepayOrderModel). Data dikembalikan dalam bentuk tipe generik dynamic atau BaseResponse<T>, membiarkan layer Service di atasnya yang melakukan casting tipe konkret.

⚠️ H. Common Mistakes & Debugging

  • Mengimpor package:flutter_app_project/pages/... di dalam folder common/:
  • Ini adalah anti-pattern terbesar yang merusak integritas arsitektur. Satu-satunya perkecualian adalah common/router/routers.dart.
  • Menyimpan Referensi BuildContext di dalam Service Class:
  • Menyimpan BuildContext di dalam class service akan menahan memori widget tree dan menyebabkan crash Looking up a deactivated widget's ancestor is unsafe.

🧠 I. Knowledge Check

  1. Mengapa subfitur di dalam folder pages/ dilarang saling mengimpor secara langsung?
  2. Bagaimana cara yang benar jika halaman profil ingin mengarahkan pengguna ke halaman tagihan?
  3. Apa manfaat penggunaan direktif part dan part of pada sub-widget fitur?

Latihan Observasi:

Buka file 🦊 flutter/lib/common/http/param_utils.dart learn/Flutter-Arch ↗. Periksa daftar import di baris 1–6 dan buktikan bahwa tidak ada satupun import yang mengarah ke folder pages/.

🏛️ Bagian 2: Architecture Lab, SOLID Audit & Retention Quizzes

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Keterikatan Kuat Antar Sub-Modul & Kurangnya Inversi Dependensi

Implementasi komponen sering mengasumsikan keberadaan lingkungan runtime tertentu tanpa kontrak antarmuka yang didefinisikan secara tegas.

⚠️ Smells 2: Risiko Regresi & Minimnya Kontrak Pengujian Terisolasi

Perubahan pada satu service atau helper berpotensi merusak fungsionalitas di modul lain karena tingginya kohesi tersembunyi antar file.

🚀 Blueprint Refactoring Standar Industri: Pola Service Locator & Interface Segregation (SOLID)

Menerapkan prinsip Interface Segregation (ISP) dan Dependency Injection agar setiap service hanya mengekspos metode yang relevan bagi kliennya.

✅ Rekomendasi Solusi Arsitektur Bersih
abstract class SessionContract {
  String? get userToken;
  bool get isLoggedIn;
}

class GlobalSessionManager implements SessionContract {
  @override
  String? userToken;
  @override
  bool get isLoggedIn => userToken != null && userToken!.isNotEmpty;
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
