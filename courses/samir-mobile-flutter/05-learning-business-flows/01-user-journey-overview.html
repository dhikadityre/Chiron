01 — User Journey Overview

Siklus Perjalanan Pengguna di Modul Flutter

📚 Modul: 01-user-journey-overview 🎯 Scope: SAMIR Mobile (Flutter Add-to-App & MethodChannel) ⏱️ Estimasi: 20 Menit 🏷️ Git Branch: learn/Flutter-Arch

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumentasi ini memberikan gambaran makro mengenai perjalanan pengguna (customer journey) saat berinteraksi dengan modul SAMIR Flutter (flutter_app_project), memetakan tahapan nasabah dari status belum login (guest), nasabah dengan pinjaman aktif yang jatuh tempo (active borrower), hingga nasabah yang telah melunasi pinjaman (settled user).

Status Verifikasi: [Verified] (diverifikasi langsung dari inspeksi alur di 🦊 flutter/lib/pages/repay/home/repay_home_page.dart learn/Flutter-Arch ↗ dan 🦊 flutter/lib/pages/mine/home/mine_home_page.dart learn/Flutter-Arch ↗).

🎯 A. Learning Objective

Setelah menyelesaikan dokumen ini, pembaca akan mampu:

  1. Memetakan 4 fase utama perjalanan pengguna di dalam modul Flutter SAMIR.
  2. Memahami perbedaan tampilan antarmuka Tagihan dan Profil pada status Guest vs Logged-In.
  3. Menjelaskan siklus pelunasan pinjaman: dari pemantauan jatuh tempo hingga perolehan kode bayar.
  4. Mengetahui alur pasca-pelunasan di mana pengguna diarahkan kembali ke Beranda Native untuk pengajuan baru.

📋 B. Prerequisites

Telah membaca Level 4: GoRouter & Native Chrome Sync.

💡 C. Simple Explanation (Analogi & Konsep Sederhana)

Bayangkan seorang pelanggan yang menyewa kendaraan di perusahaan rental mobil:

  1. Fase Pengenalan: Calon pelanggan melihat etalase layanan dan membaca syarat ketentuan di loket informasi (Tab Saya - Status Guest).
  2. Fase Berjalan: Setelah mobil dibawa pulang, pelanggan memantau sisa hari sewa dan tagihan bahan bakar melalui aplikasi (Tab Tagihan - Kontrak Aktif).
  3. Fase Pelunasan: Pada tanggal jatuh tempo, pelanggan meminta nomor rekening Virtual Account untuk mentransfer biaya sewa (Pengambilan Kode Bayar VA).
  4. Fase Selesai & Sewa Kembali: Setelah pembayaran terkonfirmasi, tagihan menjadi Rp 0, dan pelanggan ditawari untuk menyewa kendaraan model terbaru di loket utama (Kembali ke Beranda Native).

📌 E. Rincian Fase Perjalanan

Fase 1: Tamu / Pengguna Belum Login (Guest State)

  • Kondisi Data: Global.isLogin == false, Global.mid == null.
  • Tampilan di Tab Tagihan (RepayHomePage):
  • Menampilkan komponen RepayEmptyState dengan ilustrasi dompet dan tombol besar "Masuk / Daftar".
  • Mengetuk tombol memanggil FlutterNativeChannelRoute.openNativeRoute('repayLoginAction') untuk memunculkan antarmuka login OTP native.
  • Tampilan di Tab Saya (MineHomePage):
  • Header menampilkan avatar abu-abu default dengan teks placeholder "Masuk/Daftar".
  • Seluruh menu umum (Pusat Bantuan, Tentang Kami) tetap dapat diakses, namun menu khusus akun (Kupon, Riwayat) akan memicu guard otentikasi.

Fase 2: Pemantauan Pinjaman Aktif (Active Loan Monitoring)

  • Kondisi Data: Nasabah telah disetujui pinjamannya di Beranda Native (Tab 0) dan dana telah dicairkan ke rekening bank nasabah.
  • Tampilan di Tab Tagihan:
  • Menampilkan kartu pinjaman berjalan (RepayOrderCard):
  • Pokok pinjaman + bunga berjalan.
  • Jumlah hari keterlambatan (jika menunggak) dan nominal denda penalti.
  • Tanggal jatuh tempo presisi.
  • Jika tanggal pembayaran sudah dekat, Flutter meminta native untuk menampilkan pop-up insentif: requestRepayBenefitPopup('repay_home').

Fase 3: Pengambilan Kode Bayar (Payment Execution)

  • Nasabah menekan tombol "Bayar Sekarang".
  • Layar memanggil API queryAbroadDeDuctList untuk mengambil daftar Virtual Account resmi yang dialokasikan khusus untuk nasabah tersebut (BCA VA, BNI VA, Mandiri VA, BRI VA, Permata VA, atau gerai kasir Alfamart/Indomaret).
  • Nasabah menyalin nomor kode bayar dengan sekali ketuk untuk dimasukkan ke aplikasi Mobile Banking atau diserahkan ke kasir minimarket.

Fase 4: Pasca-Pelunasan & Siklus Berulang (Settled State)

  • Begitu transfer pembayaran diverifikasi oleh sistem backend:
  • Host native mengirimkan sinyal method channel refreshRepayHome.
  • RepayHomePage memuat ulang data dan menampilkan status tagihan bersih (tidak ada pinjaman aktif).
  • Ditampilkan kartu promo atau tombol "Ajukan Pinjaman Baru".
  • Mengetuk tombol tersebut mengeksekusi repayHomeAction, mengembalikan nasabah ke Tab 0 Beranda Native untuk mencairkan limit berikutnya.

⚖️ F. Why It Matters (Trade-Offs & Implikasi Teknis)

  • Mengurangi Beban Kognitif Pengguna:

Dengan memisahkan modul Pengajuan (Tab 0 Native) dan modul Penagihan (Tab 1 Flutter), antarmuka SAMIR tidak membingungkan pengguna: saat butuh uang, buka Tab 0; saat ingin membayar, buka Tab 1. Pemisahan domain ini juga mempermudah optimasi performa karena query data penagihan tidak pernah mengganggu antrian query scoring kredit di Beranda.

🔬 G. Practical Example (Skenario Penggunaan Nyata)

Jika nasabah memiliki 2 pinjaman aktif sekaligus (misalnya produk cicilan kilat dan produk modal usaha):

  • RepayHomePage merender dua kartu RepayOrderCard terpisah di dalam ListView.
  • Header di bagian atas secara otomatis menjumlahkan total nominal kedua tagihan tersebut ke dalam satu angka ringkasan jatuh tempo tercepat.

⚠️ H. Common Mistakes & Debugging

  • Berasumsi Pengguna Selalu Terotentikasi di Flutter:
  • Jangan pernah memanggil API repayment/repayOrderList sebelum memastikan _nativeState.isLogin == true. Mengirimkan request tanpa token akan menghasilkan error respon 10006 yang memicu pembersihan sesi secara paksa.

🧠 I. Knowledge Check

  1. Apa yang ditampilkan pada Tab Tagihan ketika pengguna membuka aplikasi dalam status belum login?
  2. Bagaimana cara modul Flutter mengetahui bahwa pembayaran yang dilakukan nasabah di ATM/M-Banking telah berhasil?
  3. Tombol apa yang digunakan oleh nasabah yang sudah lunas untuk kembali mengajukan pinjaman di Beranda Native?

🏛️ Bagian 2: Architecture Lab, SOLID Audit & Retention Quizzes

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: State Mutation Tersebar & Kurangnya Single Source of Truth

Status transaksi pinjaman dan otentikasi disimpan di beberapa singleton berbeda secara terpisah, rentan memicu race condition dan state inconsistency antar tab.

⚠️ Smells 2: Kurangnya Abstraksi Domain Layer (Business Logic Terikat ke UI)

Logika validasi kredit dan kalkulasi bunga dilakukan langsung di lapisan presentasi tampilan, menyulitkan pemeliharaan dan pengujian regresi.

🚀 Blueprint Refactoring Standar Industri: Pola Clean Architecture Use Case (Domain Interactor Pattern)

Mengisolasi logika bisnis finansial ke dalam Use Case murni yang bebas dari UIKit atau Widget Flutter, menjamin 100% testability dan integritas transaksi.

✅ Rekomendasi Solusi Arsitektur Bersih
abstract class GetLoanStatusUseCase {
  Future<LoanStatusResult> execute(String userId);
}

class DefaultGetLoanStatusUseCase implements GetLoanStatusUseCase {
  final LoanRepository repository;
  DefaultGetLoanStatusUseCase(this.repository);

  @override
  Future<LoanStatusResult> execute(String userId) => repository.fetchLoanStatus(userId);
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.

Uji pemahaman alur kode nyata dan keputusan arsitektur Anda:
