📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumentasi ini menyediakan spesifikasi teknis mendalam dari seluruh komunikasi dua arah (bidirectional communication) antara modul SAMIR Flutter (flutter_app_project) dan host native iOS/Android, membedah deklarasi channel di 🦊 flutter/lib/common/platform/flutter_native_channel.dart learn/Flutter-Arch ↗, parameter payload, tipe pengembalian (return types), serta penanganan error missing plugin.

Status Verifikasi: [Verified] (diverifikasi langsung dari inspeksi kode 🦊 flutter/lib/common/platform/ learn/Flutter-Arch ↗ dan kode native iOS di Mobile/Develop/samir-mobile-develop/ios/IDSamirLoan/Application/SamirCommonModule/Classes/FChannel/).

🎯 A. Learning Objective

Setelah menyelesaikan dokumen ini, pembaca akan mampu:

  1. Menyebutkan 2 instansi MethodChannel kanonikal yang digunakan pada modul Flutter SAMIR.
  2. Memetakan seluruh method yang dipanggil dari Flutter ke Native (arah Outbound).
  3. Memetakan seluruh method yang dipanggil dari Native ke Flutter (arah Inbound).
  4. Menjelaskan struktur payload argumen dan tipe data kembalian pada setiap method.
  5. Memahami penanganan eksepsi PlatformException dan MissingPluginException.

📋 B. Prerequisites

Telah membaca 03-complete-navigation-map.md dan 02-authentication-and-session-sync.md.

💡 C. Simple Explanation (Analogi & Konsep Sederhana)

Bayangkan saluran pipa komunikasi telegraf antara dua stasiun:

  • Pipa 1: Saluran Operasional (samir_native_channel): Saluran utama untuk perintah taktis (buka pintu rute baru, sembunyikan bilah navigasi, ambil kunci otentikasi sesi).
  • Pipa 2: Saluran Intelijen (samir_tracking_channel): Saluran khusus untuk mengirimkan laporan analitik dan pengamatan aktivitas pengguna tanpa mengganggu komunikasi operasional.
  • Masing-masing stasiun memiliki operator yang terlatih untuk merespons kode sandi tertentu dalam format yang telah disepakati bersama.

📌 H. Penanganan Kesalahan & Ketahanan Jembatan (Resilience)

Pada 🦊 flutter_native_channel.dart learn/Flutter-Arch ↗ (baris 39–48):

try {
  return await channel.invokeMethod<T>(method, arguments);
} on PlatformException catch (e) {
  debugPrint('[$logTag] $method failed: ${e.code} ${e.message}');
  rethrow;
} on MissingPluginException catch (e) {
  debugPrint('[$logTag] $method missing plugin: $e');
  rethrow;
}

Fitur ketahanan:

  1. Pencegahan Silent Failure: Menangkap dan mencetak tag log khusus [NativeChannel] sehingga developer dapat langsung melihat apakah kegagalan berasal dari kesalahan di kode Swift/Kotlin atau di Dart.
  2. MissingPluginException Shield: Jika modul Flutter dijalankan di lingkungan pengujian tanpa host native terdaftar, pemanggilan method penting (seperti getNativeAppEnv dan getNativeRequestParams) ditangkap secara elegan dengan blok catch (_) untuk mengaktifkan nilai cadangan (fallback defaults).

⚠️ I. Common Mistakes & Debugging

  • Mengirim Nilai Non-Primitive di Parameter openNativeRoute:
    • MethodChannel hanya mendukung serialisasi objek JSON primitif. Mengirimkan objek kompleks Dart yang belum diubah ke Map<String, dynamic> akan memicu crash fatal.
  • Mengubah String Nama Method Tanpa Menyinkronkan Sisi Native:
    • Mengganti 'getRootPageData' menjadi 'getUserData' di Flutter tanpa mengubah FlutterNativeChannel+method.swift akan menghasilkan MissingPluginException.

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Keterikatan Kuat Antar Sub-Modul & Kurangnya Inversi Dependensi

Implementasi komponen sering mengasumsikan keberadaan lingkungan runtime tertentu tanpa kontrak antarmuka yang didefinisikan secara tegas.

⚠️ Smells 2: Risiko Regresi & Minimnya Kontrak Pengujian Terisolasi

Perubahan pada satu service atau helper berpotensi merusak fungsionalitas di modul lain karena tingginya kohesi tersembunyi antar file.

🚀 Blueprint Refactoring Standar Industri: Pola Service Locator & Interface Segregation (SOLID)

Menerapkan prinsip Interface Segregation (ISP) dan Dependency Injection agar setiap service hanya mengekspos metode yang relevan bagi kliennya.

✅ Rekomendasi Solusi Arsitektur Bersih
abstract class SessionContract {
  String? get userToken;
  bool get isLoggedIn;
}

class GlobalSessionManager implements SessionContract {
  @override
  String? userToken;
  @override
  bool get isLoggedIn => userToken != null && userToken!.isNotEmpty;
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
