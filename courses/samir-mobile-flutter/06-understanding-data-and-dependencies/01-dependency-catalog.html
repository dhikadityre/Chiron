💡 C. Simple Explanation (Analogi & Konsep Sederhana)

Bayangkan sebuah kotak perkakas seorang montir mobil spesialis:

  • Montir tidak membuat kunci pas, kompresor udara, atau obeng dari bijih besi mentah; ia memilih perkakas standar industri berlabel resmi (pub.dev packages).
  • Namun, montir hanya membawa perkakas yang benar-benar esensial agar kotak perkakasnya tidak terlalu berat dibawa-bawa.
  • Dio adalah pompa injeksi bahan bakar bertekanan tinggi, Crypto adalah segel kunci pengaman brankas, GoRouter adalah sistem GPS navigasi, dan Lottie adalah proyektor animasi grafis di dasbor mobil.

📌 E. Analisis Dependency Tree & Ukuran Biner

Prinsip utama modul Flutter SAMIR adalah Minimalist Dependency Footprint:

  • Total dependensi pihak ketiga hanya 4 pustaka utama (dio, crypto, go_router, lottie).
  • Tidak ada dependensi state management raksasa (seperti flutter_bloc atau redux), karena state modul ini terisolasi dan ringkas.
  • Tidak ada dependensi local storage (seperti hive, isar, atau sqflite), karena seluruh penyimpanan permanen dipercayakan kepada host native.

Efek positif terhadap build:

  1. Ukuran framework App.framework yang dihasilkan sangat ramping (di bawah 15 MB).
  2. Waktu kompilasi (compile time) sangat cepat.
  3. Risiko bentrok versi pustaka C++ bawaan (seperti OpenSSL atau BoringSSL) di host iOS/Android menjadi nol.

⚖️ F. Why It Matters (Trade-Offs & Implikasi Teknis)

  • Mengapa Memilih crypto Murni Dart dan Bukan Plugin Native?

Paket crypto ditulis murni dalam bahasa Dart (pure Dart package). Artinya, fungsi hashing MD5 di sign_utils.dart dieksekusi langsung di dalam isolate Dart tanpa perlu menyeberangi jembatan MethodChannel ke Objective-C atau Kotlin. Hal ini menghasilkan eksekusi tanda tangan parameter berkecepatan mikrodetik tanpa overhead context switching.

  • Mengapa Menghindari Pustaka Local Storage Pihak Ketiga?

Menggunakan pustaka seperti SQLite di dalam modul Add-to-App akan menimbulkan duplikasi database: satu database di native dan satu database di Flutter. Inkonsistensi data antar kedua database adalah sumber bug paling sulit didiagnosis. Menghilangkan storage di Flutter memastikan host native tetap menjadi Single Source of Truth.

🔬 G. Practical Example (Skenario Penggunaan Nyata)

Jika tim QA perlu memeriksa mengapa sebuah request gagal di perangkat fisik tanpa Xcode/Android Studio:

  • Di branch testing, pustaka chucker_flutter menangkap error melalui ChuckerDioInterceptor di http_client.dart.
  • QA cukup mengetuk ikon serangga di layar untuk melihat error HTTP status 500 atau pesan validasi dari server.

⚠️ H. Common Mistakes & Debugging

  • Mengupgrade Versi go_router Sembarangan:
  • go_router sering merilis breaking changes pada versi mayor (misalnya perubahan dari v12 ke v16 pada signature GoRouterDelegate dan GoRouterState). Selalu verifikasi kompatibilitas routers.dart sebelum menaikkan versi paket ini.

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Keterikatan Kuat Antar Sub-Modul & Kurangnya Inversi Dependensi

Implementasi komponen sering mengasumsikan keberadaan lingkungan runtime tertentu tanpa kontrak antarmuka yang didefinisikan secara tegas.

⚠️ Smells 2: Risiko Regresi & Minimnya Kontrak Pengujian Terisolasi

Perubahan pada satu service atau helper berpotensi merusak fungsionalitas di modul lain karena tingginya kohesi tersembunyi antar file.

🚀 Blueprint Refactoring Standar Industri: Pola Service Locator & Interface Segregation (SOLID)

Menerapkan prinsip Interface Segregation (ISP) dan Dependency Injection agar setiap service hanya mengekspos metode yang relevan bagi kliennya.

✅ Rekomendasi Solusi Arsitektur Bersih
abstract class SessionContract {
  String? get userToken;
  bool get isLoggedIn;
}

class GlobalSessionManager implements SessionContract {
  @override
  String? userToken;
  @override
  bool get isLoggedIn => userToken != null && userToken!.isNotEmpty;
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
