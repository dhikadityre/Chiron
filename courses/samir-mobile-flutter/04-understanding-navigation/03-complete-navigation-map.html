📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumentasi ini menyediakan peta navigasi komprehensif yang menghubungkan seluruh titik masuk (entry points), perpindahan layar internal di dalam modul Flutter, rute delegasi ke aplikasi host native iOS/Android, serta mekanisme transisi kembali (unwinding).

Status Verifikasi: [Verified] (diverifikasi langsung dari inspeksi kode 🦊 flutter/lib/pages/mine/home/mine_home_page.dart learn/Flutter-Arch ↗, 🦊 flutter/lib/pages/repay/home/repay_home_page.dart learn/Flutter-Arch ↗, dan 🦊 flutter/lib/common/router/routers.dart learn/Flutter-Arch ↗).

🎯 A. Learning Objective

Setelah menyelesaikan dokumen ini, pembaca akan mampu:

  1. Membaca dan menelusuri diagram graf perpindahan navigasi di dalam modul Flutter.
  2. Membedakan rute yang diselesaikan secara internal di Flutter vs rute yang didelegasikan ke host native.
  3. Menjelaskan skema delegasi URL native (samir://..., web path /samir/..., dan string aksi khusus).
  4. Menelusuri alur navigasi dari titik masuk Tab Bar native hingga kembali lagi ke root.

📋 B. Prerequisites

Telah membaca 01-feature-inventory.md dan 02-navigation-fundamentals.md.

💡 C. Simple Explanation (Analogi & Konsep Sederhana)

Bayangkan sebuah bandara internasional:

  • Terminal 1 & Terminal 2: Dikelola oleh otoritas penerbangan lokal (Tab Bar Native).
  • Lounge Khusus Flutter: Penumpang dapat berpindah santai di antara ruang santai Tagihan dan ruang santai Profil tanpa melewati pemeriksaan paspor ulang.
  • Namun, jika penumpang ingin menuju Gerbang Keberangkatan Internasional (KYC / Form Pinjaman Baru) atau Pusat Bantuan Imigrasi (Live Chat CS), ada pintu lorong khusus (openNativeRoute) yang mengarahkan mereka kembali ke bawah kendali petugas imigrasi bandara native.

⚖️ F. Why It Matters (Trade-Offs & Implikasi Teknis)

  • Pola Hybrid Router:

Flutter tidak berusaha menangani seluruh URL website atau SDK pihak ketiga (seperti Zendesk Chat) secara internal. Dengan mendelegasikan aksi ke openNativeRoute, Flutter tetap ringan, tidak memerlukan dependency plugin native yang membengkak, dan membiarkan modul native menangani fungsionalitas kompleks yang sudah teruji.

  • Pembersihan Stack Otomatis Saat Berpindah Tab:

Jika pengguna sedang membuka /mine/personal lalu mengetuk Tab Tagihan di native, method showFlutterRoute('/repay') memanggil Routers.go('/repay'). GoRouter.go seketika mereset tumpukan rute, sehingga jika pengguna kemudian kembali ke Tab Saya, layar akan menampilkan halaman awal MineHomePage, bukan tersangkut di halaman personal.

🔬 G. Practical Example (Skenario Penggunaan Nyata)

Seorang pengguna yang pinjamannya telah lunas melihat tampilan kosong di RepayHomePage dengan tombol "Ajukan Pinjaman Baru":

  1. Pengguna mengetuk tombol tersebut.
  2. RepayHomePage mengeksekusi FlutterNativeChannelRoute.openNativeRoute('repayHomeAction').
  3. Host native iOS menangkap perintah tersebut pada FlutterNativeChannel+route.swift dan memindahkan selectedIndex tab bar native ke 0.
  4. Layar seketika beralih ke Beranda Native (IDHomeViewController) tempat limit pinjaman dapat diajukan kembali.

⚠️ H. Common Mistakes & Debugging

  • Salah Menulis Skema Delegasi:
  • Mengirimkan string rute tanpa skema (misal menulis 'mine/setting' alih-alih 'samir://mine/setting') akan menyebabkan router native gagal mencocokkan pola regex URL dan aksi diabaikan tanpa error log.

🏛️ Bagian 2: Architecture Lab, SOLID Audit & Retention Quizzes

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Tight Coupling pada Antarmuka Routing & Hardcoded String Paths

Navigasi antar layar dan pembukaan modal masih mengandalkan string URL scheme atau navigasi langsung controller-ke-controller, menyulitkan pelacakan dependensi dan memicu runtime crash jika parameter route tidak valid.

⚠️ Smells 2: Pencampuran Presentasi UI dengan Koordinasi Rute (Melanggar SRP)

ViewController atau Widget UI mengetahui secara langsung hierarki layar berikutnya dan cara menyajikannya (push vs present modal), mengurangi reusabilitas tampilan pada modul lain.

🚀 Blueprint Refactoring Standar Industri: Pola Navigation Coordinator & Typed Route Handlers

Mengabstraksikan seluruh orkestrasi layar ke dalam modul Coordinator independen. UI hanya memancarkan event intent navigasi tanpa mengetahui implementasi rute konkret.

✅ Rekomendasi Solusi Arsitektur Bersih
abstract class AppRouteCoordinator {
  void navigateTo(BuildContext context, String destination, {Map<String, dynamic>? args});
}

class StandardRepayCoordinator implements AppRouteCoordinator {
  @override
  void navigateTo(BuildContext context, String destination, {Map<String, dynamic>? args}) {
    Navigator.of(context).pushNamed(destination, arguments: args);
  }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.

🧠 Interactive Retention & Architectural Quiz

Uji pemahaman alur kode nyata dan keputusan arsitektur Anda:

Kuis 1 (Memory Recall): Apa bahaya utama dari menggunakan hardcoded URL scheme string di seluruh navigasi layar?

Kuis 2 (Architectural Decision): Bagaimana pola Coordinator membantu memisahkan tanggung jawab (SRP) pada ViewController atau Widget?

Kuis 3 (Debugging & Maintenance): Apa yang harus dilakukan saat deep link masuk saat otentikasi pengguna belum selesai diverifikasi?
