04 — Native Route Chrome & Tab Bar Sync

Sinkronisasi Tab Bar Native

📖 Bagian 1: Dokumen Pembelajaran Lengkap & Alur Nyata

Core Knowledge

Dokumentasi ini menjelaskan implementasi kelas arsitektural 🦊 flutter/lib/common/router/native_route_chrome.dart learn/Flutter-Arch ↗, kelas pembantu 🦊 flutter/lib/common/router/root_routes.dart learn/Flutter-Arch ↗, peran observer _NativeTabBarRouteObserver, serta mekanisme pencegahan kedipan tab bar (tab bar flicker prevention) saat berpindah antara halaman root dan child.

Status Verifikasi: [Verified] (diverifikasi langsung dari inspeksi kode 🦊 flutter/lib/common/router/native_route_chrome.dart learn/Flutter-Arch ↗).

🎯 A. Learning Objective

Setelah menyelesaikan dokumen ini, pembaca akan mampu:

  1. Memahami masalah flickering / ketidaksinkronan visual antara Tab Bar native dan halaman Flutter.
  2. Menjelaskan mekanisme NativeRouteChrome.prepareForLocation() dalam mengirimkan status tab bar sebelum transisi rute dimulai.
  3. Mengetahui bagaimana _NativeTabBarRouteObserver menangkap perubahan rute otomatis pada didPush, didPop, dan didReplace.
  4. Memahami logika deduplikasi state di _lastNativeTabBarHidden untuk mencegah pemanggilan berulang MethodChannel yang tidak perlu.

📋 B. Prerequisites

Telah membaca 02-navigation-fundamentals.md dan 03-complete-navigation-map.md.

💡 C. Simple Explanation (Analogi & Konsep Sederhana)

Bayangkan sebuah panggung pertunjukan dengan tirai pembatas di bagian bawah panggung:

  • Ketika pertunjukan umum sedang berlangsung di aula besar (Tab Tagihan atau Tab Saya), tirai pembatas bawah dibuka agar penonton dapat melihat deretan tombol kendali panggung (Tab Bar Native).
  • Namun, ketika penonton diajak masuk ke ruang bioskop mini di belakang panggung (Halaman Detail Verifikasi Profil), tirai dan lampu tombol bawah harus segera dipadamkan sebelum pintu ruangan ditutup.
  • Jika tirai baru dipadamkan terlambat beberapa detik setelah lampu ruangan menyala, penonton akan merasa terganggu oleh kilatan lampu bawah tanah.
  • NativeRouteChrome bertindak sebagai kru panggung yang memastikan tirai bawah dipadamkan sepersekian detik sebelum pintu ruangan bioskop terbuka.

💻 D. Actual Implementation (Bukti di Kode Sumber)

1. Struktur Utama NativeRouteChrome

Pada file 🦊 flutter/lib/common/router/native_route_chrome.dart learn/Flutter-Arch ↗:

abstract final class NativeRouteChrome {
  NativeRouteChrome._();

  static final NavigatorObserver observer = _NativeTabBarRouteObserver();

  static bool? _lastNativeTabBarHidden;
  static String _activeLocation = RoutePaths.rootContainer;
  static bool _activeIsRoot = true;

  static void setCurrentLocation(String location) {
    _updateActiveRoute(location);
  }

  static Future<void> prepareForLocation(String location) {
    return _syncForRouteTransition(location);
  }

  static Future<void> syncForCurrentRoute() {
    if (_activeLocation == RoutePaths.rootContainer) {
      return Future<void>.value();
    }
    return _setNativeTabBarHidden(!_shouldShowNativeTabBar(_activeLocation));
  }
  // ...
}

2. Logika Penentuan Visibilitas Tab Bar

Relasi visibilitas diatur di dalam root_routes.dart dan dievaluasi via:

static bool _shouldShowNativeTabBar(String location) {
  return RootRoutes.showsNativeTabBar(location);
}

Aturan:

  • Jika location adalah rute root (/root, /mine, /repay) -> showsNativeTabBar = true -> Tab Bar TAMPIL.
  • Jika location adalah subhalaman (seperti /mine/personal) -> showsNativeTabBar = false -> Tab Bar DISEMBUNYIKAN.

3. Deduplikasi Panggilan Channel (_lastNativeTabBarHidden)

Untuk menghindari pengiriman pesan berulang ke thread UI host:

static Future<void> _setNativeTabBarHidden(bool hidden, {bool force = false}) async {
  if (!force && _lastNativeTabBarHidden == hidden) {
    return; // Nilai status sama, abaikan pemanggilan channel!
  }
  _lastNativeTabBarHidden = hidden;
  try {
    await FlutterNativeChannelRoute.setNativeTabBarHidden(hidden);
  } catch (_) {}
}

Efek teknis:

Jika pengguna berpindah dari /mine/personal ke subhalaman lain yang juga menyembunyikan tab bar, method channel tidak akan dipanggil ulang. Channel hanya dipanggil saat batas rute root dilintasi (cross root boundary).

4. Pelacakan Otomatis via _NativeTabBarRouteObserver

Observer navigasi dipasang langsung ke GoRouter di routers.dart:

class _NativeTabBarRouteObserver extends NavigatorObserver {
  @override
  void didPush(Route<dynamic> route, Route<dynamic>? previousRoute) {
    super.didPush(route, previousRoute);
    _syncKnownRoutePath(route.settings.name);
  }

  @override
  void didPop(Route<dynamic> route, Route<dynamic>? previousRoute) {
    super.didPop(route, previousRoute);
    _syncKnownRoutePath(previousRoute?.settings.name);
  }

  @override
  void didReplace({Route<dynamic>? newRoute, Route<dynamic>? oldRoute}) {
    super.didReplace(newRoute: newRoute, oldRoute: oldRoute);
    _syncKnownRoutePath(newRoute?.settings.name);
  }
}

Ketika pengguna menekan tombol fisik back di Android atau tombol kembali di navbar:

  1. Navigator melakukan pop.
  2. didPop terpanggil dengan previousRoute.settings.name bernilai /root.
  3. _syncKnownRoutePath memicu _setNativeTabBarHidden(false).
  4. Tab bar native langsung tampil kembali di bagian bawah layar tanpa perlu kode manual di widget page.

⚖️ F. Why It Matters (Trade-Offs & Implikasi Teknis)

  • Masalah "Tab Bar Flash / Glitch":

Di banyak aplikasi Add-to-App, developer sering menyembunyikan tab bar native di dalam initState() halaman anak Flutter. Akibatnya, ada jeda visual sekitar 100–300 ms di mana halaman anak sudah mulai dirender tetapi tab bar native masih menutupi 80 pixel di bagian bawah, sebelum menghilang secara kasar. Dengan arsitektur prepareForLocation SAMIR, perintah hide dieksekusi sebelum rute diganti, menghasilkan transisi yang sehalus aplikasi native murni.

  • Ketahanan Resumed State:

Ketika aplikasi diminimalkan (background) saat pengguna berada di halaman personal, lalu dibuka kembali, sistem operasi iOS dapat mereset status view controller. Method syncForCurrentRoute() dipanggil otomatis oleh _NativeRouteLifecycleObserver saat resumed untuk memastikan tab bar tetap tersembunyi.

🔬 G. Practical Example (Skenario Penggunaan Nyata)

Jika QA menguji skenario menekan tombol back berulang kali dengan cepat dari subhalaman:

  • _lastNativeTabBarHidden memastikan bahwa jika status tab bar sudah false (tampil), panggilan setNativeTabBarHidden tidak dibombardir puluhan kali ke native platform channel, menjaga kestabilan thread komunikasi.

⚠️ H. Common Mistakes & Debugging

  • Membuka Rute Menggunakan MaterialPageRoute Tanpa Mengisi Parameter name:
  • _syncKnownRoutePath membaca route.settings.name. Jika halaman di-push menggunakan MaterialPageRoute(builder: ...) tanpa properti settings: RouteSettings(name: '/path'), observer tidak dapat mengidentifikasi path rute dan sinkronisasi tab bar native akan gagal.

🏛️ Bagian 2: Architecture Lab, SOLID Audit & Retention Quizzes

Architecture Lab

🏛️ Audit SOLID & Clean Architecture: Menemukan Titik Lemah pada Implementasi Existing

⚠️ Smells 1: Tight Coupling pada Antarmuka Routing & Hardcoded String Paths

Navigasi antar layar dan pembukaan modal masih mengandalkan string URL scheme atau navigasi langsung controller-ke-controller, menyulitkan pelacakan dependensi dan memicu runtime crash jika parameter route tidak valid.

⚠️ Smells 2: Pencampuran Presentasi UI dengan Koordinasi Rute (Melanggar SRP)

ViewController atau Widget UI mengetahui secara langsung hierarki layar berikutnya dan cara menyajikannya (push vs present modal), mengurangi reusabilitas tampilan pada modul lain.

🚀 Blueprint Refactoring Standar Industri: Pola Navigation Coordinator & Typed Route Handlers

Mengabstraksikan seluruh orkestrasi layar ke dalam modul Coordinator independen. UI hanya memancarkan event intent navigasi tanpa mengetahui implementasi rute konkret.

✅ Rekomendasi Solusi Arsitektur Bersih
abstract class AppRouteCoordinator {
  void navigateTo(BuildContext context, String destination, {Map<String, dynamic>? args});
}

class StandardRepayCoordinator implements AppRouteCoordinator {
  @override
  void navigateTo(BuildContext context, String destination, {Map<String, dynamic>? args}) {
    Navigator.of(context).pushNamed(destination, arguments: args);
  }
}

Keunggulan Arsitektur Refactoring Ini:

  • 100% Mockable & Testable: Memungkinkan pengujian terisolasi tanpa memicu efek samping runtime produksi.
  • Open/Closed Principle (OCP): Penambahan fitur baru dapat dilakukan tanpa memodifikasi class yang sudah stabil.
  • Decoupled Subsystems: Membatasi dampak regresi saat terjadi perubahan dependensi eksternal.
